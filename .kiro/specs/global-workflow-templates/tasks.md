# Implementation Plan

> **Implementation order — upstream dependency**: This spec consumes `workflow-parameterization` contracts (the parameter schema, the seed-time substitution + re-validation path, the start request shape `{ definitionId, parameters? }`, the start-input validation pipeline, and the audit field `boundInputs`), consumes the upstream **shared start path** (`workflowManager.start`, into which the active-execution + uncommitted-changes guards are consolidated so both HTTP and MCP enforce them) and inserts its prerequisite gate into that shared chain, and **extends** the upstream-created `start-graph-workflow-tool.ts` and `startExecutionSchema`. It **must be implemented after `workflow-parameterization` has shipped**, and this plan should be re-checked against what actually shipped before starting. The additive `tier` field this spec adds to `startExecutionSchema` is the sanctioned downstream extension point on that shared schema (the top-level start schema is not `.strict()`, so the addition is purely additive).

- [x] 2.2 (P) Implement deterministic prerequisite probes
  - Implement injectable deterministic probes with no agent or language-model step: (a) a path probe that resolves the worktree-relative path via realpath and is satisfied only when the resolved real path exists and stays contained within the target worktree, treating a symlink that escapes the worktree as unmet/invalid; (b) a skill probe that takes a backend and determines discoverability by REUSING the existing runtime skill-discovery service (`discoverCommands(worktreePath, backend)` / the `discoverClaudeItems` and `discoverCodexItems` scans in `src/lib/commands/service.ts`) rather than re-enumerating roots, so the roots mirror the run exactly — including the Codex built-in/system root `~/.codex/skills/.system` (`service.ts` ~line 384). Because that discovery returns both skills (`type: "skill"`) and slash-commands (`type: "command"`), a skill prerequisite matches either when `normalizeSkillReference(item.name) === normalizeSkillReference(prerequisite.skill)`, independent of the skill's dynamic enabled/disabled runtime state. Each probe returns a `ProbeOutcome` — satisfied, or unsatisfied with `reason: "absent" | "probe_error"`: realpath not-found and a worktree-escaping symlink → `absent`, any other filesystem error → `probe_error`, a skill-discovery failure → `probe_error`; a probe is never reported satisfied on error (fail closed, R5.10).
  - Observable completion: unit tests over a fixture worktree and skill tree show — the path probe satisfied for an in-worktree path but unsatisfied/invalid for a path whose realpath escapes the worktree via a symlink; the skill probe (via the reused runtime discovery) finds a backend's skills regardless of enabled/disabled state, finds a Codex built-in skill under `.system` (no false-fail), finds a slash-command (`type: "command"`) with the same normalized skill reference, treats `kiro-spec-design`, `/kiro-spec-design`, and `$kiro-spec-design` as the same reference, does not treat `kiro:spec-init` and `kiro-spec-init` as the same reference, and does NOT find a skill present only on a different backend's roots; a path probe hitting a non-ENOENT filesystem error and a skill probe whose discovery fails each return `reason: "probe_error"` (never satisfied); and no probe invokes any agent or modifies the target.
