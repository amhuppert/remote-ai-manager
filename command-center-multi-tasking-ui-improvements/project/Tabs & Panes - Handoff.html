Conversation Tabs
& Panes Mode

Two layers of multi-conversation control on the session page: a browser-style tab strip for the small set of conversations you actively juggle, and Panes mode — a split-screen grid that shows 2–6 of them as live mini-cockpits at once. Both render off the same juggled set, so adding or closing in one is reflected in the other.

Section 01

Overview & shared model

Tabs and Panes are two presentations of one underlying set — the conversations the operator is currently working with. They never diverge.

openTabs is the single source of truth for both surfaces. It is an ordered array of conversation ids, hard-capped at 6. The tab strip renders it as a horizontal row; Panes mode renders it as a grid. currentId marks the one active conversation — the highlighted tab, and the ringed pane. 

// app.jsx — App state (the contract both surfaces read)
const [layout, setLayout]   = React.useState("default");  // "convo"|"default"|"split"|"panes"|"diff"
const [currentId, setCurrentId] = React.useState("gc-multitasking");
const [openTabs, setOpenTabs] = React.useState([ /* …ids, MAX 6 */ ]);

// PanesView and TabsStrip are handed the SAME array:
layout === "panes"
  ? <PanesView paneIds={openTabs} activeId={currentId} … />
  : <TabsStrip tabs={tabConvs} currentId={currentId} … />

Each conversation carries the fields the rows, tabs, and panes read. The status set is the authoritative four-value enum already shipped in the production schema activeConversationSchema.status:

  • running — agent is working; dot pulses cyan.
  • waiting_for_input — blocked on you; amber. The agent's question is the production pendingQuestion field (surfaced as awaitingQuestion in the prototype).
  • awaiting — ready / paused; solid green.
  • new — not yet started; muted blue.
Why one setTabs answer "let me keep these few within one click." Panes answer "let me watch these few at once." Forcing them to share openTabs means there is no second list to keep in sync, and switching layout never loses your working context — the active pane is the same conversation as the active tab.
Section 02 · Feature

Conversation tabs

A persistent 36px strip above the conversation pane holding the small set of conversations being actively juggled — the browser-tab metaphor, distinct in intent from the sidebar (which lists all active conversations).

Anatomy of a tab

  • Status dot — 7px, colored by the four-value status enum.
  • Title — ellipsized, max 240px.
  • Hotkey hint — ⌘N shown for the first 9 tabs.
  • Close × — revealed on hover or when active. Closing removes the tab; it does not stop the agent.
  • Active tab — brighter --bg-surface background plus a 2px --cyan top stripe drawn via .tab.active::before.

Behavior

  • ⌘1–⌘9 activates tab N (handled in App's global keydown effect).
  • Click activates; × closes. Closing the current tab activates the next id in the strip.
  • The + button at the strip's right end pins another conversation. It disables at the 6-tab cap — 45% opacity, mono color, tooltip "Tab limit reached (6) — close a tab first".
Cap behaviorBoth tabs and panes are hard-capped at 6. At the cap the + button is disabled, and the sidebar right-click menu's Pin as tab item disables with the label Tab limit reached (6). The cap is enforced in promoteToTab / openFull in app.jsx — both early-return the unchanged array once length >= MAX_TABS.
Section 03 · Components

Tabs — components

Both new components live in conversation-view.jsx. They are presentational; all state lives in App.

NewTabconversation-view.jsx

A single tab. Props: conv, active, idx, onActivate, onClose. Renders the status dot (.tab__dot + .row__dot--{status}), title, the ⌘{idx+1} hint for idx < 9, and a close button that calls onClose with stopPropagation so it doesn't also activate.

NewTabsStripconversation-view.jsx

The role="tablist" container. Maps tabs → Tab, then renders the + add button (.tabs-strip__new). Receives atCap; when true the button is disabled and swaps its tooltip. Mounted by ConversationView above the InfoStrip, gated on tweaks.showTabs && tabs.length > 0.

Mount pointConversationView (existing) now renders <TabsStrip> as its first child when showTabs is on — see §11. The strip is part of the default / split / convo / diff layouts; in Panes mode the grid replaces it, since the panes already show every juggled conversation.

Every value resolves to a Command Center token — no hard-coded hex, no off-scale radii. Mono type throughout (tabs are chrome, never prose).

Section 05 · Feature

Panes mode (split screen)

A new full-width layout that lays 2–6 conversations side by side, each a fully interactive mini-cockpit. It is the multi-conversation view — the operator watches the fleet and triages without leaving the page.

Activation

A new 5th icon in the topbar layout switcher (a 2×2 grid mark), placed after Split and before Diff-only. Selecting it sets layout = "panes"; the shell hides the single-conversation center + right diff pane and shows the panes grid at full width. Esc exits Panes mode (resolved after closing any open peek or context menu).

Per-pane content

Each pane is a compact cockpit, not a static card:

  • Head — status dot, title, open-full ↗, and close × (removes from panes; does not stop the agent).
  • Meta row — status label · project / session · time.
  • Signal — an amber "Agent asks" banner carrying awaitingQuestion when waiting_for_input; otherwise the current-tool chip + status line.
  • Transcript tail — a "+ N earlier messages" summary above the last few messages. 2 panes → 4 messages, full type; 3+ panes → 2 messages, compact type (driven by compact = panes.length >= 3).
  • No per-pane composer — every reply routes through the single global composer pinned at the bottom, which targets the active pane.

Pane toolbar & adding

A toolbar reads N / 6 panes so the cap is always visible. Add pane opens a dropdown of active conversations not yet in panes; clicking one adds and focuses it. At 6 the button disables (dashed border, 50% opacity, tooltip "Pane limit reached (6) — close a pane first"). There is no inline "add" tile in the grid — Add lives only in the toolbar.

Section 08 · Design system

Pane separator — raised cards

Panes are separated using the Shadow (raised cards) treatment. Each inactive pane reads as a physical card lifted off the void, with a soft outer shadow over an 8px void gutter.

This is set by data-separator="shadow" on .panes (the default the prototype ships). It coordinates three CSS variables so the gutter, padding, and grid background stay consistent, then applies the shadow to every non-active pane: 

/* styles.css — "Shadow (raised cards)" */
.panes[data-separator="shadow"] {
  --pane-grid-bg: var(--bg-void);   /* void shows through the gutter */
  --pane-gap: 8px;
  --pane-pad: 6px;
}
.panes[data-separator="shadow"] .pane:not(.active) {
  box-shadow:
    0 0 0 1px var(--border-default),   /* crisp 1px outline */
    0 2px 8px rgba(0,0,0,.35);     /* soft drop shadow */
}
Property Value — design system
Gutter (--pane-gap) 8px of --bg-void between panes.
Grid padding (--pane-pad) 6px, so the active pane's outer ring is never clipped.
Outline 0 0 0 1px --border-default — the at-rest 1px border intensity.
Drop shadow 0 2px 8px rgba(0,0,0,.35) — the system's subtle dark card shadow, not a saturated glow.
Pane surface --bg-surface (the standard card surface).
Implementation noteThe separator look is variable-driven: the grid reads --pane-gap / --pane-pad / --pane-grid-bg, and only the per-pane box-shadow is treatment-specific. Shipping just the shadow treatment means hard-coding these three values on .panes and the one :not(.active) shadow rule — no attribute switch required in the real app.
Section 09 · Interaction

Active pane & composer fade

Active pane indicator

The active pane (= the current conversation) is marked with an outer cyan ring + glow, drawn outside the pane so it wraps the whole cockpit and is never cut by the inner transcript scrollbar. The grid's 6px padding leaves room for it. 

.pane.active {
  box-shadow:
    0 0 0 2px var(--cyan),
    0 0 16px var(--cyan-glow-strong),
    inset 0 0 24px var(--cyan-glow);
  z-index: 2;
}

Clicking any non-active pane makes it active (onActivate → setCurrentId). Because tabs and panes share currentId, switching back to the default layout lands on that same conversation.

Composer-focus fade

When the global composer's textarea gains focus, PanesView sets data-composer-focused="true" on .panes. The destination of the next prompt then becomes unmistakable:

  • Inactive panes fade to opacity: 0.4 over a 180ms ease.
  • The active pane stays full opacity and its ring intensifies (stronger glow + deeper inset).
  • On blur, both revert smoothly. In single-conversation layouts the fade is a no-op — there is nothing to fade. 
.panes[data-composer-focused="true"] .pane:not(.active) {
  opacity: 0.4;
  transition: opacity 0.18s ease;
}
.panes[data-composer-focused="true"] .pane.active {
  box-shadow:
    0 0 0 2px var(--cyan),
    0 0 24px var(--cyan-glow-strong),
    inset 0 0 32px var(--cyan-glow-strong);
}
Focus stickinessThe composer's control buttons (backend, model, effort, debug) use onMouseDown(e => e.preventDefault()) so adjusting them never steals focus from the textarea — composerFocused stays sticky and the fade doesn't flicker while the operator changes settings.
