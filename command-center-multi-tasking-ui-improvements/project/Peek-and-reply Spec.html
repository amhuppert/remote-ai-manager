Peek-and-reply
popover

Implementation handoff. A floating panel that lets you read and answer any conversation without leaving the one you're in. Opens on click of a sidebar row, anchors beside it, tails the last few messages, and routes a reply to that conversation. Spec source: SPEC.md §3.3.

01 In context

Clicking a non-current row dims and lightly blurs everything else, then floats the popover off the row's right edge. The example below is a waiting_for_input conversation — so the reply affordance is the real Ask-User-Question panel (the same component the live conversation view drops in via PromptInputSlot), not a free-text box.

03 Trigger & dismissal

Open click only

A single click on any sidebar row other than the current conversation opens the peek. The right-click context menu's Peek item is an equivalent entry point.

Hover-to-peek is intentionally not supported here — it would fire constantly during triage. (Note this differs from InfoDetailsPopover, which is hover-to-peek / click-to-pin.)

Anchor & reposition

Anchors to row.getBoundingClientRect().right + 8, top aligned ~40px above the row. After mount it clamps both axes to a 12px viewport gutter, so rows near the bottom or right edge stay fully on-screen. See §06.

Backdrop

A fixed, dim, blur(8px) scrim (.peek-backdrop, z-index:50) covers everything else; the panel sits at z-index:60. Clicking the scrim closes the peek.

Dismissal

Closes on Esc, on backdrop click, and after Open conversation navigates. Sending a reply does not auto-close — the user can fire a quick follow-up — but submitting from a waiting_for_input answer may close per product preference (open question, §08).

06 Positioning logic

Port the prototype's useLayoutEffect math. It mirrors the production McpConfigPopover pattern — measure the anchor, compute a fixed position, clamp to a viewport gutter — so reuse that component's structure when building the real one.

// from peek.jsx — runs in useLayoutEffect once the anchor is known const r = anchor.getBoundingClientRect(); const W = 460, H = 620; // panel footprint let left = r.right + 8; // float off the row's right edge let top = r.top - 40; // lift so the header aligns near the row // clamp to a 12px viewport gutter on both axes if (left + W > innerWidth - 12) left = innerWidth - W - 12; if (top + H > innerHeight - 12) top = innerHeight - H - 12; if (top < 12) top = 12; setPos({ left, top }); // position: fixed; never repositions while open
07 Implementation — wiring into the app

The prototype is self-contained mock UI. Below is how each piece maps onto the real Next.js codebase under command-center/src. The visual layer ports almost verbatim; the data and reply plumbing is the real work.

Component & placement new file

Create src/features/session/sidebar/PeekPopover.tsx. Model it on src/components/mcp/McpConfigPopover.tsx — createPortal to document.body, an anchorRef, open/onClose props, and the same mousedown-outside + Escape listeners. Owner of peek state is the sidebar container; pass the clicked row's element as the anchor.

Conversation data read

Header + meta come straight from the ActiveConversation object (src/lib/active-conversations/schemas.ts): name, status, projectName, sessionName, branchName, lastActivityAt. Note pendingQuestion here is only the flattened first-question string (derived server-side by derivePendingQuestion → pendingQuestions[0].question) — enough for the sidebar row, but not the structured options the panel needs (see next note).

The name field is nullable — fall back to a derived title. There is no diff or sibling data on this object by design.

Transcript tail query

The ActiveConversation carries no messages. Fetch the tail lazily on open via the existing messages query — conversationKeys.messages(project, session, id) — and render the last ~5 with the standard message renderer. Show a compact loading state on first open; the rest of the panel renders immediately from the conversation object.

Routing a reply critical

The peek replies to a different conversation than the active one. Instantiate the hook against the peeked conversation's ids:

const { send, queue } = useSendPrompt( conv.projectName, conv.sessionName, conv.id, );

If conv.status === "running", route through queue(text) (the agent is mid-turn). Otherwise call send(text, currentMessageCount, model, images, effort, backend) — pull currentMessageCount from that conversation's message cache, and default model/backend from conv.agentBackend. Exception: a waiting_for_input answer goes through the Ask-User-Question path below, not send/queue.

Answering an agent question — Ask-User-Question panel reuse

When the peeked conversation is waiting_for_input, render the existing src/components/AskQuestionPanel.tsx in place of the reply composer — exactly as src/features/session/prompt/PromptInputSlot.tsx swaps it for the PromptComposer (if (pendingQuestions && pendingQuestionId) → <AskQuestionPanel/>). Don't rebuild it; pass the same props (questions, questionId, currentIndex, onNavigate, onSubmit).

Data gotcha — the hard part. The structured AskQuestionItem[] (options, multiSelect, descriptions) and pendingQuestionId are not on the ActiveConversation — they live in the session-detail store (pendingQuestions / pendingQuestionId), populated by the ask-question SSE event via showQuestions. Because the peek targets a different conversation than the active one, you must source that conversation's structured pending-question state, not the active store's. If only the flattened pendingQuestion string is available (no live structured payload), fall back to the amber banner + free-text reply.

Submit. Wire onSubmit={(questionId, answers) => handleAnswerSubmit(questionId, answers)} — the same handler the conversation view uses — so the answer posts to that conversation's pending question and clears it. onNavigate handles multi-question (1 / N) paging.

Pin as tab / Open conversation

⌘T (while peek is open) and the context-menu “Pin as tab” add conv.id to the shared openTabs set (max 6 — see SPEC §3.8) without navigating. Open conversation does both: pins the tab and navigates to the conversation route, then closes the peek. Both must respect the tab cap — disable/short-circuit at 6 with the standard “Tab limit reached (6)” messaging.

Keyboard

Scope shortcuts to the open peek: Esc close, ⌘⏎ send, ⌘T pin. Use the app's useAppHotkey convention rather than a bare window listener so it composes with the global hotkey stack and the §7 Esc resolution order.

Accessibility

Panel is role="dialog" with an aria-label naming the conversation. Move focus to the textarea on open (autoFocus); restore focus to the triggering row on close. Quick-reply chips and footer actions are native <button>s. Keyboard glyphs are decorative — keep them out of accessible names.

08 Edge cases & open questions

Peeking the current conversation

No-op. Clicking the current row should not open a peek (you're already there) — the click selects/keeps it active. Only non-current rows are valid anchors.

Empty transcript

For a new conversation with no messages yet, render the centered “No messages yet.” placeholder in the body; the composer still works as the first prompt.

Conversation changes while open

If the peeked conversation transitions (e.g. running → waiting_for_input) while the panel is open, the banner, placeholder, and quick replies should update live off the active-conversations poll. Don't snapshot status at open time.

Close-on-send? decide

Open question for product: after submitting an Ask-User-Question answer, should the peek auto-close (triage-and-move-on) or stay open to show the resumed stream? The prototype closes on Submit Answer. Recommend close-on-submit for waiting_for_input, stay-open for running/awaiting quick-reply follow-ups.

Sticky / PiP peek out of scope

Keeping the peek pinned open while you edit the main conversation is explicitly deferred (SPEC §10). The backdrop is modal by design for this milestone.

Failed / done states deferred

Red error banner and the failed/done/idle chip sets ship once those statuses land in active-conversations/schemas.ts. Build the status→meta lookup now so adding them is data-only.
