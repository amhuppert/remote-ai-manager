# Performance Log

Durable record of performance issues found in Command Center, their root causes, and the patterns we now follow to prevent regressions.

**Keep this file updated.** When you fix a performance issue, add an entry under [Resolved issues](#resolved-issues). When you add new code in an area covered by a pattern below, follow it. If you find yourself violating a pattern, stop and ask why — the pattern was written because the alternative bit us.

Reproduction and verification tooling:

- `bun run logs:analyze -- report` against `~/.config/cc/logs/global.log` produces a concise Markdown report of slow requests, p95s, and accessor counts. Use `--format json` only when the result feeds code. Use this to spot regressions before merging server-side perf-sensitive changes.
- `bun run logs:analyze -- compare --before <before>.log --after <after>.log` quantifies a fix.

## Patterns to follow

### 1. Read state through a focused tier accessor — the whole-state read is deleted

There is no `readState()` anymore. The whole-tree read — a full Zod parse of every project, session, conversation, and reference document in the DB, a `structuredClone`, a second parse, sibling canonicalization, and a third parse inside `diffAndCommit` — was removed from the state-store public API once the focused-first migration was complete (Design 2.3). With ~200 conversations that read cost hundreds of milliseconds *per call*, so any per-keystroke or per-request handler that reached for it stalled the event loop. It is gone; every state read now goes through a focused accessor.

Use a focused accessor. The state store exposes:

- `getSession(projectPath, sessionName)`
- `getProjectSessions(projectPath)`
- `getProjectSessionListItems(projectPath)`
- `getConversation(projectPath, sessionName, conversationId)`
- `getSessionConversations(projectPath, sessionName)`
- `getReferenceDocuments(projectPath, sessionName)`
- `getProjectMcpOverrides(projectPath)` / `getProjectAgentCapabilityOverrides(projectPath)`
- `getArchivedProjects()` / `getPinnedProjects()`

If your route needs one project/session/conversation slice, use the matching accessor. If no accessor exists for the slice you need, **add one** — model it after the existing accessors in `src/lib/state-store/accessors.ts`. Focused accessors hit the repos directly — the store no longer holds a whole-state aggregate to read-everything-and-validate through — and they emit a distinct `accessor` label in `state.read.timing` so we can spot misuse in logs.

**Projection tiers — an accessor serves a tier, not a caller.** A focused accessor is defined by the columns it projects, and those columns fall into exactly one of three tiers:

- **identity** — key and status columns only: no blob columns, no heavy Zod parse. For "which entities exist and what state are they in" reads (liveness scans, existence checks, status rollups). Examples: `listConversationIdentities()`, `listProjectPaths()`.
- **list-item** — identity plus the display scalars a list surface renders (names, timestamps, counts). Never the machine-snapshot, pending-queue, or runtime blobs. For rendering rows without opening any single entity. Example: `listSessionConversationListItems()`.
- **detail** — one entity's full slice, for the surface that actually opens that entity. Examples: `getSession(...)`, `getConversation(...)`, `getProjectMcpOverrides(...)`, `getProjectAgentCapabilityOverrides(...)`.

**Review rule:** a new accessor must serve a named tier, not a caller. Two callers wanting slightly different subsets of the same tier share one accessor named for the tier — do not add a second, caller-shaped accessor that projects "identity plus this one extra field for route X". If a caller needs more than its tier provides, it belongs in the next tier up, or the tier's column set grows for everyone. This keeps the accessor count bounded by tiers × entities rather than by the number of call sites, and keeps every list surface off the blob columns.

The one genuinely whole-state consumer — startup rehydration — no longer reaches for a public whole-state read either, and the reader is **not a `StateStore` method**. It lives in `src/lib/state-store/startup-reader.ts` as the pure `readAllForStartup(repos)` plus a startup-owned composition `readAllForStartupFromDb(db = getDb())` that builds cold, one-shot repos over the process DB. It is deliberately **not** on the store's return shape (so `getStateStore().readAllForStartup()` does not exist — a domain module holding the store cannot run a whole-tree read) and **not** exported through the state-store index barrel. The one production consumer, `rehydrateConversationActors` (`src/lib/workflows/conversation/rehydration.ts`), deep-imports `readAllForStartupFromDb` directly; a `no-restricted-imports` gate (see below) blocks every other file from importing that module. The reader enumerates only the sessions and conversations `findAll` (column-projected, so it never selects the `machine_snapshot` blob — that moved to the owner-discriminated sidecar in Design 1) and assembles the project→session→conversation tree that `collectRehydrationCandidates` walks; each conversation's resume token is fetched from the sidecar on demand as its runtime is restored, so no snapshot blob rides the startup scan.

A regression guard lives in `src/lib/state-store/createStateStore-focused-read.test.ts`. It used to inject a spy `StateAggregate` that threw if `readAll`/`diffAndCommit` was touched; now that the aggregate is deleted the guard is **structural** — the store has no whole-state path left to fall back to — so the test builds a real store over a real DB and asserts each focused accessor returns correct data straight from the repos. When you add a new focused accessor, extend this test.

**Enforced by lint, now as two tripwires:** `eslint.config.mjs` still restricts importing `readState`, `mutateState`, and `writeState` (`no-restricted-imports`), but `WHOLE_STATE_ALLOWED` is now **empty** — there is nothing to allowlist, because the names no longer exist on the store. That rule stays as a tripwire against re-introducing one of them on the store. A second `no-restricted-imports` group blocks importing `**/state-store/startup-reader` from anywhere except `STARTUP_READER_ALLOWED` (just `rehydration.ts`) — so the whole-state enumeration cannot be reached through the startup module either, only through the one sanctioned startup path. Both restrictions are shared consts (`WHOLE_STATE_IMPORT_RESTRICTIONS`) spread into **every** block that sets `no-restricted-imports`: ESLint flat config *replaces* a rule rather than merging when a later block re-declares it for overlapping files, so any per-file override (e.g. the collaboration modules) that forgets to spread them back in silently drops the whole-state guard for its files. Reach for a focused accessor; if you think you need the whole tree, you almost certainly want a new tier accessor instead. To add a legitimate startup consumer, add it to `STARTUP_READER_ALLOWED` with a reason.

### 2. There is no whole-state mutate — write through a focused setter (or `mutateSession`/`mutateConversation`)

`mutateState` — the whole-tree mutate that hydrated the entire state, ran a user mutator on the in-memory copy, canonicalized siblings, and `diffAndCommit`'d the whole tree — is **deleted** (Design 2.2/2.3), along with `writeState`, `cloneAndValidate`, and `diffAndCommit`. Through it a single-column update (e.g. setting a draft prompt, toggling a flag) cost *the same* as a structural change, so a per-keystroke endpoint blocked the event loop for seconds. That path no longer exists; focused writes are the only mutation path:

- **Single column on a single row** — add a focused repo-level setter that runs a narrow SQL `UPDATE` and expose it on the state store. Examples already in the codebase:
  - `repos.conversations.setPendingPromptText(...)` + `state-store.setConversationPendingPromptText(...)`
  - `repos.projects.setArchived(...)` + `state-store.setProjectArchived(...)`
  - `repos.projects.setPinned(...)` + `state-store.setProjectPinned(...)`
  - `repos.sessions.setArchived(...)`, `setTddEnabled(...)`, `setFinished(...)`
- **One entity's slice** — `mutateSession(projectPath, sessionName, ...)` / `mutateConversation(...)`, and the focused override mutators `mutateSessionMcpOverrides` / `mutateConversationMcpOverrides` / `mutateProjectMcpOverrides` / `mutateProjectAgentCapabilityOverrides`. Each reads and writes only its own entity's rows — never the whole tree.

**Reach for the synchronous queue entry by default.** The default is `withWriteQueueSync(() => T)` (which the focused session-lifecycle and override setters are built on), not the async `withWriteQueue`. A synchronous callback makes "await external work while holding the global write lock" a *compile-time* impossibility — the callback can hold only the SQLite write itself plus pure computation (charter `no-slow-work-in-critical-section`). A shrink-only ratchet pins the async `withWriteQueue` call-site count so a new mutation cannot quietly reach for the async form; use the async entry only when a write genuinely must await another already-serialized write, and never run I/O, an LLM/git/network call, or an O(total-state) walk inside any callback.

Heuristic: if the only field you're touching is a single column on a single row, write a focused setter; if one doesn't exist yet, add it. The lint gate from pattern 1 now blocks importing `mutateState`/`writeState` **outright** — the names are gone from the store, so there is no whole-state mutate import left to admit.

### 3. Cache Zod-parsed rows; invalidate via a monotonic version counter

Zod parsing dominates the cost of `findAll` for any repo with non-trivial row counts. Even after a focused-accessor migration, anything that *does* enumerate rows (e.g. the aggregate's `readAll`, an `accessor=findAll` query) pays a per-row parse cost.

The conversations repo demonstrates the pattern (`src/lib/state-store/conversations-repo.ts`):

1. Keep a per-row cache `Map<id, { rawRow, parsed }>` and a `findAllCache.lastFindAllVersion` snapshot.
2. Maintain a monotonic `cacheVersion` counter; **every mutator (`upsert`, `delete`, `setPendingPromptText` when `info.changes > 0`, etc.) bumps it**.
3. In `findAll`, short-circuit when `cacheVersion === lastFindAllVersion` and return the cached array verbatim (same reference).
4. On a cache miss, fetch raw rows, and for each row compare the raw column object against the cached one; reuse the parsed result if unchanged, otherwise re-parse and update the cache.
5. Prune cache entries whose ids are no longer present.

If you add a new repo with a frequently-iterated `findAll`, replicate this structure. If you add a new mutator to an existing cached repo, **you MUST bump `cacheVersion`** in that mutator — a missed bump silently serves stale data. The conversations-repo contract test pins reference equality across calls to catch regressions (`expect(second).toBe(first)`).

### 4. Beware event-loop starvation cascades

CC runs on a single Node event loop. Any synchronous CPU spike — a big Zod parse, a structuredClone of a large state tree, a tight loop — blocks every other in-flight request. We've seen unrelated routes log multi-second durations during a typing burst because the keystroke handler was eating the loop.

Implications:

- Patterns 1–3 above are not micro-optimizations; they prevent cross-request starvation.
- When investigating "why is route X slow", check whether a different route was simultaneously holding the loop. The `state.mutate.complete` and `state.read.timing` log events with their `totalMs` and per-accessor labels are the primary diagnostic.
- Long-running work (>50 ms of CPU) should be split, batched, or pushed off the request path.

### 5. Don't add comments documenting the optimization

Per CLAUDE.md's comment rules, do not annotate fixes with comments like "now uses focused accessor" or "avoid full state read". The current state of the code is self-documenting; the historical context belongs here in this log.

### 6. Keep high-frequency React state local to the subtree that consumes it

When a hook owns state that updates at high frequency (scroll position, mouse coords, virtualized range, drag offset, etc.), the component that calls the hook re-renders on every update. Anything that component constructs in its render — inline object literals, freshly-bound callbacks, derived prop bundles — gets new identities and fans the re-render out to every child that takes those props, even if `React.memo` is in play (a fresh object literal defeats `Object.is`).

Place the hook call as low in the tree as possible — ideally inside a "container" component that wraps only the subtree that actually consumes the state. The parent never sees the update, so its sibling subtrees (top bars, dialogs, modal portals, mobile bottom bars) stay still.

Verification: `src/components/ReactScanInstrumentation.tsx` is mounted in dev via `src/app/layout.tsx` and exposes `window.__reactScanReport` / `window.__reactScanReset`. Use it with `?scan=1` and `playwright-cli --raw eval` to capture before/after render counts per component (see the `react-scan` skill).

Heuristic: if a hook returns state that changes on user interaction *within* a panel, put the hook call inside that panel's container — not above it.

### 7. Every unbounded collection in a persisted blob must be declared bounded

The recurring root cause behind several entries below is the same: an array or open map nested inside a value that is `JSON.stringify`'d whole into one SQLite TEXT column grows without eviction, so a per-element write rewrites the entire column and the row balloons. The fixes (prune to an active working set, cap to last N, normalize into a child table) are durable only if the *next* such field is caught when it is added, not in production.

`src/lib/state-store/persisted-blob-bounds.contract.test.ts` is the gate. It registers every schema serialized whole into a blob column (the conversation row, the session row, the `graph_workflow_execution` document) and, for each, walks its JSON Schema projection (`z.toJSONSchema`, via `findUnboundedCollections` in `src/lib/shared/testing/persisted-blob-bounds.ts`) for arrays without `maxItems` and open maps. Every one must carry an explicit discharge or the suite fails:

- `not-persisted` — dropped on write (cross-check the durability contract's `fieldPolicies`).
- `normalized: <table>` — not a blob; lives in its own child table.
- `pruned: <where>` — evicted to a bounded working set by named code.
- `bounded: <why>` — capped by construction (author-fixed graph, one in-flight set, config-keyed map).
- `tracked: <item>` — honestly still unbounded, pointing at the structural change that will fix it.

Discharge keys match **exactly** by default (so a collection added beside a discharged one is still flagged); suffix a key with `.**` only to cover a genuinely bounded subtree (every descendant is author-shaped, size-capped content — bounded on every write, not necessarily unchanging). Stale keys (covering nothing) also fail, so the registry cannot rot as schemas change. When you add a persisted field that is (or contains) a collection, expect this gate to fail until you cap it with `.max()` or record why it is bounded — that decision is the whole point.

### 8. Skip Zod parsing of trusted state in production via `parseTrusted` / `revalidateTrusted`

Command Center state that is always valid absent a bug does not need Zod re-validation on every read in production. Two helpers in `src/lib/shared/parse-trusted.ts` skip the parse when `process.env.NODE_ENV === "production"` and validate normally in every other environment (dev, test, CI, Storybook), so serialization drift is always caught before it can reach production:

- **`parseTrusted(schema, data, onInvalid?)`** — first-parse of trusted state read from storage (repo `rowToDomain`). The skip is safe only when the schema is **effect-free** (no `.default()` / `.transform()` / `.preprocess()` / `.catch()` / coercion), so `parse(raw)` would deep-equal `raw`. Enforced by a registry: wrap each such schema's definition with `registerTrustedSchema(schema, name)`. The guardrail `src/lib/shared/trusted-schemas.contract.test.ts` proves every registered schema is effect-free (`isEffectFree`, `src/lib/shared/testing/effect-free.ts`, which walks Zod v4's `_zod.def` tree). Adding a `.default()` to a registered schema fails that test instead of shipping a production-only divergence; `parseTrusted` also throws on an unregistered schema outside production, so a new skip site can't escape the guardrail.
- **`revalidateTrusted(schema, data, onInvalid?)`** — re-validation of already-canonical state (the whole-state assertion sites `readState` / `cloneAndValidate` / `diffAndCommit`). No effect-free requirement: the input already passed a first parse, so re-parsing is idempotent and the skip is safe regardless of schema effects. Safety comes from the caller's canonical-input contract.

Deliberately **kept parsing**: every write-path validation (cheap, a real integrity gate, and it canonicalizes effect-bearing objects before serialization); and the effect-bearing hot reads — `conversationStateSchema`, `sessionStateSchema`, `graphWorkflowExecutionSchema` — whose pervasive backward-compat `.default()`s make `parse(raw) ≠ raw` for legacy rows. Their per-row cost is already mitigated by the Pattern 3 parsed-row caches; making them skip-eligible would require eliminating those defaults via a full backfill migration (disproportionate — not done).

When you add a new effect-free trusted-state read, register the schema and route the read through `parseTrusted`. Never pass an effect-bearing schema to `parseTrusted` (the guardrail will fail); use `revalidateTrusted` only where the input is provably already-canonical. Per Pattern 5, do not annotate the skip in code — the rationale lives here.

## Resolved issues

### 2026-09-10 — The typecheck cold start was a full recheck that any realistic diff triggers; the registered check now runs the native TypeScript 7 compiler (101 s → 14.5 s cold, 12–15 s → 1.7 s warm)

- **Question**: why a fresh worktree's first `typecheck` takes about 110 s when the worktree init seeds `tsconfig.tsbuildinfo` from the parent and a repeat run takes about 15 s. The charter left three suspects: the parent's commit, relative paths in the seed, and the build-info stamp.
- **Attribution** (direct `tsc --extendedDiagnostics` runs in this worktree, one variable at a time, reason: the wrapper cannot expose TypeScript's phase timings): a warm no-op run is **14.2 s** with **no check phase at all** (program 11.2 s: parse 5.9 s, bind 3.0 s; 89 types) over 7,152 files and 1.52 M lines of TypeScript plus 489 K lines of declarations. The parent's seed, last written Sep 5, laid over this worktree reproduces the cold run: **101 s, 69.8 s of checking, 1.76 M types**; against today's sources it records 804 changed, 303 new, and 9 removed files under `src`, among them root schema modules. Every path in both build-info files is relative, so the seed is portable. Adding and then removing `next-env.d.ts` (present in the parent, absent in a fresh worktree) changed nothing (89 types both ways), and regenerating the build-info stamp cost 479 types and a 0.00 s check, so the wrapper fix of 2026-09-06 settled that suspect. The decisive runs: appending one comment to `conversations/schemas.ts` on a warm state cost **75 s (62.9 s check, 1.56 M types)**, one comment to the leaf `git/conflict-markers.ts` cost **37 s (25.5 s check, 691 K types)**, and seeding from the freshest sibling worktree, which differs from this one by only 41 source files, cost **97 s (68 s check, 1.76 M types)**, indistinguishable from the month-old seed.
- **Why**: fan-in, not a cycle. From the build info's reference map, 194 of the 4,850 source and script files have a transitive dependent closure covering at least half the program and 756 cover at least a tenth; `shared/parse-trusted.ts` (3,766 dependents), `shared/schemas.ts` (3,759), `shared/errors.ts` (3,708), `agent-backends/execution-admission.ts` (3,689), and every domain `schemas.ts` (about 3,600) sit at the top, `logging/index.ts` reaches 3,565, and even `git/conflict-markers.ts` reaches 987. The median non-test module reaches only 50, so ordinary feature edits are cheap to check, but anything that touches a schema, an error type, or a shared helper rechecks three quarters of the program. The production import graph has 2,353 strongly connected components over 2,569 modules; the largest is 103 modules (state-store 25, workflow-graph 25, agent-backends 19, conversations 5, logging 4), so breaking cycles would not change the closures above. A seed therefore helps only when its sources are identical to the checkout's; the fresh-worktree case is merely the first of many near-full rechecks a session pays.
- **Native checker comparison** (`@typescript/native-preview` 7.0.0-dev.20260707.2 run ad hoc through `bunx`, not added to the project): full check **14.2 s** (parse 0.68 s, check 12.5 s, 2.95 M types) against tsc's 101 s, and a warm incremental run **1.5 s** against tsc's 12–15 s construction floor. It resolved 7,139 files to tsc's 7,152, ignores the `next` language-service plugin, and reported one diagnostic tsc does not: TS2871 "always nullish" at `workflow-graph/route-runtime.ts:193`, untriaged. It writes `tsconfig.tsbuildinfo` in its own format, which tsc 5.9 cannot read; the next tsc run rechecked everything until the saved tsc state was restored.
- **Fix**: Alex chose the native compiler. TypeScript 7.0.2 is npm's `latest` (the July `@typescript/native-preview` is superseded), but its package is the binary alone with no `lib/typescript.js`, and ten scanners and lint rules import the compiler JS API, so `typescript` stays on 5.9 and 7.0.2 is installed as the `typescript-native` npm alias; `node_modules/.bin/tsc` still resolves to 5.9.3. `scripts/validate/typecheck.sh` runs `$PWD/node_modules/typescript-native/bin/tsc --noEmit --pretty false` with `--tsBuildInfoFile` under `node_modules/.cache/typescript-native/`, fails fast with a `bun install` hint when a checkout predates the dependency, and drops the 8 GB Node heap it no longer needs; the gate-composition contract pins the alias path, the dedicated build-info file, and the absence of `npx tsc`. TypeScript 7 reported one diagnostic tsc 5.9 does not, TS2871 "always nullish" on `(intent.laneId !== null ? execution.executionLanes[intent.laneId]?.worktreePath ?? null : null) ?? …` in `workflow-graph/route-runtime.ts`; a type probe showed both compilers type the lane as `LaneState | undefined` with `worktreePath: string | null`, so the check is a 7.0.2 difference on that shape, and the expression was rewritten to the equivalent `lane?.worktreePath ?? intent.worktreePath ?? state.worktreePath`. `bun run typecheck` still runs tsc 5.9 for parity and may differ on such diagnostics; the registered command is the gate.
- **Measurement** (branch wrapper run directly, reason: the registered run executes main's copy until this merges): cold **14.5 s**, warm **1.6–1.7 s**, against tsc 5.9's 101 s cold and 12–15 s warm on the same program; the alone-edit cases above (75 s and 37 s under tsc) are bounded by the 14.5 s full check.
- **Decision**: adopted as above. The other levers stand down: project references would still recheck everything on a foundation edit, and the seed refresh helps only a fresh worktree's first check.
- **Verification**: the gate-composition contract went red on the alias path and build-info assertions before the wrapper changed and green after; the hermetic pre-merge and scope-wrapper contracts carry a stub at the alias path inside their sandbox repos and pin the new invocation; the 35 architecture and workflow-graph files selected by the changed paths pass through the registered validator, as do registered lint, seams, and the registered typecheck (still tsc 5.9 until this merges, which doubles as parity for the rewrite); the branch wrapper passes directly at 1.9 s warm. The native preview removes both the cold check and the warm floor at the price of a preview dependency and one diagnostic to reconcile. Project references along foundation, domain, and feature partitions would let `tsc -b` skip untouched projects' construction but would still recheck everything on a foundation edit and need a multi-day design around `@/*` aliases, Next's generated types, and composite emit. Refreshing the parent's seed after each merge helps only a fresh worktree's very first check before any edit. The seed logic in `worktree-init.sh` is left as is: it is correct, and it is not the cause; the native compiler keeps its own state, so the seed now serves only `bun run typecheck`.
- **Lesson**: in a program with dense fan-in, incremental state is a cache of "nothing changed", not a partial-recheck mechanism; measure the check cost of one edit at each layer before attributing a slow run to cache freshness. Two checkers must not share one build-info file.

### 2026-07-21 — Two write-queue seams emitted their own timing logs (synchronous `appendFileSync`) while still holding the global write lock

- **Symptom**: end-to-end verification of the write-queue migration (Design 3) found two seams whose *own* bookkeeping log ran inside the critical section, so every successor writer was held across a synchronous `appendFileSync` in the production logger (`logging/logger.ts`) and `holdMs` folded the log-write duration into the next waiter's wait. (1) `write-queue.ts` `settle()` emitted `write_queue.timing` (and the possible `hold_budget_exceeded`) **before** `owners.shift()`/`ticket.release()`, holding the whole FIFO across the write. (2) The focused mutators nested their `state.mutate` timing wrapper **inside** the queue callback: the four generic mutators in `store.ts` (`mutateSession`/`mutateConversation`/`mutateProjectConversation`/`createSessionConversation`) and the four focused capability setters in `setters.ts` (`mutateProject`/`Session`/`Conversation`/`ProjectConversationAgentCapabilityOverrides`) wrapped `timed()`/`timedSync()` around the callback body, so their `state.mutate.complete` line (info-level `appendFileSync` at ≥50 ms) fired with the lock held — contradicting Pattern 2's rule that `timed()` wraps the queue CALL (as the snapshot-sidecar upsert already did).
- **Root cause**: the queue's release-then-log ordering was correct in `tryWithWriteQueue` but not mirrored in `settle()`; and the `timed()`-wraps-the-call convention was followed by the snapshot seams but not by the generic mutators or the capability setters, where the wrapper sat one level too deep. A synchronous logger emission is microseconds, but *any* I/O under the global serializer is the class `no-slow-work-in-critical-section` forbids — and the cost is paid by every unrelated writer behind the lock, not just the logging one.
- **Fix** (tasks `remediate-queue-logging-io` + `remediate-capability-precondition-queue-io`):
  - `write-queue.ts` `settle()` now `owners.shift()` + `ticket.release()` **first**, then emits `write_queue.timing` and runs the hold-budget check — matching `tryWithWriteQueue`. `holdMs` is captured at release, so it measures only the callback's run, never the trailing log write.
  - The four generic mutators in `store.ts` hoisted `timed()` to wrap the `withWriteQueue` CALL (routed through the injectable `storeLogger`); because the queue calls `release()` in its `finally` before the outer promise resolves, awaiting the queue defers the completion emit until after the section releases.
  - The four focused capability setters in `setters.ts` hoisted their `state.mutate` wrapper the same way — `timed(storeLogger, …, () => writeQueue.withWriteQueueSync(…))` instead of `withWriteQueueSync(…, () => timedSync(logger, …))`. `createSetters` gained the injectable `storeLogger` (defaulting to the module logger) so the ordering is observable in a test. The queue entry stays `withWriteQueueSync`, so the async-`withWriteQueue` ratchet is unchanged (55).
- **Verification**: red→green. A write-queue release-ordering probe (`write-queue.release-ordering.test.ts`) fires a fresh `tryWithWriteQueue` from *inside* the timing emit and asserts it is never `try_contended` — proving release preceded the log, for both the async and sync entries. A store critical-section test (`store-snapshot-critical-section.test.ts`) injects a recording queue that marks `queue:exit` in its `finally` (modelling release-before-resolve) plus a recording logger, and asserts `state.mutate.complete` lands strictly after `queue:exit` for `mutateSession`, `mutateConversation`, the snapshot upsert/delete seams, and `mutateProjectAgentCapabilityOverrides`. Typecheck clean; `seams:check` OK; agent-capabilities + state-store + mcp suites green (2,842).
- **Named telemetry follow-up (not further remediation)**: the DIRECT `state.mutate` wrapper log is now outside every migrated callback, but the *per-operation* repo timing helpers (`state-store.sessions.timing`, `.conversations.timing`, `.project-conversations.timing`, `.reference-documents.timing`) still emit their structured `.complete` line from inside `rowToDomain`/`updateChangedColumns` while the queue is held — the codebase's established per-operation logging architecture, microseconds per line, not the external-work class this sweep eliminates. Redesigning logger emission (e.g. buffering repo-timing lines to flush post-release, or a release-deferred log sink) is a bounded, low-priority telemetry change tracked here, **not** a per-callsite remediation. The same applies to the non-migrated sync/async setters (the MCP override setters and the `withWriteQueue`-based session/project setters) that still nest `timed()`/`timedSync()` inside their callback: their wrapper log is the same microsecond class and folds into the same follow-up rather than a new remediation task.
- **Lesson**: the queue's *own* telemetry is subject to the same rule as its callbacks — release the resource, then log, or the instrument becomes the stall. And a "wrap the call, not the callback" convention only holds where a test says so: nesting `timed()` one level too deep is invisible in review and only a queue-exit-before-log ordering assertion (injected logger + recording queue) catches it. Where the remaining emission is genuinely microsecond-cost established logging, name it as a telemetry follow-up rather than spawning an unbounded remediation loop — the boundary is external work (I/O, LLM, git, O(total-state)), not every structured log line.

A convention that says "don't call this" leaves the foot-gun loaded: every migration removed instances, but the surface that made new instances trivially reachable stayed. The focused-first migration had completed (every remaining reader was on a tier accessor and every mutate on a focused setter), so the whole-state methods had exactly one honest consumer left — startup rehydration — and no reason to remain public.
- **Fix** (Design 2.3 — delete the surface once focused-first is complete):
  - Deleted `readState`, `mutateState`, `writeState`, `diffAndCommit`, and `cloneAndValidate` from the state store, and removed the entire `state-aggregate.ts` (and its contract test) and the `aggregate` schema — the whole read-everything / clone / re-parse / diff machine is gone, not merely discouraged. The store is now its focused accessors and setters over the repos, with no whole-state fallback path.
  - The one honest whole-state consumer, startup rehydration, moved onto a startup-owned reader in `src/lib/state-store/startup-reader.ts` (`readAllForStartupFromDb`, over the pure `readAllForStartup(repos)`) that is **not a `StateStore` method** and **not** on the index barrel — so `getStateStore().readAllForStartup()` does not exist and domain code holding the store cannot run a whole-tree read. Only `rehydration.ts` deep-imports it, and a `no-restricted-imports` gate (`STARTUP_READER_ALLOWED`) blocks every other importer. It enumerates only the sessions + conversations column-projected `findAll` — never the `machine_snapshot` blob (moved to the sidecar in Design 1) and never the reference-document repo — so no snapshot payload rides the startup scan and each conversation's resume token loads from the sidecar on demand.
  - Migrated the last non-startup `readState` reads (`sessions/service.ts` ×10) onto focused accessors (`getSession` / `getProjectSessionListItems` / `listProjectPaths`), set `WHOLE_STATE_ALLOWED = []`, and kept the `no-restricted-imports` rule as a tripwire so a re-introduced name fails lint immediately rather than being re-allowlisted. Migrated ~20 test files off the deleted read/write via a **test-only** fixture (`src/lib/shared/testing/whole-state-fixture.ts`, `seedWholeState`/`readWholeStateForTest`) that opens fresh repos over a raw DB — not reachable from production.
- **Verification**: the focused-read guard is now **structural** rather than injected — with the aggregate deleted the store has no whole-state path to spy on, so `createStateStore-focused-read.test.ts` builds a real store over a real DB and asserts each accessor returns correct data straight from the repos. A SQL-capture startup test proves the enumeration selects no snapshot column; a `createPersistenceFixture` startup test seeds sessions/conversations (including sidecar snapshots) and proves rehydration still restores runtimes through the new reader. Grep proves no module imports the deleted names (remaining hits are comments, test names, and local mocks). Typecheck clean; `bun run lint` exit 0 with `WHOLE_STATE_ALLOWED` empty; `seams:check` OK with no ceiling raised; suites green (state-store, sessions 556, mcp 726, workflows 3582).
- **Lesson**: a hot-path anti-pattern dies when the **operation** does, not when a convention asks nicely. A lint allowlist and review discipline only *thin* a foot-gun's callers; the surface that keeps making new callers cheap survives every migration and re-fills. Complete the focused-first migration first (so nothing legitimate depends on the whole-state path), then **delete the surface** — leaving exactly one honest whole-state consumer (startup) on a private, barrel-unexported reader that domain code cannot even import. Deletion turns "please don't call `readState` on a hot path" into "there is no `readState` to call," which is the only form of the rule that cannot rot.

### 2026-07-20 — Whole-state `mutateState` writes, and in-lock config resolution, held the global write queue across O(total-state) work and file I/O

- **Verification**: red→green throughout. A second verification pass hardened three defects the first fence missed: (a) the fence was **target-only** while the effective hash spans state-backed ancestors, so a per-scope **ancestor-fence** test drives a parent (project/session) override change after the child precondition and asserts the stale-hash patch surfaces the conflict instead of committing; (b) the checked commit ran through the general `mutateConversation`, which restamped activity even on a fence miss, so a real-SQLite test asserts a raced conflict leaves conversation and session `lastActivityAt` unchanged; (c) `logPatch` ran inside the mutator callback (synchronous `appendFileSync`), so a queue-exit-before-log ordering test (injected logger) proves the log fires only after the focused write queue releases. Every new focused accessor (`getProjectAgentCapabilityOverrides`) is covered by the structural focused-read guard (`createStateStore-focused-read.test.ts` builds a real store over a real DB and asserts the accessor returns correct data straight from the repos — there is no aggregate left to spy on), and the added focused capability setters use `withWriteQueueSync` so the async-`withWriteQueue` ratchet is unchanged. Grep-clean: zero `mutateState`/`writeState` callers outside `src/lib/state-store`. `typecheck` clean; `seams:check` OK; async-ratchet 55; mcp/agent-capabilities/state-store/sessions tests green.
- **Lesson**: an optimistic-concurrency check need not run under the write lock. Resolve the expensive comparison (discovery, hashing) *before* the queue and let a short synchronous commit fence on the **fresh** target value — the queue's serialization makes the in-lock fresh read the real guard. When the hash function is an opaque I/O closure you can't split (agent-capabilities), move it outside and fence on the raw value with a bounded retry that re-runs it on conflict. And a "mutation" that performs no write (`applyAtTurnStart`'s resolve) has no business holding the write lock at all — a focused read replaces the whole critical section. Two more traps the focused-write migration exposed: (1) an FK `ON DELETE CASCADE` removes child rows *at the SQL layer*, bypassing the child repos' own `delete` and its `cache.bump()`, so any focused delete that leans on the cascade must invalidate every affected parsed-row cache by hand or a warm enumerator serves ghosts; (2) reusing the general `mutateConversation` for a config-only override write silently restamps `lastActivityAt` (it always session-touches), reordering activity even on a no-op conflict — a config edit needs a no-touch focused column write, not the activity-bearing mutate.

Wrapping is no longer detectable-by-eyeball; it is a test. (2) Wrapped all 22 stragglers (mechanical — most modules already imported `withTracing` for siblings; the SSE handler got an async adapter since `withTracing` recognises and correctly tags streaming responses). (3) Interior `timed()` spans on both offenders — queue POST (`load_conversation` state read / `enqueue` / post-enqueue `drain`) and context-artifacts GET (`resolve_target` whole-state read / `read_transcript` / `assemble`) — imported from `@/lib/logging/timed` so tests that stub the barrel keep working. (4) **Budgets as code**: a checked-in `scripts/log-budgets.json` (route-p95 1000ms, write-queue-hold 500ms, state-read 100ms, row-size 256KB) and `logs:analyze --assert-budgets` (advisory by default; non-zero exit on breach), plus two finding rules — `write_queue.hold_budget_exceeded` events ranked by the holding **label**, and `202 + durationMs > 1000` flagged as a `convention-violation`.

A single opaque request duration is a dead end — the routes most worth instrumenting are exactly the ones nobody instrumented, so interior phase spans belong on the known-slow paths first. And a budget only prevents the *next* silent regression if it is checked in and gated: encode the ceilings as data, run advisory to calibrate, then `--assert-budgets` turns a two-week archaeology project into a same-week red number.

### 2026-07-20 — Graph-workflow `mutateActive` ran external work (git worktrees, artifact I/O) *inside* the global write lock, and broadcast SSE *before* the transaction committed

- **Symptom**: the two-week audit (`docs/reports/2026-07-20_performance-sweep-root-cause-designs.md`) found the single global write queue held for **45.5s** and **20.8s** in graph-workflow scheduling, stalling every unrelated request behind it. Separately, a mutation whose commit transaction later threw had *already* broadcast its SSE/push, telling clients a mutation happened that never persisted (phantom events).
- **Root cause**: `mutateActive`'s reducer parameter was typed to accept a `Promise`, so callers `await`ed slow work while holding the lock. Two callers did exactly that: `scheduleEligibleContexts` awaited `getSession` + `provisionLane`/`disposeLane` (git `worktree add`/`remove` — the 20.8s hold), and `upsertSharedDocument` awaited artifact-registry disk capture. And `publishExecutionUpdate` *broadcast* events inside the mutation callback while the SQLite transaction committed afterward in `setters.ts`, so the broadcast could not be conditioned on the commit succeeding.
- **Fix** (Design 3.1–3.3 + 3.2 post-commit delivery): (1) `mutateActive`'s reducer is now typed **non-async** (`(exec) => Result`, no `Promise`), pinned by a `@ts-expect-error` fixture — "await an LLM/git/registry while holding the global lock" is now unrepresentable at the call site. (2) The two slow callers were split into **caller-specific staged protocols**: a short sync *reserve* mutation (classify + record `ready` intent, fenced), then the slow work **outside** the lock, then a short sync *fenced finalize* mutation that re-checks the loop fence (`matchesLoopFence` / `StaleLoopFenceError`) and pending-halt state before committing — or **compensates** (disposes the provisioned worktrees) when superseded. The generic retry wrapper `mutateActiveWithAsyncWork` was explicitly **not** built (no caller can satisfy an idempotent-`fn` contract while callbacks still broadcast). (3) The unrestricted async `mutateActive` form was deleted. (4) Event **delivery moved after commit**: mutation callbacks *derive* events (pure) and return them as inert `{ events, pushes }` DATA — never a callable — so the reducer's return value cannot broadcast. The state-store seam commits the event rows atomically with state and hands the committed delivery back; the graph-workflow repository (which owns the broadcaster + push dispatcher) performs the SSE/push delivery only after that seam call resolves, i.e. after `txn.immediate()` commits, so a thrown commit reaches the caller as a rejection with delivery never fired. (5) The execution seam adopted the sync `withWriteQueueSync` entry, and its queue callback does **no logging I/O** — the hold is measured with a bare clock read inside the lock but the `state.mutate.complete` line is emitted after the section, and the CAS-conflict / stale-fence warnings are reconstructed from captured data in a `catch` outside the lock. That lowered the async-`withWriteQueue` ratchet baseline 57 → 56 — the queue callback is now repo writes and pure computation only. (6) Purity had to hold **transitively**, not just lexically: reducers call helpers that logged via `appendFileSync`. The transition owners (`context-transitions.ts`: `transitionContextStatus`/`resetContextStateToInitial`/`transitionContextMergeStatus`/`resetRunningJoinsToPending`) were made pure — an illegal transition still throws (the error carries `contextId`/`from`/`to`/`reason`) but the `context_transition.illegal` log now fires in `mutateActive`'s `catch`, post-abort, outside the lock; the `debug`-level applied/merge/join traces (prod no-ops) were dropped. `applyAgentTaskAdd`, `enterAwaitingApproval`, and `applyApprovedDecision`/`applyRejectedDecision` now **return** their observability payloads as inert DATA, and their callers emit `task.added_by_agent`/`gate.pending`/`gate.applied` after the mutation commits. (7) Reservation-stranding + compensation-reliability fix: `scheduleEligibleContexts` commits its owner-discriminated `reservedByBatchId` stamps in the reserve, then resolves the session out of the lock — so `releaseReservations` is now defined *before* that lookup and every post-reserve failure (a missing dep, a rejected `getSession`, or a null session) releases the stamps, or the contexts would be permanently ineligible for a same-epoch retry. The compensation path is also **reliable when cleanup itself fails**: `disposeProvisioned` is **best-effort** (each lane's `disposeLane` is wrapped so one rejection cannot skip the remaining lanes) and returns the collected failures instead of throwing; a `compensateSchedule` helper then **guarantees** the reservation release runs after disposal (finally-style — a lane-disposal failure can no longer skip it) and **reports** the disposal failures via `scheduler.lane_dispose_failed` while the **original** scheduling error is preserved by the caller's `throw`. The release is **owner-checked** (`reservedByBatchId === batchId`) so it clears only the stamp this batch still owns — a concurrent same-epoch batch that re-reserved a context keeps its stamp.
- **Verification**: red→green throughout. A spy-broadcaster test proves a mutation whose transaction throws emits **zero** events and persists nothing, and a successful mutation delivers exactly the derived events once with the event rows already committed (`graph-workflow-execution-delivery.test.ts`). A superseded-fence behavior test per staged caller: `upsertSharedDocument` runs a fence-checked reserve, resolves the path out of the lock, and captures content **only after a committed finalize** — so bumping the loop generation mid-resolution refuses the finalize and captures **nothing** (no doc registered, no orphaned central-store write to compensate); `scheduleEligibleContexts` provisions both worktrees out of the lock then, when a concurrent resume bumps `loopEpoch`, the fenced finalize refuses and **disposes** both provisioned worktrees, and a separate test drives a `getSession` rejection after the reserve and asserts the stamps are released so a same-epoch retry still schedules both contexts. Two further tests pin the compensation path when cleanup fails: one makes **both** lanes' `disposeLane` reject mid-supersession and asserts **every** lane was still attempted (best-effort) while the original `StaleLoopFenceError` — not the disposal error — surfaces; the other fails a provision, makes the surviving lane's `disposeLane` reject, and — after seeding a **foreign** batch's stamp on the sibling context — asserts the owner-checked release still runs (this batch's stamp cleared, the foreign stamp left intact) while the original provision error surfaces. Purity is asserted directly: the transition owner reset test proves it emits **no** log, and the task-add / approval helpers return their observability payloads as DATA. `@ts-expect-error` fixture pins the sync reducer type. Full `workflow-graph` + `state-store` suites green; typecheck + `seams:check` clean; async-ratchet computes exactly 56.
- **Lesson**: the type system is the enforcement — a reducer that *can* return a `Promise` *will* eventually `await` git or an LLM under a global lock, no matter the comment above it; make the callback `() => T` and the whole class becomes a compile error. Slow work under a serializer doesn't need a generic escape hatch, it needs a per-caller reserve → work-outside-lock → fenced-finalize/compensate story, because each caller's side effects (worktrees here) need their own rollback. And delivery must be a value the seam owns, not an action the callback takes: as long as the callback can broadcast, some path will broadcast before the commit it's betting on.

### 2026-07-20 — `tryWithWriteQueue` let two writers run concurrently; queue timing events couldn't attribute a stall to its cause; long holds were invisible

- **Symptom**: the two-week performance audit (`docs/reports/2026-07-20_performance-sweep-root-cause-designs.md`) found the write queue — the single global serializer for every state mutation — had a correctness hole and two observability gaps. (1) `tryWithWriteQueue` (best-effort ingest) could execute its callback *concurrently* with a normal `withWriteQueue` write, i.e. two writers against SQLite at once. (2) A request blocked 45.9s on the queue was visible in `write_queue.timing` but unattributable — the events carried no `traceId` and never named the mutation *holding* the lock. (3) Multi-second holds (14.2s / 17.4s / 11.3s in the audit) produced only an `info`-level timing line indistinguishable from a healthy write.
- **Root cause**: (1) `tryWithWriteQueue` checked `pendingCount` to detect contention but never *reserved* the promise-chain `tail`. So while its callback was in flight, a `withWriteQueue` call chained onto the still-resolved predecessor `tail` and ran immediately — the `pendingCount` guard was advisory, not a lock. (2) `write_queue.timing` was emitted with only `label`/`durationMs`/`waitMs`/`holdMs`; the ambient trace was available (the logger auto-stamps it) but the queue tracked no notion of "who currently holds me", so a waiter could not record its blocker. (3) There was no hold-time ceiling — a slow critical section was just another timing line.

Because every modal is portaled outside `.app`, the modal's own entrance/voice animations keep running.   3. Kept the client-visible response shape unchanged: `manager.getEnvelope/listActive/listAll` re-inject the sidecar stream into `featureSnapshot.artifacts` via `hydrateEnvelopeArtifacts` (`manager.ts`), so `envelope-adapter.ts` and the client never touch the filesystem.

- **Verification**: new `artifacts-store.test.ts` (append/read/round-trip/malformed-skip/delete); `envelope.ts` / `workflow-envelope.ts` / `manager.ts` suites updated to assert the sidecar append + re-hydration path instead of the blob array. `bun run typecheck` clean; targeted collaboration suites green.
- **Lesson**: an unbounded append-only stream does not belong inside a blob that is rewritten in full on every state transition — the re-serialization is O(stream²) over the run. Push it to an append-only sidecar (`appendFile`, one line per entry) exactly like transcripts, keep an in-memory accumulator only where the run genuinely reads prior entries back, and rehydrate from the durable sidecar on resume. ### 2026-05-27 — Pre-merge validation exhausted RAM (vitest fork fan-out + orphaned workers)

- **Symptom**: smart-merging a branch ran `scripts/pre-merge-validate.sh`; the machine hit the macOS "out of application memory" dialog (~30 GB shown against WezTerm, the terminal hosting CC) and froze. Reported as "the validation script's memory explodes, I suspect vitest."
- **Root cause**: two independent infrastructure issues, neither branch-specific (`vitest.config.ts` was identical to main).
  1. **Uncapped fork fan-out.** Vitest's default `forks` pool spawns one worker per CPU core with no `maxForks` cap and no per-fork heap limit. On a 16-core / 16 GB machine that is ~16 heavyweight Node processes loading the full app module graph + jsdom simultaneously. Measured in isolation each step is modest (eslint 1.3 GB, tsc 1.0 GB, vitest ~4 GB peak summed RSS across 16 forks); the danger is the startup thundering herd landing on top of the already-resident CC dev server + per-session dev servers, tipping a 16 GB box (only 2 GB swap) into swap death. The "30 GB" is the WezTerm process **coalition** (CC + spawned validation + all forks), inflated further by per-process virtual reservation.
  2. **Orphaned workers on timeout.** CC runs the script through `execFile` (`src/lib/projects/repo-config.ts`), whose timeout signals only the direct child (the bash script). The deep tree `bash → npx → node → vitest → N workers` is not in a killed process group, so on timeout the N workers are **orphaned** and keep running. Each retried merge ("keeps happening") stacked another live worker set, compounding pressure into the spiral.
- **Fix**:
  - `vitest.config.ts`: set `pool: "forks"` with `poolOptions.forks.maxForks` scaled to RAM (`floor(totalmem_GB * 0.6 / 2)`, clamped to `[2, cores]` → 4 on a 16 GB box) plus `execArgv: ["--max-old-space-size=2048"]` so a single runaway file OOM-kills its own fork instead of growing unbounded. Verified: peak worker forks dropped from 16–18 to 4; suite still green.
  - Added `execFileGroup` in `src/lib/shared/exec.ts` — spawns `detached` (own process group) and on timeout signals the whole group via `process.kill(-pid, "SIGTERM")` then escalates to `SIGKILL` after a grace period. Output is buffered to 10 MB and **truncated** (not killed) past that, fixing a latent secondary bug where the default 1 MB `execFile` `maxBuffer` would have silently failed a noisy validation. `repo-config.ts`'s validation runner now uses it.
- **Lesson**: test-runner parallelism that scales to core count rather than memory is a latent OOM on high-core/low-RAM machines, and it compounds when the run shares the box with the app under test. Cap worker count by *memory budget*, not cores, and cap per-worker heap. Separately: any timeout that kills a process which fans out into a tree must kill the **process group** (`detached` + `kill(-pid)`), or the descendants orphan and accumulate across retries.

Every scroll tick → `setNavState` → `SessionPage` re-renders → a fresh inline `args` literal is passed to `SessionPageContent` → `useSessionPageViewProps` rebuilds `topbarProps`, `promptComposerProps`, `dialogsProps`, `mobileBottomBarProps` as new objects → the entire sibling tree (top bar, dialogs, modal portals, mobile bottom bar) re-renders, even though none of them care about scroll.
- **Fix**: extracted `src/features/session/conversation/ConversationPanelContainer.tsx` — a new container that owns the scroll-derived state locally by calling `useSessionPageConversation` itself. `SessionPage` no longer reads `conversation.*` or threads any scroll-derived field through `useSessionPageViewProps`. `use-session-page-view-props.tsx` now passes a `panelContainerProps` bundle through `contentProps`; `SessionContent` renders `<ConversationPanelContainer {...panelContainerProps} promptInputSlot={promptInputSlot} />` instead of `<ConversationPanel ... />` directly. Scroll-triggered re-renders are now scoped to the panel subtree.
- **Verification**: same scroll flow with react-scan after the refactor — total render events dropped from 866 to 182 (-79 %). `TddToggle`, `VoiceRecordButton`, `ConfirmDialog`, `AgentCapabilitiesModal`, `ConversationAgentCapabilitiesConfig`, `BackendToggle` all drop to **0** renders on scroll. Components that legitimately re-render on scroll (virtualized `MessageRow`, `MarkdownCodeRenderer`, the panel itself, `ConversationNav`) still do — they're inside the panel subtree.
- **Lesson**: Pattern 6. A hook owning high-frequency state pulls its calling component into the same update loop. If the calling component sits above the subtree that actually consumes the state, every sibling above the consumer pays the cost — and props rebuilt as inline literals will fan the re-render out even past `React.memo` boundaries. The fix isn't memoization; it's moving the hook call down.

### 2026-05-26 — Bulk session delete: 2N whole-state mutations + serial git worktree removes

- **Symptom**: `POST /api/projects/[name]/sessions/bulk` with `op=delete` for 3 sessions took 27.9 s (trace `b326bd6c`). Breakdown: 3× `exec:git.complete` for `worktree remove --force` totalling ~25.3 s (91 %), plus 6× `state.mutate.complete` totalling ~2.5 s (`aggregate.diff` ~380 ms each).
- **Root cause**: two compounding issues.
  1. `deleteSession` ran the orphan-retarget and the row-removal as two separate `mutateState` calls. Each paid the full `readAll` → `structuredClone` → `diffAndCommit` cost (~430 ms with the diff alone ~380 ms), so every per-session delete doubled the whole-state mutate cost.
  2. The bulk route handler in `src/lib/sessions/route-handlers.ts` looped `for await { await deps.deleteSession(...) }`, so the bookkeeping cost was 2×N for N sessions — there was no batch-aware path.
- **Fix**:
  - Fused retarget + remove into a single `mutateState` labeled `deleteSession` (`src/lib/sessions/service.ts`). `retargetOrphanedChildren` stays as a standalone export because the merge actor still uses it independently.
  - Added `bulkDeleteSessions(projectPath, sessionNames)` that runs per-session side effects (worktree removal, transcript purge, notification/job-record cleanup) and then applies a single `mutateState` labeled `bulkDeleteSessions` that retargets all orphaned children and deletes all successfully-prepared sessions in one pass. The bulk route handler now delegates to it for `op=delete`. State mutations drop from `2N` → `1` per batch.
  - Wrapped `git worktree remove` and its `rm -rf` fallback in `timed(logger, "session.worktree_remove", { ..., cleanup })`. The pre-existing `exec:git.complete` event lumped every git op under one signature, hiding worktree-remove p95 in aggregate reports — the new labeled span is now discriminable in `bun run logs:analyze -- report`.
- **Not fixed (intentionally)**: serial `git worktree remove` calls within a bulk batch. Concurrent invocations against the same parent repository race on `.git/config.lock` (same root cause as claude-code #34645). The real bottleneck is the filesystem `rm` of `node_modules`/`.next` inside each worktree, not git's bookkeeping; if this is a hotspot, the right pattern is parallel `fs.rm(worktreePath, { recursive: true, force: true })` first, then a single serial `git worktree prune` — not parallel `git worktree remove`.
- **Lesson**: Pattern 2. Even when each individual `mutate*` call is justified, callers that loop over them at the route layer multiply the whole-state cost. Bulk routes need a single batched mutation; per-step side effects belong outside of `mutateState`. Pair this with the discipline of giving long-running externals (like `git worktree remove`) a labeled `timed()` span so the report can see them.

### 2026-05-22 — Callers using `readState` where focused accessors would suffice

- **Symptom**: `state.read.timing accessor=readState` p95 = 660 ms, total 7.8 s across 14 calls in 1.5 min. The hot MCP composer path (`src/lib/workflows/conversation/actor-implementations.ts` and `src/lib/mcp/default-deps.ts`) read whole state just to look up one project's `mcpOverrides`.

### 2026-05-22 — `conversations.findAll` re-parsed every row on every read

- **Symptom**: `state-store.conversations.findAll.timing` p95 = 589 ms with ~200 rows. Each `readState`/`readAll` cycle paid this cost.
- **Root cause**: per-row JSON-column parse + Zod validation ran on every call with no caching.
- **Fix**: added a per-row cache keyed by raw column comparison plus a monotonic `cacheVersion` bumped by every mutator. `findAll` returns the cached array by reference when no writes have happened (`expect(second).toBe(first)`), and on cache miss reuses parsed rows whose raw columns are unchanged.
- **Lesson**: Pattern 3. Frequently-iterated repos need a parsed-row cache with explicit invalidation. Verified by `src/lib/state-store/conversations-repo.contract.test.ts` (`describe("conversations-repo findAll caching")`).

### 2026-05-22 — Event-loop starvation cascading to unrelated routes

### 2026-05-22 — Whole-state mutate for `setConversationPendingPromptText` (CRITICAL)
