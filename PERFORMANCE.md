# Performance Log

Durable record of performance issues found in Command Center, their root causes, and the patterns we now follow to prevent regressions.

**Keep this file updated.** When you fix a performance issue, add an entry under [Resolved issues](#resolved-issues). When you add new code in an area covered by a pattern below, follow it. If you find yourself violating a pattern, stop and ask why — the pattern was written because the alternative bit us.

Reproduction and verification tooling:

- `bun run logs:analyze -- report` against `~/.config/cc/logs/global.log` produces a JSON report of slow requests, p95s, and accessor counts. Use this to spot regressions before merging server-side perf-sensitive changes.
- `bun run logs:analyze -- compare --before <before>.log --after <after>.log` quantifies a fix.

## Patterns to follow

### 1. Never call `readState()` on a hot path — use a focused accessor

`readState()` runs a full Zod parse of every project, session, conversation, and reference document in the DB, a `structuredClone`, a second parse, sibling canonicalization, and a third parse inside `diffAndCommit`. With ~200 conversations this is hundreds of milliseconds *per call*. Calling it from a per-keystroke or per-request handler is a foot-gun.

Use a focused accessor instead. The state store exposes:

- `getSession(projectPath, sessionName)`
- `getProjectSessions(projectPath)`
- `getProjectSessionListItems(projectPath)`
- `getConversation(projectPath, sessionName, conversationId)`
- `getSessionConversations(projectPath, sessionName)`
- `getReferenceDocuments(projectPath, sessionName)`
- `getProjectMcpOverrides(projectPath)`
- `getArchivedProjects()` / `getPinnedProjects()`

If your route needs one project/session/conversation slice, use the matching accessor. If no accessor exists for the slice you need, **add one** — model it after the existing accessors in `src/lib/state-store/state-store.ts`. Focused accessors hit the repos directly, bypassing the aggregate's read-everything-and-validate cycle, and they emit a distinct `accessor` label in `state.read.timing` so we can spot misuse in logs.

`readState()` is appropriate when the work is genuinely whole-state: rehydration on startup, project discovery, the "active conversations across all projects" route, etc. Those callers must accept the cost; everyone else should not.

A regression guard lives in `src/lib/state-store/createStateStore-focused-read.test.ts` — it injects a spy `StateAggregate` that throws if `readAll` or `diffAndCommit` is touched, then asserts each focused accessor still returns correct data. When you add a new focused accessor, extend this test.

**Enforced by lint:** `eslint.config.mjs` restricts importing `readState`, `mutateState`, and `writeState` (`no-restricted-imports`) everywhere except the `WHOLE_STATE_ALLOWED` allowlist (startup recovery, project discovery, cross-project aggregation, session lifecycle). The import is the chokepoint — a module handed one of these via DI is unaffected — so a *new* whole-state importer fails lint with a message pointing here. To add a legitimate whole-state caller, list it in `WHOLE_STATE_ALLOWED` with a reason; otherwise add or use a focused accessor. This is what makes focused-first the default rather than a convention.

### 2. Never run a whole-state mutate for a single-column update

`mutateState`, `mutateSession`, and `mutateConversation` are general-purpose: they hydrate the entire state, run the user-provided mutator on the in-memory copy, canonicalize siblings, and `diffAndCommit` the whole tree. For a single-column update (e.g. setting a draft prompt, toggling a flag) the cost is *the same* as a structural change — which means a per-keystroke endpoint blocks the event loop for seconds.

For frequent single-column updates, add a focused repo-level setter that runs a narrow SQL `UPDATE` inside `writeQueue.withWriteQueue`, and expose it on the state store. Examples already in the codebase:

- `repos.conversations.setPendingPromptText(...)` + `state-store.setConversationPendingPromptText(...)`
- `repos.projects.setArchived(...)` + `state-store.setProjectArchived(...)`
- `repos.projects.setPinned(...)` + `state-store.setProjectPinned(...)`
- `repos.sessions.setArchived(...)`, `setTddEnabled(...)`, `setFinished(...)`

Heuristic: if the only field you're touching is a single column on a single row, write a focused setter. If a focused setter doesn't exist yet, add one rather than reaching for `mutate*`. The same lint gate described in pattern 1 blocks new `mutateState`/`writeState` imports.

### 3. Cache Zod-parsed rows; invalidate via a monotonic version counter

Zod parsing dominates the cost of `findAll` for any repo with non-trivial row counts. Even after a focused-accessor migration, anything that *does* enumerate rows (e.g. the aggregate's `readAll`, an `accessor=findAll` query) pays a per-row parse cost.

The conversations repo demonstrates the pattern (`src/lib/state-store/conversations-repo.ts`):

1. Keep a per-row cache `Map<id, { rawRow, parsed }>` and a `findAllCache.lastFindAllVersion` snapshot.
2. Maintain a monotonic `cacheVersion` counter; **every mutator (`upsert`, `delete`, `setPendingPromptText` when `info.changes > 0`, etc.) bumps it**.
3. In `findAll`, short-circuit when `cacheVersion === lastFindAllVersion` and return the cached array verbatim (same reference).
4. On a cache miss, fetch raw rows, and for each row compare the raw column object against the cached one; reuse the parsed result if unchanged, otherwise re-parse and update the cache.
5. Prune cache entries whose ids are no longer present.

If you add a new repo with a frequently-iterated `findAll`, replicate this structure. If you add a new mutator to an existing cached repo, **you MUST bump `cacheVersion`** in that mutator — a missed bump silently serves stale data. The conversations-repo contract test pins reference equality across calls to catch regressions (`expect(second).toBe(first)`).

### 4. Beware event-loop starvation cascades

CC runs on a single Node event loop. Any synchronous CPU spike — a big Zod parse, a structuredClone of a large state tree, a tight loop — blocks every other in-flight request. We've seen unrelated routes log multi-second durations during a typing burst because the keystroke handler was eating the loop.

Implications:

- Patterns 1–3 above are not micro-optimizations; they prevent cross-request starvation.
- When investigating "why is route X slow", check whether a different route was simultaneously holding the loop. The `state.mutate.complete` and `state.read.timing` log events with their `totalMs` and per-accessor labels are the primary diagnostic.
- Long-running work (>50 ms of CPU) should be split, batched, or pushed off the request path.

### 5. Don't add comments documenting the optimization

Per CLAUDE.md's comment rules, do not annotate fixes with comments like "now uses focused accessor" or "avoid full state read". The current state of the code is self-documenting; the historical context belongs here in this log.

### 6. Keep high-frequency React state local to the subtree that consumes it

When a hook owns state that updates at high frequency (scroll position, mouse coords, virtualized range, drag offset, etc.), the component that calls the hook re-renders on every update. Anything that component constructs in its render — inline object literals, freshly-bound callbacks, derived prop bundles — gets new identities and fans the re-render out to every child that takes those props, even if `React.memo` is in play (a fresh object literal defeats `Object.is`).

Place the hook call as low in the tree as possible — ideally inside a "container" component that wraps only the subtree that actually consumes the state. The parent never sees the update, so its sibling subtrees (top bars, dialogs, modal portals, mobile bottom bars) stay still.

Verification: `src/components/ReactScanInstrumentation.tsx` is mounted in dev via `src/app/layout.tsx` and exposes `window.__reactScanReport` / `window.__reactScanReset`. Use it with `?scan=1` and `playwright-cli --raw eval` to capture before/after render counts per component (see the `react-scan` skill).

Heuristic: if a hook returns state that changes on user interaction *within* a panel, put the hook call inside that panel's container — not above it.

### 7. Every unbounded collection in a persisted blob must be declared bounded

The recurring root cause behind several entries below is the same: an array or open map nested inside a value that is `JSON.stringify`'d whole into one SQLite TEXT column grows without eviction, so a per-element write rewrites the entire column and the row balloons. The fixes (prune to an active working set, cap to last N, normalize into a child table) are durable only if the *next* such field is caught when it is added, not in production.

`src/lib/state-store/persisted-blob-bounds.contract.test.ts` is the gate. It registers every schema serialized whole into a blob column (the conversation row, the session row, the `graph_workflow_execution` document) and, for each, walks its JSON Schema projection (`z.toJSONSchema`, via `findUnboundedCollections` in `src/lib/shared/testing/persisted-blob-bounds.ts`) for arrays without `maxItems` and open maps. Every one must carry an explicit discharge or the suite fails:

- `not-persisted` — dropped on write (cross-check the durability contract's `fieldPolicies`).
- `normalized: <table>` — not a blob; lives in its own child table.
- `pruned: <where>` — evicted to a bounded working set by named code.
- `bounded: <why>` — capped by construction (author-fixed graph, one in-flight set, config-keyed map).
- `tracked: <item>` — honestly still unbounded, pointing at the structural change that will fix it.

Discharge keys match **exactly** by default (so a collection added beside a discharged one is still flagged); suffix a key with `.**` only to cover a genuinely immutable subtree. Stale keys (covering nothing) also fail, so the registry cannot rot as schemas change. When you add a persisted field that is (or contains) a collection, expect this gate to fail until you cap it with `.max()` or record why it is bounded — that decision is the whole point.

### 2026-06-20 — `readConfig` re-read and re-parsed `config.json` on every request (uncached across requests)

- **Symptom**: `project-resolver.read_config` was a top hotspot in the live build — n=195, avg **791 ms**, max 4396 ms, total **154 s** — and it dominated the one slow-endpoint trace deep-dived (3795 ms of a 4.4 s `graph-workflow/execution` poll; the new execution read was sub-threshold). `resolveProjectPath` reads the global `config.json` for `baseDir` on essentially every request that resolves a project.
- **Root cause**: the default `readConfig` was `cache(readConfigUncached)` using React's `cache()`, which is **request-scoped** (RSC render) — in API route handlers it does not dedupe across requests, so each request re-`readFile`d + `JSON.parse`d + Zod-parsed + merged `config.json`. Part of the 791 ms is event-loop starvation during the batch-start I/O storm (a child `timed("read_config")` span was added 2026-06-06 to separate the two), but it paid the full parse every request regardless of load. There was also a duplicate read path: `createConfigReader().readConfig` and the module-level `readConfigUncached` were near-identical implementations.
- **Fix**: added the diff/transcript-cache pattern (Pattern 3) to the canonical `createConfigReader().readConfig` (`src/lib/config/loader.ts`): a parsed-config cache invalidated by the file's `(mtimeMs, size)` token, returned by reference on a hit; every write through the reader (`writeConfig`/`writeRawConfig`) nulls the cache so a same-size rewrite within one mtime tick can't serve a stale parse. The module-level singletons (`readConfig`/`readRawConfig`/`writeRawConfig`/`writeConfig`/`getConfigDirPath`) now delegate to one lazily-constructed default reader, deleting the duplicated `readConfigUncached`/module `ensureConfigDir`/standalone `writeConfig` and the React `cache()` wrapper. Cross-instance/process coherence holds via the same `(mtime, size)` token (a write changes it, so any other reader's next read re-validates).
- **Gotcha (caught pre-commit by the full suite)**: an earlier draft constructed the default reader **eagerly** at module top level (`const defaultReader = createConfigReader(CONFIG_DIR)`). The factory calls `createLogger("config")` at construction, and `@/lib/config/loader` ↔ `@/lib/logging` form an import cycle — so at loader's module-init `createLogger` was still `undefined`, crashing **58 test files** at load (suite-level failures, 0 failed assertions — easy to misread as the jsdom matcher flake). Fixed by constructing the reader lazily on first async access (`getDefaultReader()`), and keeping `getConfigDirPath()` a direct `CONFIG_DIR` return so it triggers no construction — restoring the original module's init profile.
- **Verification**: TDD red→green. `loader.test.ts` (new `readConfig caching` describe) pins: same parsed config by reference when the file is unchanged (cache hit, no re-parse); fresh content + new reference after the file changes on disk (mtime/size invalidation); fresh content after a `writeConfig` through the same reader; and default-config creation then cache. `bun run typecheck` clean; lint 0 errors; config + projects + dev-server + agent-capabilities + workflow-graph (1570) green after the lazy fix.
- **Lesson**: React's `cache()` is per-request memoization, not a cross-request cache — outside an RSC render it does nothing, so a hot config read still pays full parse on every API request. For a small file read on the hot path, the `(mtime, size)` token cache (same shape as the diff and transcript caches) is the right tool. And when you convert a lazily-called factory into a module singleton, **don't construct it at module top level if the factory has a side effect** (here `createLogger`) and the module sits in an import cycle — construct lazily, or the cycle hands you an undefined import at init. A wave of suite-level failures with zero failed assertions is the signature: it's a module-load error, not a test bug.

### 2026-06-20 — `findBySession` re-parsed every conversation blob on every `getSession`, making the focused accessor the read-amplification floor

- **Symptom**: log analysis of a live build (one active graph workflow) showed `getSession` as the dominant state-store cost — n=552, avg **380 ms**, p95 611 ms, total **210 s** — tracking 1:1 with `state-store.conversations.findBySession` (n=559, avg 367 ms, total **205 s**). `getSession`'s entire cost *was* the conversation re-parse: it loads the session's conversations via `findBySession`, which re-ran `rowToDomain` (multiple Zod `safeParse`s + JSON-column parses of `machine_snapshot`/`pending_queue`/`mcp_runtime`/runtime blobs) for **every** conversation on **every** call. Because the focused-first migration (the import-gate entry) routed nearly all reads through `getSession`, this uncached path became the hottest read in the system.
- **Root cause**: Pattern 3's parsed-row cache had been added to `conversations-repo.findAll` (the aggregate path) but never to `findBySession` (the focused-accessor path). So the moment focused-first succeeded and traffic moved off `readState`/`findAll` onto `getSession`/`findBySession`, the un-cached enumerator became the new floor. A focused accessor that re-parses on every call is as expensive as the whole-state read it replaced.
- **Fix**: extended Pattern 3 to `findBySession` (`src/lib/state-store/conversations-repo.ts`). A per-session memo keyed by the NUL-joined project/session pair, invalidated by the same monotonic `cacheVersion` every mutator already bumps, holds the parsed rows; on a warm hit it returns a **fresh array** of the cached `.conversation` objects (skipping SQL fetch and parse entirely); on a miss it fetches only that one session's rows and reuses `findAll`'s shared per-id parse cache where the raw row is unchanged (`rawRowsEqual`), re-parsing only genuinely-changed rows. A cross-session write bumps the global version (invalidating other sessions' memos) but their next read reuses every unchanged parsed row from the shared cache, so a write to session A never forces session B to re-parse. The array is fresh on every call — load-bearing because `getSessionConversations` sorts the result in place, so a shared array would corrupt the cache; the conversation **objects** are shared (the same contract `findAll` already established and the codebase already relies on — read-only consumers, Immer-wrapped mutators copy).
- **Verification**: TDD red→green. `conversations-repo.contract.test.ts` (new `findBySession caching` describe) pins: identical conversation references across calls (cache reuse, not re-parse); a fresh array each call (in-place sort/push by callers stays safe); only the changed conversation gets a new reference after upsert while siblings keep theirs; a write to another session does **not** re-parse this session's rows; and content correctness through upsert + delete (no stale cache). A caller mutation-safety survey confirmed every `getSession`/`getProjectSessions`/direct-`findBySession` consumer is read-only or Immer-wrapped. `bun run typecheck` clean; lint 0 errors; state-store + conversations (735) and sessions + prompt + workflows (1919) suites green.
- **Lesson**: Pattern 3 is not done when `findAll` is cached — it's done when **every enumerating method on the repo** is cached. `findBySession`/`findByProject` are siblings of `findAll`, and the focused-first inversion (the whole point of structural change #2) *guarantees* traffic will pour onto them. Cache the focused enumerator too, sharing the per-id parse cache so the two paths stay coherent, and return a fresh container around shared parsed elements so an in-place-sorting caller can't corrupt the cache. The cheapest proof is reference identity: same element across reads, different array.

### 2026-06-20 — The graph workflow execution rode the hot session row as one blob, re-serialized whole 3–5× per iteration tick and dragged through every `getSession`

- **Symptom**: an active graph workflow drove the run loop to write `sessions.graph_workflow_execution` 3–5 times per iteration tick, each write re-`JSON.stringify`ing the *entire* execution — including `workingDefinition` + `charter`, the two heaviest fields, which barely change. Simultaneously the field rode `getSession` (the hottest accessor, used everywhere) so every session read parsed the whole execution, and the session-detail poll refetched it ~1×/sec via SSE invalidation.
- **Root cause**: the execution was a single co-located column on the `sessions` row mixing immutable-ish definition, hot per-tick runtime, and (already-split) logs. One structure suffering all of read-amp, write-amp, and per-tick re-serialization of near-static data.
- **Fix** (structural change #4 — dedicated-table decoupling): moved the execution into its own `graph_workflow_executions` table (mirroring `graph_workflow_archived_executions`), split into `definition_json` (heavy near-static: `workingDefinition`/`charter`/`lanePlan` + immutable scalars) and `runtime_json` (hot fields), with `status`/`completed_at` projected to columns. `definition_json` is written **conditionally** — only when its `stableStringify` hash differs from the last write for that execution id (per-repo hash cache; cold cache after restart rewrites once, harmless) — so the per-tick writes touch only `runtime_json` + projections. The new repo splits on write and merges on read, so the in-memory `GraphWorkflowExecution` shape is unchanged. `rowToDomain` no longer populates `session.graphWorkflowExecution` (it's `null` on the row); every reader repointed to the focused `getActiveGraphWorkflowExecution`/`listActiveGraphWorkflowExecutions` accessor, the panel fetches it from a dedicated `…/graph-workflow/execution` endpoint via `useGraphWorkflowExecutionQuery`, and the `has_active_graph_workflow` list flag re-derives via a correlated subquery against the new table. Backfill via idempotent Umzug `0003` (positional raw split, NULLs the source column, no `KNOWN_SCHEMA_VERSION` bump — additive/forward-compatible). The events co-write stays in one transaction.
- **Guards**: a split-symmetry contract assertion (`DEFINITION_TIER_KEYS ∪ RUNTIME_TIER_KEYS` must exactly equal the schema keys — a new field unassigned to a tier fails loudly, preventing a silent drop); the migration imports those same tier constants so it can't drift from the runtime split; a focused-read test proving `getSession` returns `graphWorkflowExecution: null` even with an active execution in the new table; the new repo's own round-trip durability contract.
- **Lesson**: when one structure carries immutable, hot, and log-like data together, split it by write-frequency, not by feature. Tier the storage (write the static tier only on change), project the cheap status fields to columns, and make the hot field lazy on the shared accessor so unrelated reads stop paying for it. A shared tier-key constant + a union-equals-schema assertion is the cheap insurance against a serialization drop when the split is by field.

### 2026-06-19 — `mutateSession` read/cloned/validated the whole `ManagerState` and re-serialized every session column for a single-field change

- **Symptom**: any session mutate through `mutateSession` (toggle `archived`/`tddEnabled`/`finished`, set `objective`, patch `mcpOverrides`/`agentCapabilityOverrides`, edit/add/remove a child conversation or reference document) ran `aggregate.readAll()` over the entire state, `structuredClone`d + Zod-parsed the whole tree (non-prod), canonicalized **every** sibling session *with its children* twice (Zod-parsing each sibling's session/conversation/refDoc rows before and after the mutator), then `diffAndCommit`ed the whole tree. On top of that, when the target session row was rewritten it re-`JSON.stringify`ed and re-wrote all 18 mutable columns — including the large co-located blobs `graph_workflow_execution`, `workflow_lanes`, `workflow_envelopes` — even though only one top-level field changed. Cost scaled with total session count and the size of every session's blobs, not the size of the edit.
- **Root cause**: `mutateSession` (`src/lib/state-store/store.ts`) was a thin wrapper over the aggregate's read-everything-clone-validate-diff cycle, plus a sibling-canonicalization guard that re-parsed every other session to detect a cross-session write the `(session, project)` mutator signature made possible. No caller actually used the `project` arg, and the focus stopped at the whole tree — there was neither a focused load of the one session nor intra-row change detection.
- **Fix**: rewrote `mutateSession` to mirror the shipped `mutateConversation` per-column path, composed for children:
  1. Load only the target session + its two child collections (`repos.sessions.findByKey` + `repos.conversations.findBySession` + `repos.referenceDocuments.findBySession`). Loading only this session makes a sibling write structurally impossible, so the guard, `canonicalSessionWithChildren`, and the `project` mutator arg were all dropped (the mutator signature is now `(session)` — a 9-site mechanical change across the 8 callers + `MutationFns`).
  2. Run the mutator against the shared scoped `new Immer({ autoFreeze: false })` instance (`createDraft`/`finishDraft`, not `produce`, because `agent-capabilities.patchSession` is async), so structural sharing makes each touched top-level field and each touched child a fresh reference.
  3. `diffChangedSessionColumns(base, next)` (`sessions-repo.ts`) drives a per-top-level-field reference diff off a `SESSION_COLUMN_MAP` whose serializers are byte-identical to `sessionToSqlBind` (zero column drift), excluding the child collections and `last_activity_at`; `repos.sessions.updateChangedColumns` writes only the changed columns via a per-column-set prepared-statement cache. Crucially `last_activity_at` is **mutator-owned, not auto-restamped** on this path — unlike `mutateConversation`, the session-mutate callers are config toggles (archive/tdd/objective/override patches) that must not bump session-list ordering; the store includes `last_activity_at` in the changed set only when the mutator changed `session.lastActivityAt`, exactly as the prior whole-tree diff did via `canonicalSessionRow`.
  4. Child conversations diffed by `id`: added → `upsert`, removed → `delete`, edited → `diffChangedConversationColumns` + a new `conversations.updateChangedColumns` (no-touch — the prior whole-tree diff never restamped the conversation or session on a child edit; a mutator-set child `lastActivityAt` is still carried through explicitly since the conversation column map excludes it). Child reference documents diffed by `id`: added/changed → `upsert`, removed → `delete`.
  5. The session-column UPDATE + every child upsert/delete run in one store-owned `db.transaction(...).immediate()` (all repos share the `db` handle), so a mid-way failure rolls back every write; each repo bumps its own `cacheVersion`.
  - Two `mutateSession` callers (`createReferenceDocument` edit-existing, `deleteReferenceDocument`) returned a draft-internal child object; under the Immer path that proxy is revoked at `finishDraft`, so both now return a plain snapshot.
- **Verification**: `createStateStore-focused-read.test.ts` (new cases) drives session-scalar / child-edit / child-add / edit+add / child-remove / async-mutator / throwing-rollback mutates against the real store with `db.prepare` wrapped to record run SQL — asserting the session `UPDATE` mentions `objective`/`last_activity_at` but **not** `graph_workflow_execution`/`workflow_lanes`/`workflow_envelopes`/`mcp_overrides`, that the large `workflow_lanes` bytes are byte-identical across the mutate, that a child-only edit issues no session `UPDATE` (no blob rewrite, no restamp), and that a throwing mutator commits nothing. The replaced sibling-guard test now asserts the structural guarantee (a session mutate leaves a sibling's columns and timestamp untouched). `bun run typecheck` clean; state-store + conversations + workflow-graph + workflows + sessions suites green (3215 tests).
- **Lesson**: the same focused-write discipline applies one level up from a single row — to a parent row **and its child tables**. Avoiding the aggregate is necessary but not sufficient: the general `mutate*` path re-serializes every column on the parent row (here the large `graph_workflow_execution` blob) on any change, and canonicalizes every sibling for a guard that a focused load makes unnecessary. Load only the entity you edit, diff parent columns off a column map (never `Object.keys` — child collections have no column), diff children by id into add/edit/remove, and commit all of it in one transaction. When Immer is a pure change-detector, any value you return that aliases a draft node (a spliced-off or in-place-edited child) must be snapshotted to a plain object before `finishDraft`, or the caller hits a revoked proxy.

### 2026-06-19 — Three append-only collections grew without bound inside their blobs

- **Symptom**: three collections accumulated forever, each inflating a full-rewrite blob over the entity's life: `conversations.pending_queue` retained terminal entries (`delivered`/`failed`/`cancelled`) — including inline base64 image content — that nothing ever reads again; `graph_workflow_execution.taskStates[*].failureHistory` grew one entry per failed validation round; `graph_workflow_execution.collaborationContinuations` only flipped `deliveredAt` on delivery and never dropped consumed entries.
- **Root cause**: append-only-with-no-eviction collections living inline in a blob that is rewritten in full on every state transition (the structural anti-pattern from `PERFORMANCE_STRUCTURAL_CHANGES.md` rule #3). None of the retained data has a reader — the UI shows only active queue entries, the failure-history prompt only needs recent failures, and the continuation reader filters to undelivered.
- **Fix** (rule #3 — bound the growth, no schema change):
  1. `message-queue-service.ts` — `applyDeliveryResult` gained a `prune` flag (true for delivered/failed) and `cancelTransform` drops the cancelled row; the terminal entry is still returned for the SSE broadcast but removed from the persisted queue. Verified safe: every queue reader/transform filters to active, and the `deliveryAttemptId` guard makes a stale handler on a pruned id a clean no-op. Behavior delta: re-cancelling an already-settled message now returns `not_found` (404) instead of `not_cancellable` (409).
  2. `iteration-orchestrator.ts` — `appendFailureHistory` caps `failureHistory` to the last `MAX_FAILURE_HISTORY` (10); the sole reader renders the array into the retry prompt where only recent failures matter.
  3. `iteration-orchestrator.ts` — collaboration delivery now removes consumed continuations (and deletes the emptied context key) instead of flipping `deliveredAt`; the only reader filters to undelivered, so the observable prompt output is unchanged.
- **Lesson**: an append-only collection inside a full-rewrite blob needs an eviction rule, not just a focused write — once `mutateConversation`'s per-column write (the entry above) removed the *cross-column* cost, the queue's own unbounded growth was the remaining issue. If a collection's only reader filters to a live subset (active/undelivered/recent), the rest is dead weight: prune it at the transition rather than retaining tombstones. A Zod `z.array`/`z.record` inside a persisted blob should always trigger "what evicts from this?".

### 2026-06-19 — `mutateConversation` re-serialized and re-wrote every column for a single-field change

- **Symptom**: a scalar conversation mutate through `mutateConversation` (e.g. flip `status`, set `unread`, claim a `pendingQueue` row) re-`JSON.stringify`ed and re-wrote *every* column on the conversation row — including the large co-located blobs `machine_snapshot`, `pending_queue`, `mcp_runtime`, `agent_capabilities_runtime`, `mcp_overrides`, `agent_capability_overrides` — even though only one top-level field changed. High-frequency callers (the 8-site message-queue family, mark-unread/read, mcp/capability runtime apply, debug-mode toggles) each paid full-row serialization + a full-column SQLite `UPDATE` per call. A conversation carrying a big XState `machineSnapshot` re-stringified it on every unrelated status flip.
- **Root cause**: `mutateConversation` (`src/lib/state-store/store.ts`) loaded the row, ran the mutator in place, then persisted via `repos.conversations.upsertWithSessionTouch`, whose `ON CONFLICT(id) DO UPDATE` rewrites all 32 columns from a freshly-encoded bind. It already avoided the aggregate (Pattern 2, the 2026-06-06 entry), but the focus stopped at the row — not the *columns* within the row. There was no intra-row change detection, so every mutate wrote the whole row.
- **Fix**: per-column writes driven by a field→column map:
  1. `diffChangedConversationColumns(base, next)` (`src/lib/state-store/conversation-row-codec.ts`) — iterates a single-source-of-truth `(domainField, column, serializer)` map (the same serializers the full-row encoder uses, zero column drift) and, for each field whose **top-level reference** differs between `base` and `next`, serializes only that one column. Untouched JSON blobs are never re-stringified.   2. `repos.conversations.updateChangedColumnsWithSessionTouch(...)` (`src/lib/state-store/conversations-repo.ts`) — builds `UPDATE conversations SET <changed cols>, last_activity_at = ? WHERE …id = ?`, caching one prepared statement per sorted column-set so repeated mutation shapes reuse it, and runs the row UPDATE + the session `last_activity_at` touch in one `.immediate()` transaction, then bumps `cacheVersion` (Pattern 3). Always writes `last_activity_at`, even when no other column changed.
  3. `mutateConversation` now runs the mutator against an Immer draft (`createDraft`/`finishDraft` on a **module-scoped `new Immer({ autoFreeze: false })`** instance), so structural sharing makes each touched top-level field a fresh reference — the cheap, exact basis for the per-column reference diff — while untouched fields (the big blobs) keep the same reference and fall out of the diff. `createDraft`/`finishDraft` rather than `produce` because mutators may be async (mcp/capability runtime apply, scope stores) and Immer finalizes `produce` synchronously, revoking the proxy before an async recipe's first `await` resumes. Auto-freeze is disabled because the message-queue family returns rows it assigned into the draft and then mutates downstream (broadcast/view code) — a frozen return would silently no-op an in-place edit; a scoped instance keeps the rest of the app's default freezing intact.
- **Verification**: `createStateStore-focused-read.test.ts` (new cases) drives a scalar mutate against the real store with `db.prepare` wrapped to record run SQL, asserting the emitted `UPDATE` mentions `status`/`last_activity_at` but **not** `machine_snapshot`/`pending_queue`/`mcp_runtime`/`agent_capabilities_runtime`, that the persisted `machine_snapshot` bytes are byte-identical across the mutate, and that the returned value is mutable (not frozen). `conversations-repo.contract.test.ts` (new `updateChangedColumnsWithSessionTouch` describe) asserts single-/multi-column writes, no-op-still-touches-`last_activity_at`, `findAll` cache invalidation, single-transaction atomicity (success commits both; a `RAISE(ABORT)` trigger rolls back both), and a sequence of single-column writes leaving every other column byte-identical to the full-upsert baseline. `bun run typecheck` clean; conversations + workflows + mcp + agent-capabilities + state-store suites green.
- **Lesson**: focused writes extend below the row, to **column** granularity. Avoiding the aggregate is necessary but not sufficient when a row co-locates a hot scalar with a large blob — the general `upsert` still re-serializes and re-writes the blob on every scalar change. Detect the changed top-level fields (Immer structural sharing makes this exact and cheap) and `UPDATE` only those columns; drive the diff from a column map, never `Object.keys`, because some domain fields have no column. When using Immer purely as a change detector and you hand the mutator's return value back to callers, disable auto-freeze on a scoped instance — the value may alias a node that was assigned into the draft, and a frozen return breaks a caller's later in-place edit silently.

### 2026-06-19 — Collaboration artifact stream re-serialized inside the envelope blob on every lifecycle upsert

- **Symptom**: the `workflow_envelopes` write cost grew with run length. (This compounded the whole-state `mutateSession` cost in the entry above.)
- **Fix**: moved the stream out of the blob into a durable per-workflow JSONL sidecar, mirroring how conversation transcripts already work:
  1. New `src/lib/workflows/collaboration/artifacts-store.ts` — `appendCollaborationArtifact` writes one JSONL line per artifact under `<configDir>/collab-artifacts/<workflowId>.jsonl` (OUTSIDE the worktree, durable across worktree removal and process restart); `readCollaborationArtifacts` reads them back in append order, skipping+logging malformed lines; `deleteCollaborationArtifacts` purges the sidecar.

The user path keeps an in-memory `ArtifactTracker.artifacts` accumulator as the *in-run* source of truth (the negotiation loop composes prompts from prior-round artifacts) with `appendSink` as the durability sink; the workflow path threads artifacts through explicit locals and appends straight to the sidecar via `pushArtifact`. On resume, `initializeEnvelope` rehydrates the prior stream from the sidecar (`deps.readArtifacts`), not the blob — load-bearing because the slice may re-enter in a fresh process.
  3. Kept the client-visible response shape unchanged: `manager.getEnvelope/listActive/listAll` re-inject the sidecar stream into `featureSnapshot.artifacts` via `hydrateEnvelopeArtifacts` (`manager.ts`), so `envelope-adapter.ts` and the client never touch the filesystem.

- **Verification**: new `artifacts-store.test.ts` (append/read/round-trip/malformed-skip/delete); `envelope.ts` / `workflow-envelope.ts` / `manager.ts` suites updated to assert the sidecar append + re-hydration path instead of the blob array. `bun run typecheck` clean; targeted collaboration suites green.
- **Lesson**: an unbounded append-only stream does not belong inside a blob that is rewritten in full on every state transition — the re-serialization is O(stream²) over the run. Push it to an append-only sidecar (`appendFile`, one line per entry) exactly like transcripts, keep an in-memory accumulator only where the run genuinely reads prior entries back, and rehydrate from the durable sidecar on resume. Re-inject at the read boundary so the persisted-shape change stays invisible to clients. Place the sidecar under `<configDir>` (not the worktree) so it survives worktree removal, and purge it explicitly on session delete since nothing else will.

### 2026-05-27 — Pre-merge validation exhausted RAM (vitest fork fan-out + orphaned workers)

- **Symptom**: smart-merging a branch ran `scripts/pre-merge-validate.sh`; the machine hit the macOS "out of application memory" dialog (~30 GB shown against WezTerm, the terminal hosting CC) and froze. Reported as "the validation script's memory explodes, I suspect vitest."
- **Root cause**: two independent infrastructure issues, neither branch-specific (`vitest.config.ts` was identical to main).
  1. **Uncapped fork fan-out.** Vitest's default `forks` pool spawns one worker per CPU core with no `maxForks` cap and no per-fork heap limit. On a 16-core / 16 GB machine that is ~16 heavyweight Node processes loading the full app module graph + jsdom simultaneously. Measured in isolation each step is modest (eslint 1.3 GB, tsc 1.0 GB, vitest ~4 GB peak summed RSS across 16 forks); the danger is the startup thundering herd landing on top of the already-resident CC dev server + per-session dev servers, tipping a 16 GB box (only 2 GB swap) into swap death. The "30 GB" is the WezTerm process **coalition** (CC + spawned validation + all forks), inflated further by per-process virtual reservation.
  2. **Orphaned workers on timeout.** CC runs the script through `execFile` (`src/lib/projects/repo-config.ts`), whose timeout signals only the direct child (the bash script). The deep tree `bash → npx → node → vitest → N workers` is not in a killed process group, so on timeout the N workers are **orphaned** and keep running. Each retried merge ("keeps happening") stacked another live worker set, compounding pressure into the spiral.
- **Fix**:
  - `vitest.config.ts`: set `pool: "forks"` with `poolOptions.forks.maxForks` scaled to RAM (`floor(totalmem_GB * 0.6 / 2)`, clamped to `[2, cores]` → 4 on a 16 GB box) plus `execArgv: ["--max-old-space-size=2048"]` so a single runaway file OOM-kills its own fork instead of growing unbounded. Verified: peak worker forks dropped from 16–18 to 4; suite still green.
  - Added `execFileGroup` in `src/lib/shared/exec.ts` — spawns `detached` (own process group) and on timeout signals the whole group via `process.kill(-pid, "SIGTERM")` then escalates to `SIGKILL` after a grace period. Output is buffered to 10 MB and **truncated** (not killed) past that, fixing a latent secondary bug where the default 1 MB `execFile` `maxBuffer` would have silently failed a noisy validation. `repo-config.ts`'s validation runner now uses it.
- **Lesson**: test-runner parallelism that scales to core count rather than memory is a latent OOM on high-core/low-RAM machines, and it compounds when the run shares the box with the app under test. Cap worker count by *memory budget*, not cores, and cap per-worker heap. Separately: any timeout that kills a process which fans out into a tree must kill the **process group** (`detached` + `kill(-pid)`), or the descendants orphan and accumulate across retries.

### 2026-05-27 — Scrolling the message panel re-rendered top-bar/dialog components

- **Symptom**: react-scan captured 866 render events during a single scroll flow on the conversation page. `TddToggle`, `VoiceRecordButton`, `ConfirmDialog`, `AgentCapabilitiesModal`, and `ConversationAgentCapabilitiesConfig` each re-rendered 18× on scroll despite living in the top bar / dialog layer with no scroll-dependent state of their own. `BackendToggle` re-rendered 9×.

### 2026-05-26 — Bulk session delete: 2N whole-state mutations + serial git worktree removes

- **Symptom**: `POST /api/projects/[name]/sessions/bulk` with `op=delete` for 3 sessions took 27.9 s (trace `b326bd6c`). Breakdown: 3× `exec:git.complete` for `worktree remove --force` totalling ~25.3 s (91 %), plus 6× `state.mutate.complete` totalling ~2.5 s (`aggregate.diff` ~380 ms each).
- **Root cause**: two compounding issues.
  1. `deleteSession` ran the orphan-retarget and the row-removal as two separate `mutateState` calls. Each paid the full `readAll` → `structuredClone` → `diffAndCommit` cost (~430 ms with the diff alone ~380 ms), so every per-session delete doubled the whole-state mutate cost.
  2. The bulk route handler in `src/lib/sessions/route-handlers.ts` looped `for await { await deps.deleteSession(...) }`, so the bookkeeping cost was 2×N for N sessions — there was no batch-aware path.
- **Fix**:
  - Fused retarget + remove into a single `mutateState` labeled `deleteSession` (`src/lib/sessions/service.ts`). `retargetOrphanedChildren` stays as a standalone export because the merge actor still uses it independently.
  - Added `bulkDeleteSessions(projectPath, sessionNames)` that runs per-session side effects (worktree removal, transcript purge, notification/job-record cleanup) and then applies a single `mutateState` labeled `bulkDeleteSessions` that retargets all orphaned children and deletes all successfully-prepared sessions in one pass.   - Wrapped `git worktree remove` and its `rm -rf` fallback in `timed(logger, "session.worktree_remove", { ..., cleanup })`. Concurrent invocations against the same parent repository race on `.git/config.lock` (same root cause as claude-code #34645). The real bottleneck is the filesystem `rm` of `node_modules`/`.next` inside each worktree, not git's bookkeeping; if this is a hotspot, the right pattern is parallel `fs.rm(worktreePath, { recursive: true, force: true })` first, then a single serial `git worktree prune` — not parallel `git worktree remove`.
- **Lesson**: Pattern 2. Even when each individual `mutate*` call is justified, callers that loop over them at the route layer multiply the whole-state cost. Bulk routes need a single batched mutation; per-step side effects belong outside of `mutateState`. Pair this with the discipline of giving long-running externals (like `git worktree remove`) a labeled `timed()` span so the report can see them.
