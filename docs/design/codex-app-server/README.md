# Codex in-turn delivery: technical design

Date: 2026-09-16. The conversation adapter now implements this design using exactly pinned `@openai/codex` and `@openai/codex-sdk` **0.153.3**. Revised against [Command Center's operating envelope](../../../ENVELOPE.md). The shared queue contract, app-server transport, privileged instructions, accounting, and cleanup reporting are implemented in this worktree. **In-turn delivery is enabled** by `codex/rollout-policy.ts`: production reports `in_turn` and exposes live queue delivery. Alex explicitly requested enablement without Linux verification on 2026-09-16. See the [implementation report](implementation.md) for verification receipts and verification follow-ups.

## Decision

The implementation replaces the Codex **conversation** adapter's `codex exec` transport with `codex app-server --listen stdio://`. Start one supervised process for each admitted CC turn; keep the existing opaque Codex thread reference between turns. Use `turn/steer` for additional user text/images while that turn is active. Retain the SDK task runner.

The proof of concept established real in-turn delivery, SDK-thread interoperability, persistence across restart, text/image support, and cancellation. It also found behavior that materially changes the implementation: **process-local token totals, non-idempotent client message IDs, ignored instruction overrides on resume, and surviving tool children after abrupt server death**. See [the results and evidence](poc-results.md), [the protocol contract](protocol-contract.md), and [the integration map](integration-map.md).

No shared daemon, WebSocket listener, remote service, or alternate backend is needed. Keep Codex's existing authentication/model selection. The process change has no separate model-pricing multiplier; new input and any newly delivered governing instructions consume ordinary context tokens.

One process per turn preserves the current process count, not a measured RAM profile. Include startup/steady-state memory observations in the supported-host smoke checks; app-server internals and event buffers may differ from `exec`.

Design for Alex's independent macOS and Linux installations, concurrent local agents, finite host RAM/context windows, and CC restarts during active work. Filesystem restrictions coordinate trusted agents; strict parsing handles unreliable provider/MCP data. No cross-machine coordination, public API compatibility layer, Windows support, or distributed recovery service is in scope.

## Scope and preserved behavior

- Enable live delivery for ordinary session and project Codex conversations through the existing capability-driven queue. Existing command, model-change, question-answer, checkpoint, and managed-workflow admission restrictions still decide whether a message is eligible.
- Preserve transcript display/replay, final-answer extraction, structured-output post-validation, images, synthetic forks, checkpoint continuity, model/effort/service-tier selection, filesystem policy, MCP configuration, managed skills, native-memory suppression, and CC environment identity.
- Codex graph implementers dispatch `conversation_turn` through the conversation manager and use this adapter; their managed write envelope requires regression coverage. Graph validators, graph collaborator calls, and ordinary Codex collaboration dispatch `task_run` and retain the SDK, including validators whose continuity strategy is named `conversation`. User-steering permissions do not expand.
- Do not add native forks, native questions, external turns, remote execution, persistent cross-turn processes, or a new UI. Do not expose provider RPC methods above the Codex boundary.
- Preserve persisted thread refs and CC result-frame meanings. Adapter-owned instruction state uses existing lossless transcript storage. Cleanup-hold columns, durable admission checks, and an acknowledgement API/CLI are deferred after the measured parent-death and escalation probes; the selected scope retains explicit manual recovery and restart-limited protection.

## Architecture and ownership

| Owner | Responsibility |
| --- | --- |
| `src/lib/agent-backends/codex/conversation-runtime.ts` | Implements the existing neutral runtime; owns one admitted turn, active identity, start/steer acceptance, event ordering, cancellation, instruction delivery, and normalized result. |
| `codex/app-server-client.ts` and `app-server-client-process.ts` | Own executable resolution, process lifecycle, bounded UTF-8/LF framing and diagnostic retention, request correlation, raw notifications, server requests, timeouts, and bounded shutdown; the runtime owns the initialize handshake. Private to Codex. |
| `codex/app-server-events.ts` | Interprets native events into existing neutral content/results. No state-store access. |
| `codex/instruction-state.ts` | Reads/writes the latest governing-instruction hash and unresolved marker through the existing transcript interface; owns cache invalidation and bounded reapplication before model start. |
| `codex/app-server-protocol.ts`, `app-server-protocol-generated.ts`, and `transcript-records.ts` | Validate native envelopes using the pinned protocol subset and stream stored transcript records with a finite per-record bound. |
| `src/lib/prompt/queue.ts` and message-queue service | Remain the sole owners of durable user claims, user transcript entries, delivery watermarks, and delivered/pending/uncertain states. Own the acceptance-settlement callback below. |
| Conversation lifecycle and existing notification owner | Retain failed live ownership and surface typed cleanup evidence through logs and the existing error-notification path. Durable cleanup review remains a separately evaluated lifecycle change; the measured escalation survivor is an explicit manual-recovery condition. |
| Existing Codex policy/config modules | Continue composing environment, sandbox, MCP suppression, capabilities, managed skills, and memory policy. The task runner uses the same policy without a transport rewrite. |

Do not add another backend-neutral transport abstraction. A typed private RPC client plus the existing semantic runtime is enough. Reuse process identity/signal primitives where appropriate, but do not import the Cursor SDK supervisor as the Codex lifecycle.

Resolve the native executable from the installed platform package using the same platform/architecture mapping as the pinned SDK. Do not select an unrelated `codex` on PATH. Pin the SDK and an explicitly owned `@openai/codex` runtime to **0.153.3** and update them together, including the existing SDK patch; maintain version agreement in a contract check. Generate relevant TypeScript protocol types from that executable and validate required external envelopes/fields at runtime. Do not commit the entire schema bundle.

### Transport memory bounds

Enforce a **16 MiB maximum incoming JSONL record**, including an incomplete record with no LF, before concatenating/decoding/parsing it into an unbounded string. Count UTF-8 bytes across chunks, split only on LF, and preserve multibyte characters. A chunk containing several small records is processed record by record; the limit applies to each record, not to the aggregate read. Oversized or malformed required frames fail the turn and begin bounded teardown; written requests without conclusive acceptance/refusal remain uncertain.

Keep at most **16 MiB of queued wire payload** awaiting raw archival or ordered event delivery, including acceptance-barrier events. Track bytes rather than event count; do not retain an unbounded promise chain or a full in-memory copy of the turn's raw history. Responses and server requests continue to be dispatched independently. If an archive/content consumer cannot keep up within this budget, fail rather than pausing the reader indefinitely. These are payload budgets, not claims about total JavaScript heap consumption.

Drain stderr continuously and retain only a **256 KiB tail** per process for failure diagnosis. Operational logs carry bounded metadata, never prompt text or tokens. Archive complete valid protocol frames through existing transcript storage as they arrive. For a rejected oversized/truncated frame, retain bounded failure evidence and byte counts, explicitly marking truncation; do not claim lossless retention of rejected data. The production client does not copy the POC's unbounded `frames`, stderr string, or pending log-write chain. Stored transcript scans for instruction state and cumulative cost use `transcript-records.ts`: LF-only UTF-8 streaming with a **64 MiB per-record cap**, allowing for escaping inside archived wire envelopes without loading whole history. Malformed, truncated, oversized, or unreadable history stops instruction dispatch or makes the cost baseline unknown.

## Lifecycle

1. Honor retained live cleanup failure before replacing/reusing that runtime. Compose the existing environment/config and reconcile managed skills. Spawn with the exact worktree or restricted-lane cwd. Start stderr draining immediately. There is no new durable cleanup-hold read in the initial scope.
2. Send `initialize`, wait for its response, then `initialized`. Use `experimentalApi:false`; steering needs no experimental opt-in. Leave required turn/item notifications enabled.
3. `thread/start` for a fresh reference, otherwise `thread/resume` with `excludeTurns:true` to avoid hydrating the full historical transcript into the response. Pass the composed model, sandbox, approval policy, configuration, and cwd explicitly. Check the returned effective settings. Never project historical items into live display.
4. Establish governing instructions as described below. Publish `backend_init` with the authoritative thread ref, without claiming prompt acceptance.
5. Register the pending start before writing `turn/start`. Admit exactly one start per process. On its correlated success, publish `input_accepted` once and establish the active turn ID. A matching authoritative `turn/started` may establish acceptance if it wins the notification/response race; normalize both observations to one acceptance.
6. Drain native events in order. A steering acknowledgement belongs to its queued user message; it never emits another `input_accepted`, CC turn, or `backend_init`.
7. On `turn/completed`, close new steering admission immediately. Settle requests already sent, finish the accepted-input barriers, flush native events, and prepare a provisional result. A final message alone is not completion.
8. Close stdin and await bounded process teardown, then publish/settle the single result: verified teardown preserves the provisional outcome; unverified cleanup adds typed failure and prevents successful release. After successful teardown the CC runtime stays reusable; the next `sendTurn` creates a fresh process and resumes the thread. `close()` permanently invalidates that runtime and awaits bounded teardown.

Protocol response handling must remain independent of the ordered content drain. Otherwise waiting for acceptance/persistence can prevent the RPC response that releases the wait from being processed.

A spawn, initialization, thread-resume, or configuration failure is pre-input failure. A lost `turn/start` response after bytes were written is **not** evidence of non-acceptance. Keep the thread ref, report the failed/uncertain dispatch through existing recovery semantics, and do not silently start the prompt again. Test checkpoint acceptance receipts with both event orders.

## Live delivery and durable ordering

At `queueUserInput` entry, capture the active thread/turn identity before any await. Refuse locally if absent, terminal, or closing. Serialize each admitted steering attempt through acceptance and durable settlement; keep the protocol reader running. Send text and local-image paths with `expectedTurnId` and a runtime-generated, correlation-only `clientUserMessageId`. This ID is not the durable queue attempt ID; that remains private to the callback. Never retarget the attempt to a later turn.

| Evidence | Decision |
| --- | --- |
| Nothing could have been written; no active turn | Definite rejection; retain pending for next turn. |
| Correlated known rejection: wrong/ended turn, invalid input, unsupported active turn | Definite rejection; retain pending. Preserve structured reason. |
| Correlated successful steer response for the captured turn | Accepted; settle that claim exactly once. |
| Write may have occurred, but response is lost/timed out or process exits | `InputDeliveryUncertainError`; hold for review, never automatically resend. |
| Success known; user transcript/images archived; queue settlement fails | Let the current turn finish. Retain the claim for review, report settlement failure, and prohibit automatic redelivery. Never downgrade to pending. |
| Success known; transcript/image archival fails or cannot be confirmed | Preserve acceptance and the claim, then fail/close the turn through bounded teardown. Suppress later normalized output whose preceding user archive is missing; never classify the input as rejected. |

The pinned runtime returned `-32600` for both a wrong turn ID and an ended turn, with different messages. Numeric code alone is insufficient classification. Keep exact pinned mappings behind the adapter; unfamiliar internal errors after a write are uncertain unless they prove rejection. Do not retry any steer on a timer. The POC demonstrated that repeating the same client ID creates two user messages.

### Acceptance-settlement callback

Extend `ConversationQueuedUserInput` with a neutral optional `onAccepted(): Promise<void>` callback; the durable queue always supplies it. The queue creates it; the runtime calls it exactly once after provider acceptance and before releasing content that may follow the input. It performs the current accepted path: delivery watermarks, image/content archival, the single user transcript append, and matching-claim settlement. Use existing `appendTranscriptEntryOnce` with the CC queue-row ID to make archive recovery idempotent. Keep best-effort watermark failures best-effort.

Distinguish **archive failure** from **queue-settlement failure after a confirmed archive**. The callback rejects if image/user-entry archival fails or is unconfirmed. Once both are durably archived, it catches a later queue-settlement failure, records that failure in queue-owned attempt state, logs it at error level, and tries to mark the original claim uncertain. It then resolves so the runtime can release output and finish the current turn. The queue caller surfaces the review outcome rather than claiming successful settlement. If marking uncertain also fails, leave the original delivering claim for abandoned-claim recovery; never automatically resend or recreate a row already confirmed pruned. Serialize later live attempts and block subsequent queue claims while an unresolved claim needs review. This changes no provider acceptance fact and introduces no retry loop.

Codex installs a content/terminal barrier when dispatching a steer. Already-drained earlier events remain visible; subsequent events are buffered until its callback settles. Definite rejection releases the barrier without a user entry. Unknown acceptance releases buffered events with the row held uncertain; it must not deadlock turn completion. A resolved callback releases the barrier, including the confirmed-archive/failed-queue-settlement case. An archive failure rejects the callback, preserves acceptance as uncertain, suppresses later normalized output whose user archive failed, and fails/closes the turn while retaining bounded raw evidence. It is never an ordinary retryable rejection. Barrier events count toward the shared **hard** 16 MiB queued-payload budget above; this is not a second allowance. A per-record cap cannot bound an accumulating queue, so an optional warning before the threshold does not replace bounded failure at the limit. Never pause the response reader to impose backpressure on an acknowledgement it still needs.

Move the post-acceptance work rather than copy it. Claude and Cursor adapters invoke the same callback after their respective acceptance signals, preserving the neutral seam. Add a delayed-persistence test that proves a fast model response cannot appear before the acknowledged user message. The raw provider `userMessage` echo is evidence only; the queue remains the only visible user-entry writer.

The callback and dispatch ordering were implemented and tested as the **shared prerequisite**, with Claude/Cursor coverage and Codex still declaring next-turn delivery. Keep this prerequisite as a separate review/change boundary when landing the work; the app-server adapter adopts its neutral contract. Both changes currently coexist in this worktree, which is not evidence that either has been merged.

The queue owner must also serialize eligible live dispatch by durable claim order before asynchronous reference/image preparation. A later request cannot overtake a slow earlier one. This serialization is per conversation and separate from the one admitted agent turn; it must not lock the provider event reader. Retain existing abandoned-claim recovery and stop/drain exclusions.

## Governing instructions on new and resumed threads

Available privileged delivery is required by existing governed contracts; preserving a fenced user-only block would not satisfy that requirement after this transport change. Change the Codex conversation execution declaration to `instructionDelivery:"privileged"`. Preserve neutral instruction composition order and the separation between stable governing instructions and changing memory/notepad/ticket context.

- **Fresh thread:** send composed stable instructions through `thread/start.developerInstructions`. Do not replace Codex's base system instructions. Remove the fenced duplicate from the first user prompt. The live probe proved developer authority over a conflicting user prompt.
- **Resumed thread:** do not rely on `thread/resume.developerInstructions` to update model-visible history. It was ignored in two independent probes. For an exec-created thread migrating to app-server, or a changed governing-instruction hash, append one developer message through stable `thread/inject_items` before `turn/start`. The probe proved both authority and persistence across another process restart.
- **Unchanged instructions:** read the **latest instruction state for this thread** from CC's transcript and skip reinjection only if its hash matches and it is resolved. An older matching hash does not establish the current state: A→B→A requires another A injection, and unresolved B prevents reuse of an older resolved A. A fresh checkpoint/fork thread has a fresh instruction baseline. The adapter owns these records; shared callers never interpret their raw payload.

Persist only a versioned SHA-256 hash of the exact stable block/composition policy, the opaque thread ref, and an `unresolved` marker through the existing transcript interface. There is no separate instruction-operation/attempt journal. Before injection, durably write the current target hash with `unresolved:true`; after correlated RPC success, persist `unresolved:false`. Missing state on a resumed thread requires injection. Failure to read or persist required state stops dispatch with a clear error; it is not permission to use an older success. A fresh thread whose developer instructions were accepted needs resolved state before its initial user turn starts.

An unresolved marker stops the current dispatch, but does **not** force a new checkpoint. After the prior process is closed and there is no unresolved live cleanup failure, the next admitted attempt reapplies the **current** full governing block once, awaits acknowledgement, and resolves its state before `turn/start`. If that attempt is ambiguous again, leave the marker unresolved and fail that attempt; no timer/backoff loop or automatic sequence of model turns. Explicitly supersede earlier CC governing blocks without replacing Codex's base instructions. An occasional duplicate static block costs context tokens; it does not authorize replay of a user command. The no-automatic-resend policy for uncertain `turn/start`/`turn/steer` remains unchanged. Do not claim native injection is idempotent or parse provider-owned history files to infer acceptance.

Resolved matching state avoids large duplicate blocks during ordinary operation. Dynamic memory/notepad context and its watermarks remain in user-turn delivery. The `instruction-recovery-01` extension passed lost-ack reapplication, duplicate identical blocks, A→B→A, and restart persistence on macOS x86_64. This establishes the measured recovery behavior on the pinned runtime/model; CC instruction-state persistence races are covered separately by adapter and real transcript tests.

### Compaction and instruction state

An acknowledgement proves delivery, not continued presence after context compaction. On an authoritative compaction/context-loss signal, invalidate the instruction state (`unresolved:true`) and use the existing memory-index reset path. Before the next CC model turn, reapply the current block and require acknowledgement, even if its hash is unchanged. A compaction invalidation observed during instruction settlement must win over an older injection acknowledgement; serialize these state updates and do not clear a newer invalidation.

Treat the required context-pressure probe as a **migration regression check against exec**, not a requirement to fix every existing Codex compaction weakness. Run comparable workloads on the same pinned runtime/model: the current exec path with its first-user-message governing block, app-server with fresh developer instructions, and app-server with injected instructions on a resumed/legacy thread. Compare governing-instruction behavior during the remainder of the compacting turn and after process resume; record existing weaknesses separately. Block demonstrated regressions in the changed instruction path and establish a supported refresh boundary if that is needed to remove them. An inconclusive comparison remains open evidence, not a pass.

The current exec adapter reports `compacted:false`; that proves missing reporting, not preserved instructions. Do not assume fresh developer instructions survive because they may form a persistent prefix. Where app-server supplies authoritative context-loss events, retain instruction-state invalidation and the memory-index reset above. Reporting usage as unknown is an accounting policy, not evidence of instruction retention. The migration need not solve a demonstrated pre-existing compaction weakness merely to equal the baseline, but must disclose it rather than claim preservation.

## Event and accounting contract

Keep complete valid native frames losslessly in the adapter transcript envelope within the transport/archival bounds above, with operational logs excluding prompt text/tokens and rejected/truncated data explicitly identified. Normalize completed agent text, reasoning/commentary, command start/results, file changes, MCP tools, plans, and errors into existing content types. Use native IDs to join deltas to completed items; do not append both as duplicate text. Display completed items initially, preserving current behavior; token-by-token UI is independent scope.

Use `agentMessage.phase` when present. It was present as `commentary` and `final_answer` in the probes. Retain the existing pending-message fallback when absent; the schema permits absent phases. Structured-output validation consumes final-answer text only. Continue prompt-based output contracts and omit native `outputSchema`.

`error.willRetry:true` and stderr warnings are diagnostic, not terminal failure. Completion status `completed`, `failed`, or `interrupted` owns settlement. Map provider compaction evidence to existing context-loss behavior when observed; do not infer compaction from token changes or enable unrelated capabilities.

### Usage: account per process, accumulate in CC

The probe disproved a transport-independent lifetime-total assumption:

- Within one process, `tokenUsage.total` accumulates model calls. One steered turn reported totals **12,283 → 24,660**, while `last` was **12,377** at its end. Billing `last` would omit the first model call.
- A new process resuming that same thread reported **12,411**, equal to its new call, not **37,071**. An SDK-created thread showed the same reset on app-server resume.

With exactly one admitted CC turn per process, use the last observed `total` as that turn's usage (never sum intermediate totals, never subtract the previous process's counter). If a baseline usage event appears before start, subtract that baseline within the same process and test it explicitly. Require nonnegative, consistent, monotonic cumulative categories within the process. A decrease/reset or invalid counter makes affected turn/cumulative accounting unknown with a diagnostic and retained raw evidence; do not silently bill only the smaller final total. This policy covers unproven compaction/reset behavior without guessing its meaning. Map token categories into the existing pricing helper.

Set `costUsd` to this turn's estimate. Compute `cumulativeCostUsd = persisted CC lineage baseline + this turn's estimate`. Continue the existing result-frame shape: `raw.costUsd` stays CC lineage-cumulative and `raw.turnCostUsd` stays per-turn. A native compaction does not reset CC's cumulative ledger. Preserve the latest available usage on interrupted/failed turns; missing counters remain unknown, not zero. An unreadable historical baseline means cumulative cost is unknown and diagnosed rather than a fabricated fresh lineage. `numTurns` stays one despite multiple model calls/steers.

Preserve explicit unknown through persistence/replay: the Codex result projector must not substitute turn cost for a null cumulative cost, and the baseline reader must use the **latest lineage result state**, including unknown, rather than skip null frames to revive an older number. Keep an unknown-cost result in the neutral usage projection. A later measured turn does not repair missing earlier cost; the cumulative total remains unknown. Distinguish a proven fresh zero baseline from absent/unreadable/unknown resumed history. Cover known→unknown→restart→known-turn in the projection and baseline tests.

Do not label cumulative billing counters as context occupancy. Keep `contextWindowMetrics:false` in this change. `modelContextWindow` alone does not establish occupancy. This work changes conversation accounting only; any similar SDK assumption is a separate investigation.

## Configuration and server requests

Keep all CC-owned policy explicit. Process environment carries CC identity, capability tokens, server coordinates, workflow scope, PATH, and restricted TMPDIR; thread requests have no environment map. Apply the existing filesystem envelope at thread and turn boundaries without weakening its effective cwd/write roots. The POC wrote inside the workspace, received `EPERM` outside it, and read the expected process environment.

Retain native MCP suppression and portable MCP translation; inspect startup failures and don't claim tools are configured merely because a request parsed. Preserve skill/plugin selection and native-memory switches. A fresh process avoids introducing cross-turn refresh semantics. Tool approval requirements remain provider policy: an unannotated fixture tool was rejected under `approvalPolicy:"never"`; a read-only fixture ran, and its elicitation was automatically declined under that policy.

Every server request gets an explicit response. Keep `nativeMidTurnAskUser:false` and CC's current question path. Deny unexpected command/file/permission approval requests; decline MCP elicitation; return a structured unsupported result for unregistered dynamic tools. For native questions or externally managed auth/attestation requests that CC cannot fulfill, return a protocol error, interrupt, and surface a clear unsupported-operation failure. Never fabricate a user answer, approve unexpected permissions, or silently wait. Pin the exact response shapes in [the protocol appendix](protocol-contract.md).

## Cancellation and process cleanup

Prefer native cancellation while the connection exists: close steering admission, send `turn/interrupt`, await `turn/completed:interrupted`, settle written steers, then EOF and await exit. The probe settled interrupt in **16 ms** and resumed the thread successfully. Active-turn EOF also exited cleanly and reaped the observed tool child; use explicit interrupt as the primary cancellation contract because it supplies a terminal result.

Bound shutdown: 5 seconds for interruption/terminal drain, 5 seconds for EOF/exit, then identity-checked TERM and KILL escalation with 2-second confirmation windows. Ordinary RPC acknowledgement timeout is 30 seconds; model execution uses CC's existing stall policy, not that RPC timer. Reject outstanding promises on process exit. Clear all timers/listeners on settlement.

Supervise an owned process group with open pipes and an awaited lifecycle; do not detach a background job. Native shell tools can form separate groups. **SIGKILL of app-server left a tool child alive in the probe.** `commandExecution.processId` was an opaque tool-session ID, not its OS PID. Never pass it to `process.kill`.

Do not claim universal reaping after an abrupt crash. Use existing identity-checked OS process supervision for owned groups. When native cancellation became impossible and ordinary tool children may remain, report typed neutral `cleanup_unverified` evidence, permanently reject new starts/steers on that runtime, and reject `close()` with a bounded cleanup error. The live runtime binding retains its owner when close rejects. A per-turn process failure must also reach the lifecycle owner even if nobody has called `close()` on the reusable runtime object: carry cleanup evidence on the neutral turn result, and treat that turn as failed rather than publishing successful completion/release.

### Cleanup review and deferred durability

The initial scope keeps typed cleanup failure, retained live ownership, blocked runtime reuse, and a clear error through the existing notification owner, including best-effort phone notification when configured. The notification names the affected conversation/worktree and the need to inspect/stop surviving commands; it contains no prompt or tool-output dump. Notification failure never converts cleanup failure to success. This is notification of a failure, not verification that a child is gone.

This protection is **in-memory** and ends at CC restart. A rebuild is an ordinary lifecycle event, not necessarily a second failure. Restarting can therefore admit work that overlaps a surviving command; the error and recovery guidance must say so. Alex must inspect/clean up before resuming, and uncertain user inputs retain their separate review state. The recorded SIGKILL survivor makes this a real limitation, even though ordinary interruption and explicit EOF passed.

The macOS CC-parent-death and full interrupt→EOF→TERM/KILL probes have run. Ordinary parent SIGKILL and graceful termination reaped both observed processes; frozen/ignored-signal app-server escalation left an independently identified tool alive after the server exited. The selected decision retains explicit manual recovery with restart-limited protection. The proposed `runtimeCleanupHold` field, columns in both conversation tables, durable admission/rehydration checks, and acknowledgement API/CLI remain **deferred**, not selected implementation work. Linux lifecycle evidence remains unverified; Alex waived it as an enablement prerequisite. If necessary, implement durable cleanup review as a separately estimated backend-neutral lifecycle change and have affected backends report through that contract. Do not disguise cleanup failure as an uncertain user message, checkpoint operation, or workflow ownership claim.

Do not claim parity with Cursor's retained ownership merely because it records `cleanupFailure`: its current cleanup-failure branch can let `close()` resolve, while the shared binding retains an owner when close rejects. CC does install `installRuntimeShutdownHook(stopAllConversationActors)` in `instrumentation.node.ts`; the hook is best effort and cannot replace parent-death evidence. Universal detached-child containment, global workspace quarantine, and automatic process hunting remain outside scope.

## SDK and runtime upgrade procedure

This section owns the upgrade checklist for both retained transports. Keeping the SDK task runner adds maintenance; there is no scheduled exec retirement in this design.

1. Update the exact SDK and `@openai/codex` runtime versions together, verify platform executable resolution, and regenerate the existing SDK LF/readline patch for the new SDK. Run its Unicode-separator regression test.
2. Regenerate the relevant app-server type/schema subset, review protocol changes, and replay the framing, request/event, instruction, accounting, and cleanup contract fixtures. Do not add multiversion wire shims.
3. Run registered SDK task-runner/conformance and app-server conversation tests, including the shared policy/config regression cases and the separately reviewed queue contract.
4. Rerun the live app-server POC and a real SDK task/exec smoke case, including SDK-created-thread interoperability. Exercise the focused supported-host checks on Mac and Linux; repeat comparative compaction and lifecycle probes when accepting a changed runtime. Record runtime/model/architecture, outcomes, and relevant memory observations.
5. Accept the version only with the required evidence and an updated compatibility record. An SDK task-runner migration may be evaluated separately if removing dual-transport maintenance is worth its cost; do not expand this conversation-steering change to retire exec.
