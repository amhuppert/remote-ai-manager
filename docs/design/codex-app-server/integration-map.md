# Command Center integration map

This appendix describes the repository work for moving **Codex conversation turns** to a per-turn stdio app-server process. The SDK task runner remains in place. [The main design](README.md) owns the selected architecture and policies; [the proof-of-concept report](poc-results.md) owns measured protocol behavior. This appendix maps those decisions to existing repository owners and preservation obligations. The migration is implemented in this worktree, including the shared queue prerequisite. The conversation adapter now uses app-server and privileged instructions; `codex/rollout-policy.ts` enables in-turn delivery and the runtime exposes its live queue method in production. Alex explicitly requested enablement without Linux verification on 2026-09-16. Linux and live restart-recovery observations remain unverified follow-ups.

## Scope and module ownership

CC already has a backend-neutral live-delivery seam. The migration implements that seam inside the Codex adapter and preserve the queue, transcript, lifecycle, and checkpoint owners. It does not require a shared daemon, a WebSocket listener, provider-specific branches in the composer, or adopting every app-server feature.

| Owner | Implemented responsibility or preservation obligation |

## Delivery and turn-completion races

The existing queue is already stronger than a simple retry buffer:

1. `prompt/queue.ts` persists the user content before attempting delivery. Enqueue does not append a transcript message.
2. `conversations/message-queue-service.ts` atomically claims a pending row with a generated `deliveryAttemptId`, timestamp, and incremented attempt count. Cancellation or another claimant can win; the loser must not send.
3. `prompt/queue.ts` calls the runtime. Resolution means backend acceptance. `InputDeliveryUncertainError` means the message might have reached the provider; an ordinary rejection means it did not.
4. The accepted path saves the transcript image/content, appends exactly one user entry, and only then marks the matching claim delivered (`queue.ts`). The queue owns this user entry; a provider `userMessage` echo must not create another visible user entry.
5. `queue-operations.ts` nudges the conversation manager after the live attempt settles. `workflows/conversation/manager.ts` waits for the admitted turn's completion before draining. `claimNextTurnBatchTransform` refuses to claim while any row is delivering or needs review (`message-queue-service.ts`).

The app-server adapter must use these outcomes:

| Situation | Runtime outcome | Durable queue behavior |
| --- | --- | --- |
| No active provider turn, or turn ended before the request was written | Definite rejection | Return the claim to pending; the post-enqueue nudge delivers it next turn. |
| Provider rejects the expected active-turn identity | Definite rejection after checking the correlated response | Return to pending; do not retarget the same message to a newly active turn inside the adapter. |
| Correlated successful steer response | Accepted | Append the user transcript once and settle the original claim, even if turn completion is subsequently observed. |
| Stdio disconnect, timeout, process death, or abort after bytes may have been sent and before acceptance/refusal is known | `InputDeliveryUncertainError` | Retain as uncertain for explicit review; never automatically replay. |
| Known acceptance, confirmed transcript/image archive, then queue-settlement failure | Accepted, with queue review required; current turn continues | Retain/mark the original claim uncertain, report failure, and block automatic redelivery. Do not recreate an already-pruned row. |
| Known acceptance followed by failed or unconfirmed transcript/image archival | Accepted, with archive failure; bounded stop | Preserve the claim, suppress later normalized output whose preceding user archive is missing, and close/fail the turn. Never return the input to pending. |
| CC restarts with a delivering row | Existing abandoned-claim recovery | `recoverAbandonedDeliveriesTransform` holds it uncertain (`message-queue-service.ts`). Missing ownership is not evidence of non-delivery. |

`confirmDelivery` is a separate existing recovery operation reserved for durable attempt-correlated acceptance evidence, currently checkpoint receipts (`message-queue-service.ts`). A request ID in transient memory or an uncorrelated provider user-message event is not sufficient to use it.

The runtime should synchronously snapshot the active turn identity and register a pending steer before its first await. Serialize writes/steer admission within that active turn, correlate the response to the captured identity, and forbid new steers after the terminal event. Do not infer order from arrival times of independent promises. On turn completion, preserve enough of the process lifetime to settle already-written steer requests and flush ordered events; a bounded unresolved request becomes uncertain. Teardown must not convert an acknowledged steer into a retryable failure.

A runtime absent during preparation or finalization can reject a live attempt safely before writing. The durable row then waits for the already-admitted turn to finish. This does not require exposing preparation phases through the queue API.

Existing exceptions remain next-turn work regardless of the new capability: a caller-imposed checkpoint policy, an explicit model selection, CC question answers, and conversation commands (`queue.ts`). Managed workflow conversations remain outside user queue admission (`queue-operations.ts`); transport support does not grant permission to steer them.

### Implemented neutral acceptance-settlement callback

The previous `queueUserInput(): Promise<void>` boundary reported provider acceptance before `queue.ts` completed asynchronous persistence. The new acceptance callback closes that ordering gap for an independent app-server notification pump. Merely awaiting an RPC response would not prove archive-before-output ordering.

The shared prerequisite adds `onAccepted?(): Promise<void>` to `ConversationQueuedUserInput` (`agent-backends/conversation.ts`). The provider has accepted this input; before releasing later visible content, the callback must confirm durable image/user-entry archival and handle the queue-settlement outcome. A resolved callback permits output, but does not imply the queue row was successfully marked delivered: the queue owner may have recorded a post-archive settlement failure for review. `queueUserInput` resolves after provider acceptance and callback resolution. The optional form keeps callers without queue receipts small; every implementation invokes it when supplied, exactly once, after its own provider acceptance signal. The durable queue always supplies it.

The queue owns the callback and its once-only promise. Its first synchronous action sets an `accepted` flag; then it settles acceptance-owned notepad watermarks, saves images, appends the user transcript with a stable CC-owned message ID, and attempts to mark the original delivery delivered. Preserve best-effort watermark handling. Set a queue-owned archive-complete flag only after image/user-entry writes succeed. Archive failure rejects the callback; after confirmed archive, catch queue-settlement failure inside the callback, remember the failure for the queue caller, log at error level, and attempt to mark the claim uncertain before resolving. No new provider field or callback return type is needed. Use `appendTranscriptEntryOnce` (`prompt/transcript.ts`) for archive idempotency with the queue-row ID; explicit retries already get fresh row IDs (`message-queue-service.ts`). Provider `clientId` is not a deduplication key.

For Codex, installing a steer reserves an event-emission barrier before request dispatch. The reader continues resolving RPC responses and servicing server requests while ordered content/terminal delivery waits. The correlated success triggers `onAccepted`; its resolution releases buffered notifications in wire order, including when archival succeeded but queue settlement failed. A definite refusal releases the barrier without invoking the callback. Unknown acceptance releases buffered events after the row is held uncertain; it never triggers resend or a fabricated user entry. Separate the reader from ordered delivery to avoid an acknowledgement deadlock. Barrier events share the design's **hard** 16 MiB queued archival/content payload budget. Exceeding it fails the turn with honest delivery state and bounded teardown; a warning or per-record limit alone cannot bound aggregate memory.

The queue catch path checks `accepted` as well as `InputDeliveryUncertainError`; either prevents `markPending`. Separately inspect the queue-owned post-archive settlement failure even when `queueUserInput` resolves, so the caller receives a review outcome rather than false settlement success. If marking uncertain fails, retain the original delivering claim for abandoned-claim recovery and surface the error. A visible user entry plus a review row must not cause redelivery. If both writes committed but the acknowledgement was lost, never recreate the pruned row. Serialize later live attempts and use existing review/delivering claim blockers to prevent subsequent queue work from skipping the unresolved claim.

Only failed/unconfirmed image/user-entry archival rejects the callback and requires suppressing later visible output plus bounded fail/close. Queue settlement failure after confirmed archival is handled inside the callback and lets the current turn finish; logs/review state make the failure visible. Do not retry either case by dispatching another steer. `sendTurn` completion and `close` await the callback promise; a turn-ended notification cannot release ownership while the user archive is still being written.

The callback/failure semantics and dispatch ordering were implemented and tested as a prerequisite; preserve their separate review/landing boundary. Claude and Cursor adopt them at their existing acceptance seams (`claude/conversation-runtime.ts`, `cursor/conversation-runtime.ts`) with delayed-archive, post-archive settlement failure, archive failure, and no-redelivery coverage; Codex stays next-turn-only. Declared live-delivery backends and conformance fakes adopt the same contract before the Codex transport enables live delivery. This separates regression diagnosis without removing the prerequisite.

Cancellation and disposal preserve the existing durable states:

- Before the atomic live claim, cancelling a pending row prevents sending. After claim, `cancelTransform` refuses cancellation (`message-queue-service.ts`), including while the callback runs. Aborting the agent turn cannot retract accepted user input.
- Close refuses new steering immediately. Unwritten requests can be definite refusals; written unresolved requests become uncertain; acknowledged requests finish or record callback failure. Do not clear an accepted callback from a pending-request map as though it were unsent.
- `markPending` clears the claim fields only for a matching definite refusal; uncertain retains the attempt; delivered/cancelled terminal rows are pruned. Existing fields suffice—no provider request or turn ID belongs in the persisted queue schema.
- `runtime-binding.ts` awaits backend close before unregistering it. Codex `close` therefore owns callback and event-chain settlement as well as child cleanup. On teardown failure, preserve the rejected close outcome rather than detach work that can still append after the runtime was declared released.
- The HTTP request's end or disconnect is not withdrawal of the durable message. The current queue call supplies no request abort signal; preserve that behavior. A bounded provider deadline still distinguishes definitely unsent from possibly delivered.

The queue owner also serializes eligible live delivery by durable claim order before asynchronous reference/image preparation, as selected in [the main design](README.md#live-delivery-and-durable-ordering). The runtime can order calls it receives, but only the queue owner can prevent a slow earlier request from being overtaken before it reaches `queueUserInput`. Include a delayed-first-request test; no provider sequence field belongs in the neutral queue.

## Initial acceptance, checkpoints, and continuation

`workflows/conversation/actor-implementations.ts` advances prepared context on neutral `input_accepted`; `backend_init` separately updates the opaque reference and checkpoint receipt. `pre-turn/checkpoint-seed.ts` requires both facts for the same dispatch attempt. It accepts either event order, and neither spawn, initialize, nor thread creation alone proves the user's prompt was accepted.

For the app-server path:

- Emit `backend_init` from an authoritative thread start/resume response and retain the opaque ref, including on a resumed turn where needed by the current lifecycle.
- Emit `input_accepted` exactly once for the initial turn from its correlated `turn/start` success response or matching authoritative `turn/started` notification, whichever establishes acceptance first. Coalesce the other observation. Do not use the first arbitrary app-server notification.
- A steering acknowledgement resolves that queued input only. It must not re-emit the initial turn's context-acceptance event or create an external/virtual CC turn.
- A failed attempt may be replaced automatically only when the adapter can attest that the initial input was never delivered. Loss of a response is not that attestation.
- Preserve synthetic fork seed delivery, checkpoint fresh-context creation, acceptance-before-archive recovery, memory/notepad delivery watermarks, and continuation disposition. Native `thread/fork` or native compaction is additional scope.

An app-server process that exits between turns is intentional in this design. The CC runtime remains reusable and resumes the same thread in the next process. `close()` still makes the CC runtime permanently dead and waits for the verified cleanup outcome or records a bounded cleanup failure according to the existing runtime contract (`agent-backends/conversation.ts`). It must not equate server-process exit with proof that every tool subprocess exited.

## Teardown and process ownership

[The POC results](poc-results.md#scenario-results) narrow the implementation claim: killing app-server while a long-running command was active left an OS child alive, and the protocol `commandExecution.processId` was an opaque unified-exec handle, not that child's PID. Never pass this protocol field to `process.kill`, interpret it as a process-group ID, or advertise complete tree cleanup merely because the app-server parent exited.

There are useful existing mechanisms, but neither solves escaped descendants automatically:

| Existing code | Reusable principle and limit |
| --- | --- |
| `agent-backends/cursor/worker/supervisor.ts` | Bounded native cancellation, orderly shutdown, then ownership-guarded process-group TERM/KILL and verification. `close` is memoized and the worker remains registered until teardown settles. |
| `shared/process-identity.ts` and Cursor's `process-host.ts` | Pair the spawned OS PID with an OS start marker and known PGID before signalling. The source explicitly notes that SDK shell children may lead separate groups and require native cancellation. The Codex and Cursor hosts now share the extracted OS identity primitives; do not import Cursor's worker protocol or whole supervisor. |
| `agent-backends/cursor/worker/entry.ts` | Run provider-native cancellation/disposal while the live SDK connection still exists, before process-group escalation. Group signalling is a fallback for members of that group. |
| `shared/exec.ts` | Its command collector uses a private group and timeout escalation, but ignores stdin, collects rather than streams stdout, and verifies no escaped process identities. It is unsuitable as the app-server transport or as proof of whole-tree cleanup. |

The smallest honest Codex shutdown sequence is:

1. Mark the runtime closing; reject new starts/steers. Keep the RPC reader running and preserve each pending input's delivery state.
2. When a provider turn is active and the connection works, send native `turn/interrupt` and await the correlated terminal outcome within the cancellation bound. Await known acceptance callbacks and ordered event flushes; an interrupt response alone is not evidence every command process has exited.
3. Once the turn is inactive, close stdin and await ordinary app-server exit. The active-EOF probe also reaped its observed tool child, but explicit interruption remains primary because it provides a terminal lifecycle result.
4. If the spawned process/group remains, signal only the owned OS group using a guarded TERM/grace/KILL/verification ladder. Keep the child referenced and tracked by the runtime; a private group is isolation for signalling, not an untracked detached background task.
5. Record which facts were established: protocol turn terminated, app-server exited, known group gone, and any unresolved tool lifetime. A native failure or hard crash that removed the only tool supervisor before cancellation, with potentially escaped children, is `cleanup_unverified` even when the parent group is gone. Retain diagnostic identities without guessing which other host processes are ours.

The selected policy in [the main design](README.md#cancellation-and-process-cleanup) reports typed `cleanup_unverified` evidence, permanently rejects new starts/steers on that runtime, and rejects `close()`. Retain the live owner through `runtime-binding.ts` and surface the failure through logs and the existing error-notification owner, including best-effort phone delivery when configured. This protection is in memory and ends at CC restart; notification is not a durable admission guard or proof of reaping. Columns and acknowledgement APIs remain deferred under the measured parent-death/escalation decision below. The bounds remain 5 seconds for interruption/terminal drain, 5 seconds for EOF/exit, and 2-second TERM/KILL confirmation windows.

CC installs a best-effort signal shutdown hook in `instrumentation.node.ts`; `agent-backends/runtime-shutdown.ts` explains why it cannot guarantee completion before parent exit. Cursor's `conversation-runtime.ts` records cleanup failure while allowing close to resolve, so it does not establish parity with the proposed retained-owner policy. These facts reinforce the need to observe the actual parent-death and escalation paths rather than infer them.

Universal hard-crash reaping would be additional work: an OS-owned containment boundary, or descendant identities captured from the OS while ancestry is still observable, with PID/start-marker validation before signalling. Periodic PPID scans alone have a gap when a process forks, changes group, and reparents between scans. A post-crash command-line search or guessed PID is not an acceptable substitute. On the current scope, retain this explicit hard-crash limitation rather than invent an app-server guarantee. The standalone probes demonstrate ordinary interrupt, orderly EOF shutdown, successful CC-like parent termination, and separate-group tool survivors under frozen-server TERM/KILL escalation; production acceptance must re-prove these outcomes through the implemented supervisor and its cleanup-failure path.

## Transcript and usage mapping

The production UI/replay path reads normalized content rather than SDK `ThreadItem` shapes (`prompt/transcript.ts`). The lifecycle persists neutral `content` events under the conversation descriptor and writes raw transcript envelopes without inspecting them (`actor-implementations.ts`). Preserve that split.

The event projector must cover completed assistant text, commentary/reasoning, command start/result, file changes, MCP invocation/result, web search, plan/todo updates, errors, and terminal status. Use item IDs to correlate streamed deltas and final items, and prevent repeated full-item notifications from duplicating normalized content. Final-response extraction must yield only the final answer used by structured-output validation; commentary must not become the answer merely because it arrived last. Preserve lossless native envelopes independently of visible content, with no second visible projection of a provider user-message echo.

Read JSONL by LF delimiters with a streaming UTF-8 decoder, not Node `readline`; `codex/sdk-line-splitting.test.ts` and the installed SDK patch cover the U+2028/U+2029 failure in the SDK path, but they do not protect a new reader. Apply the [transport bounds](README.md#transport-memory-bounds): 16 MiB per incoming record, 16 MiB queued archival/content payload, and a 256 KiB stderr tail. Reject oversized incomplete records before unbounded concatenation/parsing. Use `excludeTurns:true` on resume to avoid hydrating historical turns. Test split multibyte characters, multiple individually valid messages in a large chunk, CRLF, Unicode separators, oversize with/without LF, truncated final frames, slow consumers, and stderr flooding without logging prompt text or secrets. Complete valid frames remain lossless; rejected/truncated evidence is bounded and marked accordingly. Stored transcript scans separately enforce a 64 MiB per-record bound with LF-only UTF-8 decoding and no whole-history string/array. Invalid history stops instruction dispatch or makes lineage cost unknown.

These CC contract targets are preserved by [the main accounting decision](README.md#usage-account-per-process-accumulate-in-cc):

| CC field/behavior | Required meaning |
| --- | --- |
| `ConversationBackendTurnResult.costUsd` | Estimated cost attributable to this admitted CC turn, not the thread's entire history. Steering stays inside that same turn. |
| `cumulativeCostUsd` and persisted Codex result `raw.costUsd` | Thread-lineage cumulative cost compatible with `codex/transcript-projections.ts` and persisted restart baselines. Preserve `raw.turnCostUsd` separately. |
| `numTurns` | One admitted CC turn for one start/completion, regardless of the number of steer inputs or model/tool cycles. |
| `contextTokens`, `contextWindowMax` | Only report quantities whose app-server meaning is established. Do not label total billed tokens as context occupancy or enable `contextWindowMetrics` from the mere presence of a token counter. |
| `compacted` | Report observed provider context-loss/compaction evidence through the existing result path if supported; do not infer compaction from a reduced usage count. This affects memory-index delivery, not just telemetry. |
| Missing usage | Preserve unknown/null when the transport provides no defensible measurement. Do not silently treat unknown usage as zero. |

[The measured usage evidence](poc-results.md#accounting-findings) establishes that `total` accumulates within the app-server process and resets in the next process, while `last` describes a model request rather than the whole user turn. Under the one-process-per-admitted-turn invariant, use the last observed process `total` for turn attribution and add that turn's cost to the persisted CC lineage baseline. Never sum intermediate totals, subtract the previous process's counter, or bill only `last`. If a baseline event appears before `turn/start`, subtract that baseline within the same process. Require nonnegative, consistent, monotonic cumulative categories within that process; a decrease/reset or invalid counter makes affected turn/cumulative accounting unknown, with a diagnostic and raw evidence. Preserve valid observed usage on failed/interrupted turns; missing usage and unreadable historical cumulative baselines remain unknown with diagnostics. Compaction does not reset CC's cumulative ledger. Mapping tests cover these rules, and the macOS context-pressure extension observed monotonic counters through one actual compaction; billing totals do not enable context-window metrics.

The implementation updates `descriptor.ts`, `cost-baseline.ts`, and `transcript-projections.ts` to carry that policy: explicit unknown cumulative cost is preserved, unknown-cost result frames remain visible to usage projection, and the latest lineage state is authoritative. Preserve explicit null in the result and neutral usage projection (whose contract already permits it), and read the latest lineage result state, including unknown. A known later turn cost cannot recover missing earlier cost. Test known→unknown→restart→known-turn through actual transcript persistence/replay, not only the new runtime's return value.

Keep structured output under the current post-validation contract in `.kiro/steering/agent-backends.md`: the authored schema is a deterministic final-message instruction and the shared gate validates it. Adopting app-server native schema enforcement is independent scope.

## Cleanup ownership and deferred durability

The initial migration adds typed neutral cleanup evidence at `agent-backends/conversation.ts` and the Codex runtime, consumed by close/turn-completion lifecycle owners (`workflows/conversation/manager.ts`). Per-turn process teardown must finish or contribute cleanup failure **before** the final result is published, even when the reusable runtime remains installed. Keep failed live ownership and use the existing error-notification owner; notification is best effort and cannot substitute for cleanup verification. No provider error-string parsing or raw-frame inspection belongs above the adapter.

Persistent cleanup review remains deferred after the macOS CC-parent-death and escalation probes. Ordinary parent death reaped both observed processes; frozen-server escalation left an ordinary tool in its own process group. The selected decision treats that survivor as a manual-recovery condition and explicitly accepts restart-limited protection. The initial scope does **not** add `runtimeCleanupHold`, columns, durable admission/rehydration guards, or an acknowledgement API/CLI. Existing `stopFailure`/`durabilityFailure` are process-local (`manager.ts`), and conversation status is not an admission hold (`conversations/schemas.ts`). A restart loses retained live ownership, so recovery guidance must tell Alex to inspect/stop surviving commands before resuming. Do not claim a durable guarantee or repurpose checkpoint operations, workflow ownership, or uncertain queue rows.

If further evidence justifies durable protection, estimate/design it separately as shared lifecycle work for affected backends. Its review must cover both conversation repositories/codecs, turn admission (`production.ts`), live/next-turn queue claims (`message-queue-service.ts`, including commands), startup rehydration, and conditional explicit recovery under the existing exclusive actor owner. A recorded conversation hold would still not cover a parent crash before persistence, synthetic calls without durable rows, other conversations sharing a workspace, or old builds that do not enforce it. These limitations belong in that decision; they do not silently add the deferred machinery to this migration.
