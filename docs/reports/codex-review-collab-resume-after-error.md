VERDICT: REJECT

Architecture score: **3/10**. The sidecar is useful as a cache of completed model outputs, but it is not the complete, exactly-once checkpoint log the design claims. The proposed abstraction hides neither the gate-consumption boundary nor final delivery, and the lifecycle protocol has compound-claim, stale-conversation, stop, and zombie-worker races. Implementing this document as written would make some failed collaborations resumable while introducing paths that silently skip user input, splice incompatible artifacts, duplicate the final transcript, or resume into a newer conversation turn.

## BLOCKING issues

### 1. The central checkpoint claim is false: the sidecar records model outputs, not completed steps

**Evidence status: CODE-CONFIRMED.** For a clean, single-pass run, the proposed logical keys are mostly unique: two initial drafts are distinguished by agent, there is one cross-review, the three negotiation outputs are distinguished by round, and there is one gate/final output. That limited observation does not establish the claimed invariant.

The stored schema does not even implement the prose invariant that every line has `(kind, agent, round)`: `open_conflicts` has no `agent` (`src/lib/workflow-graph/collaboration-schemas.ts:573-584`), while initial-draft and cross-review schemas accept non-canonical agents and arbitrary integer rounds (`src/lib/workflow-graph/collaboration-schemas.ts:409-418`, `src/lib/workflow-graph/collaboration-schemas.ts:438-448`). The proposed per-kind key union is more accurate than the prose (`docs/designs/collab-resume-after-error.md:143-150`), but neither `trackArtifact` nor the sidecar enforces uniqueness (`src/lib/workflows/collaboration/helpers.ts:55-62`, `src/lib/workflows/collaboration/artifacts-store.ts:78-85`). The design itself acknowledges that current restart re-entry can append duplicate keys (`docs/designs/collab-resume-after-error.md:52-57`). A key is therefore a logical lookup key, not an existing uniqueness guarantee.

More importantly, a missing line does not prove the work did not happen. `callPrimitive` completes the backend call and records lane continuity before returning (`src/lib/workflows/collaboration/helpers.ts:282-311`); the `WorkflowAgentCaller` also persists its post-turn lane outcome before returning the result (`src/lib/workflows/primitives/workflow-agent-caller.ts:269-278`, `src/lib/workflows/primitives/workflow-agent-caller.ts:411-427`). The agent has already written deterministic markdown paths in the worktree (`src/lib/workflows/collaboration/artifact-files.ts:35-91`) before the phase parses, validates, and appends the structured artifact. A crash or append failure in that window leaves generated files, billed provider work, backend history, and an advanced lane ref but no ledger line. Re-entry sends the prompt again against already-mutated state and can overwrite those files. This is at-least-once execution, not the rule “an absent artifact means the step has not happened” asserted at `docs/designs/collab-resume-after-error.md:84-97`.

The parallel phase supplies a concrete counterexample to “every completed step is already logged.” Both calls finish before processing begins (`src/lib/workflows/collaboration/initial-draft.ts:76-119`), but an Agent One file-validation failure returns before a successful Agent Two result is tracked (`src/lib/workflows/collaboration/initial-draft.ts:121-163`). The current log can therefore omit the successful peer even without a process crash.

There are also meaningful operations with no artifact checkpoint: policy evaluation, lane initialization/outcome writes, the Alignment seen-version mutation (`src/lib/workflows/collaboration/initial-draft.ts:219-259`), gate consumption, transcript delivery, conversation release, and backend-ref advancement. Pure or idempotent operations need not all become artifacts, but gate consumption and final delivery are separate correctness boundaries and cannot be inferred from the model-output line.

Required change: narrow the sidecar contract to “recorded model output that may be reused,” explicitly document the unavoidable at-least-once provider-call window, and make resume validate a canonical causal prefix before dispatching. Do not claim universal step checkpointing.

### 2. The proposed parallel `runCollaborationStep` refactor loses deterministic commit ordering and does not honor its gather promise

**Evidence status: CODE-CONFIRMED design consequence.** Today only the two backend calls are concurrent; parsing and artifact commits occur in deterministic Agent One then Agent Two order, and call failures become terminal only after both successful results have been processed (`src/lib/workflows/collaboration/initial-draft.ts:76-103`, `src/lib/workflows/collaboration/initial-draft.ts:121-190`).

The design moves parse, validation, `trackArtifact`, persistence, and failure handling inside `runCollaborationStep` (`docs/designs/collab-resume-after-error.md:158-184`) and then runs two whole helpers concurrently (`docs/designs/collab-resume-after-error.md:186-189`). `trackArtifact` pushes to shared memory without serialization and then awaits an independent `appendFile` (`src/lib/workflows/collaboration/helpers.ts:55-62`, `src/lib/workflows/collaboration/artifacts-store.ts:78-85`). The in-memory order used by the original run can therefore differ from the on-disk order used after restart. That violates the design's own requirement that replay seed the same ordered prompt history (`docs/designs/collab-resume-after-error.md:128-133`). If one helper terminalizes through `failRun` while its sibling commits, the sibling can append a line after failure while its envelope progress update is refused by the terminal guard (`src/lib/workflows/collaboration/envelope.ts:822-843`).

Required change: keep concurrent execution but separate it from commit. Gather both outcomes, validate both, commit successful artifacts in a canonical order through one serializer, and only then choose the terminal outcome. The generic helper must not own `failRun` for parallel peers.

### 3. `final_answer` is not an idempotent step and can be appended or delivered twice

**Evidence status: CODE-CONFIRMED.** The generic helper is specified to track and persist every live artifact, while the design also retains `finalizeFinal` for post-step work (`docs/designs/collab-resume-after-error.md:168-189`). Current `finalizeFinal` begins by tracking `finalAnswer` itself (`src/lib/workflows/collaboration/envelope.ts:1002-1013`). Unless the extraction contract explicitly removes that write, even the non-crash path can append two `final_answer` lines.

The deeper problem is the final-delivery window. The final artifact is appended before its file is read (`src/lib/workflows/collaboration/envelope.ts:1012-1044`), before the answer is appended to the originating transcript (`src/lib/workflows/collaboration/envelope.ts:1047-1064`), before the conversation is released and its backend ref advanced (`src/lib/workflows/collaboration/envelope.ts:1067-1104`), and before envelope completion (`src/lib/workflows/collaboration/envelope.ts:1106-1122`). A crash after transcript append but before completion leaves a replayable final artifact and a failed/running envelope; re-entry repeats finalization and appends the assistant answer again.

The production callback uses non-idempotent `safeAppendTranscriptEntry` (`src/lib/workflows/collaboration/deps-factory.ts:176-180`, `src/lib/prompt/transcript.ts:1420-1437`), and the entry passed by the finalizer has no stable `id` (`src/lib/workflows/collaboration/envelope.ts:1050-1057`). The codebase already has an ID-based `appendTranscriptEntryOnce` primitive (`src/lib/prompt/transcript.ts:311-342`). The artifact also precedes conversation status/ref mutations, so artifact replay alone cannot tell which of those effects committed.

Required change: treat “final output produced” and “final output delivered” as different states. Give the transcript entry a stable ID such as `collab-final:<workflowId>` and use the idempotent append API; make conversation release/ref advancement idempotent and attempt-fenced; then record or derive an explicit final-delivery receipt before completing the envelope. Test every crash boundary, not merely failure of the final model call.

### 4. `open_conflicts` proves that questions were generated, not that the user resumed

**Evidence status: CODE-CONFIRMED.** The design interprets an existing `open_conflicts` line as “the user has been asked and has chosen to proceed” (`docs/designs/collab-resume-after-error.md:213-231`). Current code appends that artifact first, then persists the paused envelope, and only afterward publishes/notifies the pause (`src/lib/workflows/collaboration/envelope.ts:934-980`). A crash after line 946 but before the later mutations produces a gate artifact the user may never have seen. Under the proposed restart policy, that envelope becomes `failed` (`docs/designs/collab-resume-after-error.md:327-337`); failure resume then carries no token or answers (`docs/designs/collab-resume-after-error.md:272-278`) and silently bypasses the unseen questions.

This is not equivalent to the code being deleted. The current short-circuit requires both an `open_conflicts` artifact and an explicit `input.resume` (`src/lib/workflows/collaboration/envelope.ts:719-725`), after `manager.resume` verified the pause token (`src/lib/workflows/collaboration/manager.ts:1604-1612`). That explicit resume invocation is the missing consumption fact.

Two narrower claims are valid but do not save the reduction:

- A genuine round-2-of-5 pause currently ends negotiation at round 2; with the same snapshot and policy implementation, replaying rounds 1 and 2 and then finalizing reproduces that behavior.
- A genuine paused resume with zero answers also finalizes today; the current manager passes an explicit resume payload even when its merged answer map is empty (`src/lib/workflows/collaboration/manager.ts:1667-1689`, `src/lib/workflows/collaboration/manager.ts:1757-1772`), and `runResumeFinalAnswer` does not require a non-empty answer list (`src/lib/workflows/collaboration/envelope.ts:1278-1296`).

A later failure after an answered pause adds another missing contract. Prior answers are currently merged into the durable snapshot and supplied again (`src/lib/workflows/collaboration/manager.ts:1667-1689`), but the design says a failed resume carries no answers and does not say how the stored answers reach the rebuilt final prompt. Deleting the special path must not delete that reconstruction.

Required change: persist a distinct gate-consumed receipt, bound to the gate round/token and answer snapshot, or recover a terminal unconsumed `open_conflicts` artifact back to a real pause. Artifact presence alone must never mean consent.

### 5. The ledger is not fail-closed and can splice new upstream work into old downstream artifacts

**Evidence status: CODE-CONFIRMED.** The design uses an empty stream as the fresh-run signal (`docs/designs/collab-resume-after-error.md:153-156`) and says a corrupt stream will fail on a missing prerequisite (`docs/designs/collab-resume-after-error.md:363-365`). The current reader returns `[]` both when the file is absent and when the read fails, and it removes malformed or schema-invalid lines before returning the remaining entries (`src/lib/workflows/collaboration/artifacts-store.ts:149-199`). The slice's read dependency is optional as well (`src/lib/workflows/collaboration/envelope.ts:271-286`). A transient read failure can therefore redispatch the entire run as if it were fresh.

Skipping an interior line is worse. If a `proposed_changes` line is corrupt but its old `counter_proposal` and `resolution_decision` remain valid, the proposed loop runs a new proposed-change step and then replays downstream outputs that were generated from the old one. The design specifies no causal-prefix check. It also specifies no reject/first/last policy for duplicate keys even though current restart behavior can create duplicates (`docs/designs/collab-resume-after-error.md:52-57`), and the ledger tests cover neither duplicates nor gaps (`docs/designs/collab-resume-after-error.md:367-371`). Any arbitrary duplicate choice can mix attempts.

Required change: make the resume read seam required and discriminated (`absent | valid | unreadable | corrupt`), preserve line diagnostics, reject duplicates and non-canonical keys, and validate that the stream is one causal prefix of the phase graph before any model call. Existing sidecars with duplicates need an explicit migration/refusal policy; silently choosing a map entry is unsafe.

### 6. Re-evaluating policy is deterministic only under an unstated version/configuration invariant

**Evidence status: DESIGN-TEXT REASONING backed by CODE-CONFIRMED policy inputs.** The current policy is pure over the recorded resolution, threshold, and rounds remaining (`src/lib/workflows/collaboration/policy.ts:104-148`). Therefore a valid prefix replayed by the same code with the exact same snapshot will make the same decision. That is the part of `docs/designs/collab-resume-after-error.md:203-207` that is correct.

The design does not persist a policy version or policy outcome. A process restart after deployment can run changed policy code over old resolutions. Supported legacy envelopes can also reconstruct missing inputs from current defaults: current resume defaults missing brief/round/backend fields and re-parses the threshold (`src/lib/workflows/collaboration/manager.ts:1625-1657`). If an earlier replayed round now says `fail` or `ask_user` where the original said `continue`, the orchestrator stops before later recorded artifacts that are already in the sidecar. Nothing in the design rejects or supersedes that impossible suffix. If it says `ask_user`, the run can create a new gate alongside later-round evidence; if it says `fail`, it becomes terminal without consuming the suffix.

There is also a code-confirmed permanently failing class. A `resolution_decision` is persisted before policy evaluation (`src/lib/workflows/collaboration/resolution.ts:245-264`); `next_action === "fail"` deterministically maps to policy failure (`src/lib/workflows/collaboration/policy.ts:104-115`), after which the envelope is marked failed (`src/lib/workflows/collaboration/envelope.ts:498-508`). The design makes every `failed` envelope claimable and offers Resume for every failure (`docs/designs/collab-resume-after-error.md:267-278`, `docs/designs/collab-resume-after-error.md:313-322`). Such a run replays the resolution and fails again forever without a live step.

Required change: distinguish operational/retryable failure from semantic policy failure and expose Resume only for the former. Persist/version the policy contract or record policy outcomes, and reject a stream whose recorded suffix disagrees with the policy version used for replay.

### 7. `claimForRun` is atomic for one envelope, but the proposed resume claim is not atomic

**Evidence status: CODE-CONFIRMED.** The narrow compare-and-set can be implemented correctly: `WorkflowEnvelopeStore.upsert` explicitly owns serialized read-modify-write (`src/lib/workflows/primitives/workflow-envelope-store.ts:34-46`), production executes the mutator inside one session-state mutation (`src/lib/workflows/primitives/workflow-envelope-store.ts:156-184`), and that mutation holds the shared write queue across read/mutate/write (`src/lib/state-store/setters.ts:2066-2095`). Within Command Center's supported single-process writer model, two envelope claims can therefore yield one winner.

That does not make the manager protocol atomic. The design deliberately reclaims the conversation before claiming the envelope (`docs/designs/collab-resume-after-error.md:279-282`). Those are separate queued mutations. If the envelope claim loses, Stop wins between them, or the process exits, the conversation remains `running` with no worker. Reversing the order merely strands the envelope instead. A shared queue serializes two calls; it does not turn them into one transaction.

The answer/history write is underspecified too. Current resume persists merged answers and then separately marks the envelope running (`src/lib/workflows/collaboration/manager.ts:1667-1689`). The proposed `claimForRun` signature has no snapshot patch (`docs/designs/collab-resume-after-error.md:248-254`). If answers/resume history are written before the claim, a losing request can contaminate the winner; if written afterward, a crash leaves a claimed worker without its inputs.

Finally, the claim only promises to clear `errorSummary` (`docs/designs/collab-resume-after-error.md:239-247`). Repository terminal transitions can stamp `completedAt`, and running transitions do not clear it (`src/lib/workflows/primitives/workflow-envelope-repository.ts:131-190`). A resumed envelope can therefore be `running` with its prior failure completion time, and a later completion can preserve that stale value.

Required change: expose one collaboration-owned `claimCollaborationResume` operation that atomically checks and updates the envelope, conversation generation/ownership, answers, failure history, `resumeCount`, attempt epoch, `errorSummary`, `pause`, and `completedAt`. It should live behind the conversation/workflow lifecycle seam, not as two feature-level mutations. Use the real persistence fixture because the guarantee depends on SQLite serialization (`AGENTS.md:69-82`).

### 8. The conversation idle predicate is neither a generation check nor the actual single-flight mechanism

**Evidence status: CODE-CONFIRMED.** The assertion that `new | awaiting` proves no later prompt occurred (`docs/designs/collab-resume-after-error.md:283-292`) is false. A normal prompt completes by incrementing `promptCount` and returning to `awaiting` (`src/lib/workflows/conversation/machine.ts:889-914`). A user can finish an entire intervening turn after collaboration failure; the proposed predicate then accepts the stale collaboration and later appends an obsolete answer/advances the backend ref. Start already demonstrates the correct generation technique: it checks `expectedPromptCount` and idle state atomically before incrementing (`src/lib/workflows/collaboration/manager.ts:349-379`). The collaboration snapshot currently stores no claimed count (`src/lib/workflows/collaboration/envelope.ts:734-751`). Allowing `new` is also unexplained for a run whose start necessarily incremented the count.

Persisted `status = "running"` is not the server's prompt lock. Prompt admission checks the process-local conversation single-flight registry (`src/lib/prompt/route-handlers.ts:328-369`); the collaboration reclaim does not acquire it. A newly created conversation actor derives `new/awaiting` from `promptCount`, ignoring the persisted `running` value (`src/lib/workflows/conversation/machine.ts:408-420`), and accepts `SUBMIT_PROMPT` from idle (`src/lib/workflows/conversation/machine.ts:468-490`). An already-settled actor can also be reused without rereading the manually changed row (`src/lib/workflows/conversation/manager.ts:618-649`). The UI status is therefore not an exclusive claim against another API caller.

The state cases the design must handle are:

| Event | Envelope | Persisted conversation | Result under the proposed predicate |
|---|---|---|---|
| Normal slice failure | `failed` | usually `awaiting`, but release is best-effort (`src/lib/workflows/collaboration/envelope.ts:859-903`, `src/lib/workflows/collaboration/envelope.ts:1143-1169`) | Usually accepts; can falsely reject forever after a release failure. |
| Ask-user pause | `paused` | remains `running` (`src/lib/workflows/collaboration/envelope.ts:920-972`) | Correctly needs no second claim, but still does not hold the real prompt lock. |
| Process restart | proposed `failed` | remains the pre-crash `running` row because workflow recovery mutates only envelopes (`src/instrumentation.node.ts:301-336`, `src/lib/workflows/primitives/recover-workflow-envelopes.ts:118-145`) | Always rejects the ticket's restart-resume path until some other event repairs the row. |
| User prompt starts after failure | `failed` | `running` | Correctly rejects while that prompt is live. |
| That user prompt finishes | `failed` | `awaiting`, with a higher `promptCount` (`src/lib/workflows/conversation/machine.ts:893-905`) | Incorrectly accepts the stale run. |
| Stop while paused | `completed` | remains `running`; direct Stop mutates only the envelope (`src/lib/workflows/collaboration/manager.ts:1849-1882`) | Leaves the conversation stranded even though the workflow is terminal. |

This also violates the architecture contract that the conversation lifecycle module owns turn submission, completion, persistence, and attached-workflow cancellation (`CONTEXT.md:206-209`). Required change: persist the collaboration's claimed conversation generation, compare it on every resume/release, and make ordinary prompt admission and collaboration ownership share one lifecycle API. Startup recovery and paused Stop must repair/release that ownership explicitly.

### 9. The terminal guard does not fence zombie attempts, and Stop can race a resumed dispatch

**Evidence status: CODE-CONFIRMED.** The design claims that after `failed -> running`, an old worker's straggler write is still refused by the existing terminal guard (`docs/designs/collab-resume-after-error.md:261-265`). The guard checks only the envelope's current status (`src/lib/workflows/collaboration/envelope.ts:822-843`). Once the new claim makes that status `running`, an old attempt passes. Manager-level exception handling bypasses the slice guard entirely with an unconditional repository update (`src/lib/workflows/collaboration/manager.ts:171-212`). Even when an old envelope update is refused, `failRun` still releases the conversation and publishes failure, and `finalizeFinal` performs artifact/transcript/conversation effects before its guarded envelope update (`src/lib/workflows/collaboration/envelope.ts:859-903`, `src/lib/workflows/collaboration/envelope.ts:1002-1122`). Status is not a worker identity.

There is a direct claim-to-dispatch race. The existing analogous path marks running, builds dependencies, registers the Stop controller, and dispatches in separate steps (`src/lib/workflows/collaboration/manager.ts:1686-1689`, `src/lib/workflows/collaboration/manager.ts:1691-1755`, `src/lib/workflows/collaboration/manager.ts:1783-1819`). Stop can observe `running` before registration, find no controller, and mark the envelope completed (`src/lib/workflows/collaboration/manager.ts:1849-1882`); resume then registers and dispatches anyway. At slice entry, `initializeEnvelope` unconditionally writes `status: "running"` without a terminal/attempt check (`src/lib/workflows/collaboration/envelope.ts:701-753`), so it can reopen the just-stopped envelope.

Stop is not active cancellation of the in-flight provider call. The slice checks `stopSignal` only between phases (`src/lib/workflows/collaboration/envelope.ts:354-405`), while the production conversation backend creates and passes its own timeout/stall controller (`src/lib/workflows/collaboration/agent-caller-production.ts:359-410`). An in-flight resumed call can keep spending and later append an artifact after Stop. The proposed identity-checked registry release (`docs/designs/collab-resume-after-error.md:339-347`) fixes only one teardown race. The shared registry already exposes compare-and-delete (`src/lib/shared/abort-registry.ts:49-67`), which collaboration currently bypasses with unconditional release (`src/lib/workflows/collaboration/manager.ts:871-891`).

Required change: add a durable attempt epoch/capability returned by the claim and require it on every envelope transition, artifact commit, conversation release/ref update, and terminal side effect. Thread cancellation into both backend call paths, recheck ownership after controller registration, and make slice initialization distinguish fresh creation from claimed re-entry. The graph workflow's `(executionId, loopEpoch)` fence is the local precedent (`.kiro/steering/workflows.md:709-720`). Fence provides correctness; cancellation limits cost. Both are required.

### 10. Dropping a token for failed resumes loses failure-instance binding and request idempotency

**Evidence status: DESIGN-TEXT REASONING backed by CODE-CONFIRMED current token checks.** Current requests always require a token and manager verifies it against the observed pause (`src/lib/workflows/collaboration/manager.ts:245-249`, `src/lib/workflows/collaboration/manager.ts:1604-1612`). The design argues that an envelope CAS is enough for failure resume because there are no answers to bind (`docs/designs/collab-resume-after-error.md:272-278`). That only fences requests concurrent with the same `running` interval.

It does not fence a delayed retry from an earlier failure instance. Example: failure generation N is displayed, a resume request claims it, that attempt quickly fails as generation N+1, and then a delayed browser/network retry of the original request arrives. With no expected token/epoch, the stale request can claim N+1 and spend again. A version also supplies audit provenance and protects deliberate retry UX from cached tabs or automation replay. “No answer payload” does not mean “no state transition to bind.”

Required change: issue a fresh failure-resume token or expose an `If-Match`-style attempt generation for every resumable terminal instance. It need not misuse the paused envelope projection; it belongs in a collaboration-owned resumability/attempt record. The atomic claim must compare it and consume it.

### 11. Backward compatibility and exact staffing replay are unspecified and, for some supported records, impossible

**Evidence status: CODE-CONFIRMED.** The design promises verbatim replay of models, effort, profiles, round count, threshold, and context (`docs/designs/collab-resume-after-error.md:349-358`). Current typed user snapshots deliberately allow `sessionContext` and `agents` to be absent for persisted legacy envelopes (`src/lib/workflows/collaboration/feature-snapshot.ts:39-58`). Current resume falls back to default brief/round/backend values and, when `agents` is absent, re-resolves models and efforts from current global configuration without the original profile snapshots (`src/lib/workflows/collaboration/manager.ts:1625-1657`, `src/lib/workflows/collaboration/manager.ts:1696-1734`). That contradicts the architecture promise that profile snapshots replay the stored instruction block byte-for-byte (`CONTEXT.md:272-281`) and that collaboration staffing is fixed at start (`CONTEXT.md:289-295`). The original profile cannot be reconstructed after the fact.

Current sidecars also need a compatibility policy for duplicated restart attempts, canonical ordering, truncated last lines, and interior invalid lines; issue 5 explains why a permissive map is unsafe. Existing failed envelopes may lack the proposed normalized failure, history, resume count, conversation generation, or attempt epoch. Adding those persisted fields must update the collaboration-owned schema and durability contracts rather than relying on a permissive `Record<string, unknown>` (`AGENTS.md:69-82`, `src/lib/workflows/primitives/workflow-envelope-vocabulary.ts:20-25`). Backward-compatibility shims require Alex's explicit approval (`AGENTS.md:45-52`).

Required change: define a versioned strict executable snapshot and an eligibility matrix. For records without sufficient premises, choose explicitly between refusing resume with a restart instruction or an approved, visibly non-verbatim fallback. Do not claim exact replay for data the system never stored.

### 12. A smaller design meets the ticket without the universal-step abstraction

**Evidence status: DESIGN-TEXT ASSESSMENT grounded in the confirmed boundaries above.** The proposed generic `runCollaborationStep` and general-purpose primitive `claimForRun` are over-built for ticket #81 while still omitting the hard state transitions. The graph path is explicitly out of scope (`docs/designs/collab-resume-after-error.md:359-362`) and already uses a stronger execution-specific epoch fence (`.kiro/steering/workflows.md:709-720`), so speculative graph reuse is not a reason to put an envelope-only claim in the primitive layer (`docs/designs/collab-resume-after-error.md:257-259`).

A materially simpler, safer scope is:

1. Resume only operational failures explicitly marked resumable; exclude semantic policy failure, corrupt streams, and legacy records without an exact executable snapshot.
2. Add one collaboration-owned, versioned resume record containing `attemptEpoch`, failure-instance token, claimed conversation `promptCount`, prior failure history, and gate-consumption/answer state.
3. Add one atomic `claimCollaborationResume` lifecycle operation that validates and claims both envelope and conversation, clears terminal fields, and returns the immutable run snapshot plus epoch.
4. Read the sidecar as a fail-closed, canonical causal prefix and use its artifacts only to avoid model-output calls. Put small replay checks at the existing phase boundaries or behind a narrow `replayOrRunModelOutput` helper. Preserve the current deterministic parallel gather/commit structure.
5. Keep ask-user consumption and final delivery as explicit, idempotent transitions; use a stable transcript entry ID. Thread Stop into live calls and fence every commit by epoch.

This retains the design's useful “reuse recorded model output” idea without pretending one artifact rule covers user consent, provider execution, conversation ownership, or delivery. To reach 10/10, the revision needs all five properties plus a declared migration policy, usage accounting, structured observability, and crash-window tests on the real persistence store.

## NON-BLOCKING issues

### 1. “Durable append” is stronger than the implementation proves

**Evidence status: CODE-CONFIRMED.** The sidecar uses `appendFile` and awaits it, but performs no file `sync`, directory `sync`, transaction with SQLite, or append serialization (`src/lib/workflows/collaboration/artifacts-store.ts:31-32`, `src/lib/workflows/collaboration/artifacts-store.ts:78-90`). `trackArtifact` also mutates the in-memory tracker before awaiting that append (`src/lib/workflows/collaboration/helpers.ts:55-62`). The design should define durability as “append completed at the Node filesystem API” unless it adds a stronger crash-persistence protocol. This wording does not fix the blocking cross-store windows above.

### 2. Resumed-run cost accounting has no durable owner

**Evidence status: CODE-CONFIRMED plus DESIGN-TEXT OMISSION.** Agent results expose per-call cost, cumulative cost, duration, and token usage (`src/lib/workflows/primitives/agent-call-vocabulary.ts:156-168`), but lane persistence retains tokens/context and drops cost/duration (`src/lib/workflows/primitives/workflow-agent-caller.ts:430-465`, `src/lib/workflows/primitives/lane-vocabulary.ts:37-58`). A failed billed call may produce no artifact at all, so the ledger cannot reconstruct spend. The design records only resume count/failure history (`docs/designs/collab-resume-after-error.md:293-311`) and has no accounting test (`docs/designs/collab-resume-after-error.md:367-389`). Specify whether collaboration cost is attempt-level, run-level, or intentionally unavailable; if recorded, distinguish incremental from provider-cumulative values so resume does not double-sum them.

### 3. Observability is not designed at the new decision boundaries

**Evidence status: DESIGN-TEXT OMISSION measured against CODE-CONFIRMED logging contract.** Current resume logging records coarse dispatch/result facts (`src/lib/workflows/collaboration/manager.ts:1774-1791`), and the project requires stable structured events without secrets or prompt contents (`AGENTS.md:85-88`). The revision should name events/fields for claim won/refused, expected versus observed conversation generation, attempt epoch, resumed-from status/failure, ledger read outcome, duplicate/gap rejection, replayed versus live keys/counts, gate receipt, final-delivery dedupe, Stop fencing, incremental usage, and terminal outcome. Do not log resume tokens, profile instructions, or prompts.

### 4. The promised resume-conflict API response is not wired in the route design

**Evidence status: CODE-CONFIRMED.** The UI section promises an inline 409 when conversation reclaim conflicts (`docs/designs/collab-resume-after-error.md:313-322`). The current RESUME handler maps ownership, token, paused-state, and session-context errors, then turns everything else into 500 (`src/lib/workflows/collaboration/route-handlers.ts:665-709`). The revised design must specify the new domain error/code and the route mapping; reusing `CollaborationStartConflictError` without adding a RESUME catch will not meet the UI contract. The client mutation and row renderer also currently require `resumeToken` (`src/lib/workflows/mutations.ts:721-746`, `src/features/session/hooks/use-collab-row-renderer.tsx:50-59`), so failed and paused submissions need an explicit discriminated request type rather than scattered optional assertions.

### 5. The test plan misses the failures that define correctness

**Evidence status: DESIGN-TEXT OMISSION backed by CODE-CONFIRMED seams.** The proposed tests cover happy replay and one claim race (`docs/designs/collab-resume-after-error.md:367-389`) but not: unreadable/truncated/interior-corrupt/duplicate sidecars; Agent One validation failure with successful Agent Two; crash between gate artifact and pause; crash after final artifact, transcript, conversation release, or ref update; a later prompt that completes before resume; restart with a stale `running` conversation; crash between the two proposed claims; Stop before controller registration or during an in-flight resumed call; repeated fail/resume tokens and `completedAt`; legacy staffing/config; or failed-attempt cost. Concurrency/durability tests must use `createPersistenceFixture`, not only the in-memory store (`AGENTS.md:76-83`).
