# Performance sweep — root-cause designs

**Date:** 2026-07-20
**Input:** Two-week log audit (2026-07-06 → 2026-07-20), 822k records; findings and trace IDs in the audit report (chat) and the `performance-sweep-log-findings` memory.
**Status:** IMPLEMENTED 2026-07-21 (was DESIGN v3). Approved 2026-07-20 (all three decision points), then amended twice the same day: first after an Ousterhout-style review (projection-tier vocabulary, context-field disposition contract, seam interface contracts, `mutateActive` naming), then after an external Codex design review whose findings were independently verified in code (post-commit event delivery, `WriteQueue`-boundary enforcement + `tryWithWriteQueue` overlap race, dev-server premise correction, sidecar ownership across two parent tables, TS-level drift guard, corrected migration inventory). **Out of scope by Alex's direction (2026-07-20): a generic async-retry mutation API, and the async session-provisioning job redesign.** Each design names its prevention mechanism, because the goal is to make this class of regression structurally unlikely, not to patch the five current instances.

**Implementation status (2026-07-21, recorded by the final-verification context):** all Phase 0–3 designs below landed and are wired on their production paths; each carries a `Resolved issues` entry in `PERFORMANCE.md`. The phased table matches what shipped. The two scope-outs are honestly absent from the code (no `mutateActiveWithAsyncWork`, no async session-provisioning job scaffolding). Two elements were legitimately narrowed during implementation and are recorded here rather than left implied: (1) Design 5's dev-server work moved the durable-acceptance boundary and instrumented every pre-202 phase, but reducing the *remaining* synchronous pre-spawn latency (port selection stays ahead of the boundary because it owns the `409 UNMANAGED_DEV_SERVER_DETECTED`/`EADDRINUSE` ordering) is deferred to an evidence-based follow-up using the new phase spans; (2) end-to-end verification found write-queue callbacks the original migration missed that still resolved config file I/O inside the critical section — all now **remediated** in-workflow, not deferred. `mcp/config-mutation-service.ts` `patchGlobal` and `mcp/runtime-apply.ts` `applyAfterOverrideChange` (siblings of the migrated `config-mutation-service ×3` and `applyAtTurnStart`) now resolve + hash + decide outside the queue and commit only a short synchronous fenced write; `applyAfterOverrideChange` additionally gained a focused existence pre-read, and both apply paths (`applyAfterOverrideChange` and `applyAtTurnStart`) now run their whole body through a per-conversation in-process apply serializer, so moving the resolve out of the lock cannot let a slow stale resolve overwrite — durably or on the live runtime — what a newer submission already applied (a strict-submission-order guarantee, not a generation drop). And `agent-capabilities/scope-store.ts` `patchSession`/`patchConversation`/`patchProjectConversation` — which awaited the effective-hash **precondition** (discovery + whole-chain file I/O) inside their `mutateSession`/`mutateConversation` callbacks — were a genuine `no-slow-work-in-critical-section` violation independent of ever being `mutateState` sites (they were never mutateState sites, but that is orthogonal to holding slow work in the lock). They now run the precondition **outside** the queue and commit under a deep-equal fence with a bounded retry, exactly mirroring the already-fixed `patchProject`. These fixes dropped the async `withWriteQueue` ratchet baseline to **55**, and every one carries a `PERFORMANCE.md` Resolved-issues entry and a queue-gate test (an unrelated write acquires the queue while the slow work is in flight — the pre-fix code deadlocks it). A further verification pass closed a logging-I/O boundary miss: `write-queue.ts` `settle()` emitted its `write_queue.timing` line *before* releasing the FIFO, and the four generic mutators plus the four focused capability setters nested their `state.mutate` timing wrapper *inside* the queue callback — a synchronous `appendFileSync` under the lock. `settle()` now releases before it logs, and every migrated seam wraps `timed()` around the queue CALL (recorded in the 2026-07-21 `PERFORMANCE.md` entry, proven by a release-ordering probe and a queue-exit-before-log store test). The *per-operation* repo-timing helpers (`state-store.*.timing`) and the non-migrated MCP/session setters still emit their structured line from inside the held section; this is the established microsecond-cost logging architecture (not the external-work class this sweep eliminates) and is recorded as a **named telemetry follow-up** in that entry rather than a further remediation task.

## Diagnosis: three root causes, not five symptoms

The audit surfaced five findings (full-state read cost, multi-second write-queue holds, uninstrumented worst-case routes, blocking "202" dev-server starts, 1,314 failed ephemeral-conversation mutations). They reduce to three architectural root causes plus two conventions gaps:

- **RC-A — `ManagerState` still exists as a readable/mutable product.** PERFORMANCE.md Patterns 1–2 moved most traffic to focused accessors, but the whole-state surface survives: 10 `mutateState` call sites across four files, per-turn `readState` in MCP runtime-target listing (`src/lib/mcp/default-deps.ts:192`) and agent-capabilities resolution (`src/lib/agent-capabilities/default-deps.ts:174` — reads *everything* to extract one project's overrides), and the aggregate's `readAll`/`diffAndCommit` cycle behind them. Anything that can pay O(total-state) on a hot path eventually will — the lint gate blocks new *imports* but not DI-injected handles, and the allowlist is static, not a ratchet.
- **RC-B — unbounded opaque blobs ride the hot rows.** `machineSnapshot` is `z.unknown()` (`src/lib/conversations/schemas.ts:252`), so the Pattern-7 blob-bounds gate cannot see inside it. Inside: `context.lastResult.contentBlocks` (2.96MB on the worst row — the full turn output, which the transcript already owns) and `children` (2.2MB of child-actor snapshots). 41.5MB of snapshot bytes across 154 conversations is what every `SELECT *` enumeration drags through, and why `findAll` degraded ~5× in two weeks.
- **RC-C — the global write queue accepts arbitrary async work in its critical section.** `mutateActive` runs the caller's async callback inside the queue (`src/lib/workflow-graph/execution-repository.ts:357` — worst observed hold 45.5s). `mutateState` holds it through a full-state read + clone + 2× Zod + full diff. `mcp.applyAtTurnStart.resolve` does a whole-state *read* while holding the *write* lock. Nothing bounds hold time; every violation silently stalls all writers and (via bun:sqlite's synchronous calls) the event loop.
- **Gap 1 — async semantics by convention only.** The dev-server start route already asks for a non-blocking start (`ensure({ wait: false })`, in place since 2026-05-25) yet still blocked 9–29s in the audit window: `ensure`'s pre-202 phases — session reconcile, the once-per-process tailscale orphan cleanup, port resolution, and the awaited `startServer` spawn — all run before the response. "202 means accepted, not performed" exists nowhere as a checkable rule.
- **Gap 2 — instrumentation is opt-in and traces don't propagate into the store.** The two worst routes had zero spans; `write_queue.timing` events carry no `traceId`, so a 45.9s request blocked on the queue is unattributable from logs.

The designs below are ordered by leverage, not by finding number.

## Design 1 — Make the machine snapshot a resume token, not an archive (RC-B)

**Change (two parts, both recommended):**

1. **Persist a projection, not the raw XState snapshot.** Introduce an explicit persisted-snapshot codec in `src/lib/workflows/conversation/persistence.ts`: `toPersistedConversationSnapshot(snapshot)` keeps what rehydration actually consumes (machine `value`/`status`, `context` identity fields, `backendRef`, `totals`, `activeTurn` identity, `debugMode`, queue/turn bookkeeping) and **drops `lastResult.contentBlocks` and `children`**. The transcript is the system of record for content; the snapshot is a resume token. `lastResult` keeps its scalars (cost, tokens, error, aborted) — consumers needing blocks read the transcript. The projection gets a real Zod schema replacing `z.unknown()`.

   **Codec interface contract:** *a persisted snapshot contains exactly what rehydration needs to resume the machine and re-attach its backend; all content is re-readable from the transcript.*

   **Drift guard (required, not optional):** a projection creates a dual-schema — the machine's context shape and the persisted schema can now diverge, and the failure mode (a resume-relevant field silently dropped) surfaces only on a restart after a crash. Every context field therefore carries an explicit disposition — `persist` | `derive-on-rehydrate` | `drop`. **Enforcement (corrected after external review):** the machine context is a TypeScript interface (`ConversationContext`, `src/lib/workflows/conversation/types.ts:112`), not a Zod schema, so the exhaustiveness guard is compile-time — a disposition map typed `satisfies Record<keyof ConversationContext, Disposition>`, making a newly added context field fail `bun run typecheck` until someone decides its fate. The persisted projection itself gets the runtime Zod schema (new code, schema-first). This adapts the tier-key union precedent from the `graph_workflow_executions` split (PERFORMANCE.md 2026-06-20) to a TS-interface-shaped source.
2. **Move the snapshot off the hot row.** New sidecar table `conversation_machine_snapshots(owner, conversation_id, snapshot_json, updated_at, PRIMARY KEY (owner, conversation_id))`, following the `graph_workflow_executions` split precedent (PERFORMANCE.md 2026-06-20): written only by `persistConversationSnapshot`, read only by per-conversation rehydration. `conversations.findAll`/`findBySession`/`rowToDomain` never see it; `ManagerState` conversations drop the field. Idempotent Umzug migration moves existing blobs (applying the projection as it copies).

   **Ownership (added after external review):** `machine_snapshot` lives on **two** parent tables today — `conversations` *and* `project_conversations` — so an ID-only sidecar would have ambiguous ownership and no reliable cleanup path. The `owner` discriminator (`session` | `project`) ties each row to its parent repo; each parent's `delete` removes its sidecar rows in the same transaction, and a contract test asserts no orphan sidecar rows survive either parent's delete. Both parents migrate — which also means the audit's 41.5MB figure *undercounts* the problem (it measured `conversations` only).

Part 1 kills write amplification (a debounced 5MB rewrite per transition becomes a few KB) and shrinks the DB; part 2 makes whatever remains invisible to every enumeration. Either alone helps; together the ~42MB scan tax and its growth curve disappear.

**Prevention:**
- The typed schema closes the `z.unknown()` blind spot: the persisted-blob-bounds contract can finally walk the snapshot. Additionally, extend `findUnboundedCollections` policy so an **opaque (`unknown`/`any`) node inside a registered persisted blob is itself a finding** requiring an explicit `tracked:` discharge — the next opaque blob can't hide.
- **Row-size telemetry:** repos log `state-store.row_size.exceeded` (warn, with table/column/id/bytes) when a serialized column crosses a threshold (proposed 256KB). Growth becomes a ranked log finding within days instead of a p95 archaeology project after two weeks.

**Risk / open point:** rehydration must genuinely not need dropped fields — needs a consumer inventory of `machineSnapshot` reads during implementation (14 sites in `workflow-manager.ts` are graph-execution snapshots, a different field; the conversation-snapshot readers are `rehydration.ts` + `persistence.ts`). If some flow reads `lastResult.contentBlocks` post-restart, it moves to the transcript read path.

## Design 2 — Finish focused-first, then delete the whole-state surface (RC-A)

**Change:**

1. **Migrate the remaining hot readers onto a projection-tier vocabulary.** Accessors are designed around a small set of recurring projection tiers, **not around callers**:
   - **identity** — key columns only (id / project / session / status), no blobs, no Zod-heavy parse. Serves MCP `defaultListGlobalRuntimeTargets` (needs identity tuples, not state) via a new `listConversationIdentities()`.
   - **list-item** — identity plus the display scalars list surfaces need. The existing rich-vs-thin conversation-list split already has this shape; cross-project list, discovery, and active-conversations migrate onto it.
   - **detail** — one entity's full slice; the existing `getSession`/`getConversation` tier. Agent-capabilities resolution needs one project's overrides → `getProjectAgentCapabilityOverrides(projectPath)`, sibling of the existing `getProjectMcpOverrides`.

   **Review rule:** a new accessor must serve a tier, not a caller. Two callers wanting slightly different subsets of the same tier share the accessor; a caller-shaped accessor (`getStateForMcpTargets()`-style) is the `storeUser()`/`storeProduct()` trap and gets rejected in review. This is what keeps the store's interface from growing linearly with call sites as the migration completes.
2. **Migrate the 10 `mutateState` sites (inventory corrected after external review)** — `sessions/service.ts` (×5: `createSession`, `rollbackSession`, `retargetOrphanedChildren`, the bulk-delete family), `mcp/config-mutation-service.ts` (×3), `mcp/scope-store.ts` (×1), and `agent-capabilities/scope-store.ts` (×1) — to focused repo mutations in short transactions, following the `mutateSession`/`mutateConversation` precedent entries. The sessions/mcp-config labels are exactly the audit's worst write-queue holds (14.2s / 17.4s / 11.3s). The authoritative inventory is the grep at migration time, not this list — the migration's first task re-derives it, so a caller added between design and implementation can't be silently skipped.
3. **Delete the surface.** Remove `readState`/`mutateState`/`writeState` from the store's public API, and with them `diffAndCommit` + `cloneAndValidate`. Startup rehydration — the one honest whole-state consumer — gets a private `readAllForStartup()` owned by the startup module, not exported through the store index, and (with Design 1) it no longer hydrates snapshot blobs for every conversation.

**Prevention:** deletion is the guardrail — the DI loophole in the lint gate and the static allowlist both vanish with the API. Until deletion lands, fold the `WHOLE_STATE_ALLOWED` count into the existing seam ratchet (`bun run seams:check`) so the number can only go down; a new whole-state caller fails CI rather than lint-with-allowlist-edit.

**Why this beats "optimize `readAll`":** caching, `parseTrusted`, and the versioned row cache have each already been applied (PERFORMANCE.md Patterns 3/8) and the operation *still* costs O(everything) on every version miss — because it is O(everything) by definition. The class of bug only dies when the operation does.

## Design 3 — The write queue only ever holds short, synchronous commits (RC-C)

**Change:**

1. **`mutateActive` becomes a synchronous reducer; the generic async form is out of scope.**
   - `mutateActive(reducer)` — reducer typed **non-async** (`(exec: GraphWorkflowExecution) => Result`, not `Promise`). Runs inside the queue. The type system makes "await an LLM while holding the global lock" unrepresentable. **Interface contract:** *reducer runs inside the global write queue; it must be synchronous and pure — no I/O, no awaits, nothing that can block.* Several callers already fit (e.g. `join-runner`'s `applyJoinProgress` reducers are sync-pure today).
   - Slow callers (the 45.5s / 20.8s holds) get **caller-specific staged protocols**: *reserve* (a short sync mutation that records intent and fences an epoch) → perform the slow work outside the lock → *fenced finalize or compensate* (a short sync mutation that re-checks the fence before committing — the loop-fence machinery is the precedent). Designed per caller during migration, because each caller's effects (worktree writes, artifact emission, event publication) need their own compensation story.
   - A generic retry-based `mutateActiveWithAsyncWork` is **explicitly out of scope** (Alex, 2026-07-20, on external-review advice): no current caller can satisfy an idempotent-`fn` contract — today's callbacks broadcast SSE inside (item 2 below), so a conflict retry would double-publish. Revisit only when a provably effect-free-until-commit caller exists.

   Migrate callers (execution-route-handlers, join-runner, validator-runner, execution-tool-context, iteration paths); delete the unrestricted form.
2. **Event delivery moves after commit (added, from external review).** `publishExecutionUpdate` currently *broadcasts* SSE/push inside the mutation callback (`execution-events.ts` → `publishEvents` → `publishEvent`), while the SQLite transaction commits afterwards in `setters.ts` — a thrown commit has already told every client the mutation happened. Event *rows* already persist atomically with state in the same transaction; that stays. The redesign: mutation callbacks **derive** events (pure) and return them — which `mutateActiveGraphWorkflowExecution`'s signature already shapes — and the mutation seam delivers them **after** its transaction commits. Prevention is structural, not conventional: callers lose access to delivery entirely; the seam owns delivery timing, so pre-commit broadcast becomes unrepresentable at the call site.
3. **Enforcement lives at the `WriteQueue` boundary, not per-wrapper (revised, from external review).** Constraining only `mutateActive` misses every other mutation path. The queue gains a sync-callback entry point as the default reach; the async entry survives only for callers whose awaits are queue-internal by design (the async Immer mutators that `mutateConversation` exists to support), tracked in a ratchet that can only shrink. Separately, **`tryWithWriteQueue` has a live overlap race today**: it checks `pendingCount` but never reserves `tail`, so a normal queued write chains onto the old resolved tail and runs concurrently with an in-flight try-write — two writers at once. The fix (reserve the tail exactly as `withWriteQueue` does) ships as a **standalone Phase-0 correctness fix** with an overlap regression test, independent of the perf program.
4. **Reads never happen under the write lock.** `mcp.applyAtTurnStart.resolve` (386ms avg hold ×140) resolves its config *before* entering the queue and commits only the result. With Design 2 this becomes a focused read anyway; the rule generalizes: queue callbacks contain repo writes and pure computation only.
5. **Hold budget as a loud invariant.** `withWriteQueue` measures hold time (it already does) and logs **error-level** `write_queue.hold_budget_exceeded` with label + captured enqueue stack when hold > budget (proposed 500ms). Not a kill switch — aborting mid-write is worse — but every future violation becomes a ranked, attributable event, and `logs:analyze` gains a finding rule for it (see Design 6).

**Prevention:** the sync-callback type contract at the queue boundary prevents the whole category at compile time; seam-owned post-commit delivery makes phantom events unrepresentable; the hold budget catches whatever squeezes through any path; staged reserve/finalize protocols give slow work a correct home so nobody is tempted to "just await inside."

**Deliberately not proposed:** sharding the write queue per entity. After 1–3 the queue only ever holds sub-ms–to–tens-of-ms transactions; added lock granularity is complexity without a measured need. Revisit only if post-fix telemetry still shows contention.

## Design 4 — Persistence is a construction-time facet; ephemeral conversations get the null one (RC-A adjacent)

**Change:** `compaction-*` and `__validator__:*` conversations run the full conversation machine wired to durable persistence actions (`syncDerivedFields`, `persistSnapshot`, mark-read/unread), then fail 1,314 times because their row was never created — each failure paying the full write-queue + focused-read pipeline first. Make persistence an injected facet of the conversation runtime, chosen at construction (consistent with the backend-facet architecture in `.kiro/steering/agent-backends.md`). **Coverage requirements (strengthened after external review):**
- The mode is a **required discriminated field** — `persistence: durable | ephemeral` with no default, so constructing a runtime without deciding fails to compile.
- **One adapter covers every persistence path**: machine actions (`syncDerivedFields`, `persistSnapshot`, mark-read/unread), invoked/child actors, and notification side effects all go through the same injected adapter — a facet that only intercepts the top-level actions would leave invoked-actor and direct-DB paths writing durably behind an "ephemeral" label.
- `createProvidedMachine` receives the adapter instead of importing `mutateConversation` directly.

**Facet interface contract:** *the adapter owns every durable side effect of the conversation lifecycle — `durable` persists derived-field sync, snapshots, and read-state transitions; `ephemeral` guarantees zero state-store writes for the runtime's entire life.* The contract test below is that sentence made executable.

**Prevention:** the decision moves from "every action checks (or forgets to check) whether this conversation is real" to one explicit choice where the conversation is created — the next ephemeral conversation kind inherits correct behavior by construction. Contract test (verification target corrected after external review): an ephemeral runtime driven through a full turn produces **zero database table changes**, asserted by diffing the real SQLite fixture before/after — not by counting write-queue calls, which would miss any path that bypasses the queue.

## Design 5 — Long-running work is a job you observe, not a request you hold (Gap 1)

**Change:**
- **Dev-server start (premise corrected after external review):** the route has passed `wait: false` since 2026-05-25 — the original design's "pass the flag" fix was moot. The audit's 9–29s blocking lives in `ensure`'s synchronous pre-202 phases: `reconcileSessionDevServers`, the once-per-process tailscale orphan reconcile, port resolution, and the awaited `startServer` spawn. The design work is therefore: instrument each phase with `timed()` spans (Design 6 makes them attributable), then define the **durable-acceptance boundary** — what must be true before the 202 (intent recorded, spawn *initiated*) versus what belongs to observed readiness via the existing dev-server SSE reactions — and move the phases that exceed the boundary behind the response. `cctl dev ensure` keeps its blocking UX client-side, which it must already support for the crash-after-start case. *(Implementation note: `wait` is a flag parameter switching `ensure` between two concepts — start vs. start-and-await. When this code is touched, prefer splitting into `ensure()` + `awaitReady()` over propagating the boolean.)*
- **Session creation (narrowed — async job redesign out of scope):** the full async-provisioning job design (durable job ID + 202 response schema, lifecycle states, restart recovery, route gating until `ready`, client migration off the synchronous 201) is **explicitly out of scope** (Alex, 2026-07-20); the synchronous response flow stays. What remains in scope is the part that hurts everyone else: `createSession` stops holding the **global write queue** across external work (worktree add, `bun install`) — that falls out of Design 2's `mutateState` migration, which converts the persisted state changes into short focused transactions around the external steps.

**Prevention:** write the convention down where route authors look — `.kiro/steering/structure.md` (route composition) and `data-fetching-and-sse.md`: *a 202 response must not await the work it accepts; work expected to exceed ~1s runs as a job with SSE progress.* Then make it measurable: a `logs:analyze` finding flags 202 responses with `durationMs > 1000` as convention violations, so drift shows up in the next report instead of the next incident.

## Design 6 — Observability that attributes by default (Gap 2)

**Change:**
1. **Every route provably wrapped (revised after external review).** `withTracing` (`src/lib/logging/tracing.ts`) already establishes request-scoped AsyncLocalStorage context and root timing — that is *why* the audit could see the 45.9s request at all; the floor is not zero, and re-adding root spans would duplicate what exists. The actual gaps: an **architecture test** asserting every route export is `withTracing`-wrapped (so a new route can't ship outside the tracing net), and interior `timed()` phase spans for the two known offenders (conversation `queue` POST, `context-artifacts` GET).
2. **Attribution names the culprit, not just the victim (revised after external review).** Store timing events (`write_queue.timing`, `state.read.timing`, repo timings) carry no `traceId` today. Two additions: (a) stamp events from the ambient `TraceContext` — this names the request *suffering* a wait; (b) the write queue records **current-owner metadata** (the label and trace of the mutation *holding* the queue) on every wait it causes — this names the request *causing* it. Ambient trace alone can never answer "what was the 45.9s POST blocked on?"; owner metadata turns that from an archaeology project into one log line.
3. **Budgets as code.** `logs:analyze` gains a checked-in budget config (per-route-class p95 ceilings, write-queue hold ceiling, `state.read` ceiling, row-size ceiling) and an `--assert-budgets` mode (nonzero exit on violation). Run advisory for a week to calibrate, then wire into the perf-sensitive-change workflow PERFORMANCE.md already prescribes, plus an optional scheduled weekly report. The two-week silent 5× degradation this audit found becomes a same-week red number.
4. **Tooling (diagnosis corrected; fix already landed):** the original "wrapped log line poisons the prelude" theory was **wrong** — there is no bad log line. The actual cause is a DuckDB 1.5.4 `->>`/`->` operator-precedence bug: two extracts in one expression swallow the rest of the predicate as the path argument, and the resulting conversion error names an arbitrary record. Already fixed in this worktree (uncommitted): a `jget()` macro (`json_extract_string`) in `prelude.sql` plus `TRY_CAST` timestamp hardening, a selftest probe in `run.sh`, and updated README/skill guidance. Nothing further to design here.

## Explicitly out of scope (and why)

- **A generic async-retry mutation API** (`mutateActiveWithAsyncWork`). No current caller can honor an idempotent-retry contract while callbacks publish events; slow callers get caller-specific reserve → work → fenced finalize/compensate protocols instead (Design 3.1). Revisit only when a provably effect-free-until-commit caller exists. (Alex, 2026-07-20.)
- **The async session-provisioning job redesign** (durable job ID, 202 schema, lifecycle, restart recovery, route gating, client migration). The synchronous creation flow stays; only the global-write-queue hold across external work is eliminated, via Design 2's migration. (Alex, 2026-07-20.)
- **Moving SQLite to a worker thread.** After Designs 1–2 the remaining synchronous reads are small row fetches; the event-loop freezes the audit observed were O(everything) operations that will no longer exist. Worker isolation is a large architectural swing with real costs (serialization boundary, transaction semantics); reassess against post-fix telemetry, with Design 6's budgets as the trigger.
- **Voice transcription / pre-merge / `bun install` latency.** External costs. Worth a smaller upstream timeout than the observed 60s hang for voice, but not architecture.

## Suggested sequencing

| Phase | Designs | Rationale |
|---|---|---|
| 0 | 3.3 `tryWithWriteQueue` race fix + overlap test | Standalone correctness bug (two writers can overlap today) — ships immediately, independent of the program |
| 1 | 1 (snapshot projection + sidecar), 6.2 (waiter + owner attribution) | Biggest byte lever; attribution makes every later phase verifiable |
| 2 | 2 (focused-first completion + deletion), 3 (queue contracts + post-commit delivery) | Frequency lever + worst-stall elimination; 3 depends partly on 2's migrations |
| 3 | 4 (ephemeral facet), 5 (dev-server phase instrumentation + acceptance boundary), 6.1/6.3 (route-wrap test, budgets) | Independent; parallelizable |

Verification per phase follows PERFORMANCE.md practice: red→green TDD on contracts (zero-write ephemeral runtime, sync-reducer typing, focused-read spy aggregates), then `logs:analyze -- compare` before/after on a live build, then a budget-clean weekly report.

## Decision points — APPROVED 2026-07-20

1. **Design 1.1 snapshot projection** — dropping `lastResult.contentBlocks`/`children` from the persisted snapshot changes what survives a process restart mid-conversation (content re-reads go to the transcript). **Approved.**
2. **Design 2.3 deletion** — removing `readState`/`mutateState` from the public store API is the point of no return for the whole-state pattern; the alternative (permanent allowlist + ratchet) is weaker but reversible. **Approved.**
3. **Design 3 budget value** (500ms hold) and **Design 6 budget ceilings** — proposed numbers are calibration starting points from this audit's data, not sacred. **Approved as starting points.**
4. **Post-review revision (2026-07-20, external Codex review — directed by Alex):** Design 3 reshaped (generic async-retry API **out of scope**; post-commit event delivery added; enforcement moved to the `WriteQueue` boundary; `tryWithWriteQueue` race fix pulled into Phase 0), Design 5 narrowed (async session-provisioning job **out of scope**; dev-server premise corrected to phase instrumentation + acceptance boundary), Design 1 sidecar gains the two-parent `owner` discriminator, Design 4 verification switched to DB-diff. The prior approvals (items 1–3) are unaffected in substance.
