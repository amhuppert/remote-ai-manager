## Key Learnings

### Technical assumptions that were validated or fell
- **Claude `strictMcpConfig: true` + `setMcpServers()` full-list replacement** — verified by Alex empirically. The plan hardcodes `strictMcpConfig: true` in `query-session.ts` and pushes the full effective list (all discovered user servers the user hasn't disabled + CC gateway servers) through both the initial `mcpServers` option and `setMcpServers()` between turns. The SDK docs describe `setMcpServers()` as only affecting dynamically-added servers, but with `strictMcpConfig: true` the filesystem sources are bypassed so the dynamic set IS the complete effective set.
- **Codex `mcp_servers.<name>.enabled = false` native honoring** — ✅ VERIFIED 2026-04-20 (codex-cli 0.118.0 + `@openai/codex-sdk` 0.118.0). Spike at `memory-bank/phase-0-spikes/codex-enabled-false.ts` (+ `mock-mcp-server.mjs`). Control run: server spawned, `ping` tool called, `"pong"` returned. Disabled run: server NOT spawned (sentinel file never created), zero `mcp_tool_call` events, agent replied `"TOOL_NOT_AVAILABLE"`. Full findings in `memory-bank/phase-0-verification.md`. Existing `translatePortableMcpToCodex` already emits `enabled` unconditionally — no translator change needed.
- **SSE transport** — dropped from MVP. Parsed from source files but excluded from emission with a `discovery.sse_unsupported` warning.
- **Per-backend compatibility filter** — needed because canonical `PortableMcpServerConfig` fields like `cwd`, `bearerTokenEnvVar`, `startupTimeoutSec`, `toolTimeoutSec` are Codex-only; Claude rejects them. New `src/lib/mcp/backend-compat.ts` module filters per active backend; incompatible rows render read-only in UI.

### Review-driven architecture corrections
- **Schemas in `src/lib/schemas.ts`** — project convention, not a separate `override-schema.ts` module.
- **State mutator in `src/lib/conversations.ts`** (service layer), not `src/lib/state.ts` (persistence primitives).
- **`runtimeState.tooling.portableMcp` is reserved for transient injected tools** (workflow-graph). Resolved conversation MCP is a LOCAL variable at turn start, never written back to runtime state.
- **PATCH serialization** via per-conversation `apply-mutex` keyed by `${projectPath}::${sessionName}::${conversationId}` prevents "newer state + older apply" interleaving.
- **Lazy tool discovery** via `/mcp/tools/[serverId]` endpoint (GET cache-preferred, POST force-refresh). GET `/mcp` does NOT eagerly fetch tools (avoids spawning every stdio server on popover open).
- **CC-injected gateway servers hidden from UI** (per focus.md: always on, not togglable).
- **`runtime-registry`** (keyed by `conversationId`) is authoritative for "is there a live backend runtime"; separate from the path-keyed workflow runtime-state map.
- **`McpApplyResult` shared contract untouched**. Route-local response adds `no_active_runtime` disposition via its own wrapper type (`patchMcpOverridesResponseSchema`).

### Pending-badge rule covers:
- `applied_now` → clear
- `deferred_to_next_turn` / `no_active_runtime` → set; cleared on `isRunning: true → false` transition
- `unsupported` / `rejected` / network error → clear + inline error state (don't leave user in phantom pending)

## Background Context

### Project
Command Center (CC) — a Next.js 16 web control plane for managing Claude Code and Codex sessions running in isolated git worktrees. Each session is a worktree + branch; each conversation runs via the `@anthropic-ai/claude-agent-sdk` `query()` API or the `@openai/codex-sdk`.

### Feature requirements (from `memory-bank/focus.md`)
1. Per-conversation toggle of individual MCP servers (scoped to one conversation).
2. Per-tool filtering within a server (discover tools dynamically, allow/deny individual ones).
3. Hierarchical defaults via patch model (global → project → conversation); only conversation level ships in MVP.
4. Mid-conversation reconfiguration — toggle during an active turn queues the change for next turn; UI shows pending badge.
5. Backend-agnostic — Claude + Codex today, pluggable for future backends.
6. Read-only toward user config files (`.mcp.json`, `settings.json`, `~/.codex/config.toml`). CC stores overrides in its own state.

### Out of scope for MVP
- CRUD of MCP servers in UI (users still hand-edit config files).
- User-level / project-level default overrides (schema reserves; UI deferred).
- `enabledTools` allowlist (only `disabledTools` ships).
- `disallowedTools` name-mangling as canUseTool alternative (future optimization).

### Key existing abstractions used
- `PortableMcpConfig` at `src/lib/agent-backends/portable-mcp.ts` — canonical cross-backend shape.
- `translatePortableMcpToClaude` / `translatePortableMcpToCodex` at `src/lib/agent-backends/mcp-translation.ts` — emission boundary.
- `ConversationBackendRuntime.applyPortableMcpConfig` — per-turn apply hook.
- `ConversationBackendCapabilities` — declares `portableMcpAtStart` / `portableMcpBetweenTurns`.
- Backend registry at `src/lib/agent-backends/registry-core.ts`.
