# Dev Server Fixes — Context Save (2026-05-31)

## Summary

Fixed a macOS-only bug in CC's dev-server port-ownership detection that caused "Could not verify ownership of port X for worktree …: listener_lookup_failed: port listener lookup failed: ss and lsof both unusable" errors when starting dev servers via the UI, even though the servers actually started successfully (they showed up as "ADOPTED" on the next refresh).

Branch: `csm/dev-server-fixes-6d23b1`. Worktree: `.worktrees/dev-server-fixes-6d23b1`. Changes are staged but **not committed** — the user has not requested a commit.

## Key Learnings

### The bug

`src/lib/dev-server/port-ownership.ts` had a `getExitStatus()` helper that read `err.status` from caught exec errors. That field is populated by `execSync` but **not** by promisified `execFile` — async exec errors put the exit code on `err.code` instead. The async production code path (`defaultListListeningPids`) used `execFileAsync`, so:

1. On macOS, `ss` isn't installed → caught silently, `ssOk = false`.
2. `lsof -tiTCP:<port> -sTCP:LISTEN` exits with code **1** when the port is free (no listener match) → rejects with `err.code = 1`.
3. `getExitStatus(err)` returned `null` (looked for `.status`), so the `=== 1` branch was missed.
4. Fell through to `else if (!ssOk)` → threw "ss and lsof both unusable".
5. `classifyPort` returned `{ status: "unknown", reason: ... }`.
6. Reconciler (`reconciliation.ts:132`) set entry to `error` with the "Could not verify ownership" message — even though the server had started fine.

The batched listener lookup (`defaultListAllListeningPorts`) works because `lsof -iTCP -sTCP:LISTEN` (no port filter) finds listeners system-wide and exits 0. That's why adoption later succeeded.

### Dev-server architecture details (gathered in conversation)

These aren't documented in one place — captured here so a successor doesn't have to re-explore:

**Ownership detection** (`port-ownership.ts:120-203`, `classifyPort`):
- Lists PIDs listening on a port (`ss`, falling back to `lsof`).
- For each PID, reads its cwd (`/proc/<pid>/cwd` on Linux, `lsof -d cwd` on macOS).
- Compares cwd to the session's worktree path (and an optional `allowedCwd` for subdir-based apps), with symlink-aware realpath normalization.
- Returns `available` (no listener), `owned` (cwd inside worktree), `conflict` (listener cwd outside), or `unknown` (tool failure).

**Three detection mechanisms**:
1. `liveness.ts` — 5s timer, re-classifies running entries' ports, demotes on loss. Only started by `startServer`; adoption alone never starts it.
2. `reconciliation.ts` — runs on every `list`/`ensure` call. `verifyRunningEntry` for running entries; `tryAdoptExternal` (`findOwnedListenerInRange`) sweeps the preset port range to discover entries CC didn't start.
3. Spawn-time classification — after CC_PORT/readiness, `classifyEntrySource` decides `cc-started` vs `external-adopted` by PID/pgid matching.

**`cc-started` vs `external-adopted`** — functional differences beyond stdout capture:
- Stop kill: cc-started runs `killProcessGroup(_pid)` first, falls back to port-PID kill. Adopted has `_pid: null`, so only the port-PID kill runs — sibling processes spawned by the adopted server won't be cleaned up.
- Remote URL: `tryAdoptExternal` sets `remoteUrl: null` and never calls `deferredRemoteUrlRegister`. Adopted servers get no Tailscale registration / no LAN URL.
- Liveness polling: only `startServer` calls `livenessStart()`. If only adopted servers exist, the 5s timer never runs — death is detected only when something triggers reconciliation.

**`cc-assigned` vs `stdout-cc-port` startup strategies** — functional differences:
- Port discovery location: cc-assigned scans in CC (Node, `port-selection.ts`); legacy scans in the child shell script.
- "Running" semantics: cc-assigned gates on TCP probe (port actually bound); legacy transitions immediately on `CC_PORT=<n>` stdout line (may pre-date `listen()`).
- Spawn cwd: cc-assigned spawns directly in `cwd` subdir; legacy always spawns at worktree root and the script `cd`s itself.
- Timeout: cc-assigned uses `readiness.timeoutMs` from config (configurable); legacy uses hardcoded `STARTUP_TIMEOUT_MS = 60_000`.
- Command shape: cc-assigned takes direct commands; legacy requires `.cc/dev-servers/<name>.sh` wrapper.
- Likely-racy gap: when `selectPort` Pass 1 returns `source: "external-adopted"`, `service.ts:486-493` builds startMode from that port and `startServer` always spawns — would EADDRINUSE if reconcile didn't already adopt first. Worth investigating.

**Registry key**: `${projectPath}::${sessionName}::${serverName}` — `name` is the within-session identifier.

## Open Questions / Challenges

1. **Should we also harden `defaultListAllListeningPorts`?** It catches errors and returns an empty `Map`, so the same exit-code-shape bug wouldn't surface — but if both ss and lsof legitimately fail there, adoption silently stops working with no error surfaced to the user. Probably fine to leave; flagging for awareness.

2. **`selectPort` "external-adopted" path looks racy** (see Key Learnings above). `service.ts:486-493` builds a startMode from the selected port even when Pass 1 found it owned by an existing listener. Reconcile should normally short-circuit before this path runs, but if it doesn't (e.g. timing window, missing scan hint), CC would try to spawn on an already-bound port. Not part of this fix — worth a follow-up investigation.

3. **Adopted servers don't get Tailscale/LAN remote URLs**. `tryAdoptExternal` sets `remoteUrl: null` and never calls `deferredRemoteUrlRegister`. This is a real functional gap — adopting a server forfeits the remote-access feature. Unclear if intentional.

4. **Adoption doesn't start liveness polling**. If a user only ever has adopted servers (never CC-started anything), the 5s liveness loop never runs. Death detection then depends entirely on UI fetches triggering reconciliation. Likely an oversight.
